# Ночной замер: аналитика V7 и конкуренты на ваших реальных событиях

Прогон 21.10.2026, 04:06–12:06. Все цифры измерены в этом прогоне на локальной копии реальных событий проекта `puzzle_gravity_test` (**994 564 события, 217 установок**, выгрузка 20.10). Сырые данные и скрипты лежат в `night-run~/` (`STATE.md` — журнал, `results/` — результаты, `results/TABLES.md` — все таблицы).

## 0. Как читать и чему верить

* **Это не телефон.** Физического устройства нет. Android-замеры сняты на эмуляторах arm64 (API 35 и API 25) на Apple Silicon, Unity-замеры — IL2CPP-сборка на эмуляторе API 35. Абсолютные микросекунды на реальном телефоне будут другими (обычно хуже); **сравнение SDK между собой** на одном стенде корректно, абсолютные значения — нет.
* **Что измерено, а что нет.** Размер в сети Firebase/Facebook/Adjust/GameAnalytics/Amplitude/HyperKit — снят с реальных запросов SDK (TLS-приёмник, коллектор). Оценок и «цифр из интернета» в таблице нет. Не измерено: батарея, температура, физический телефон, ARMv7 (эмуляторов нет), серверная часть конкурентов.
* **Нагрузка на компьютер.** Часть замеров снималась при нагрузке 20–37 на 10 ядрах (другие процессы + мои параллельные задачи), затем я повторил ключевые серии в тихом режиме (нагрузка 1–6). Использую **CPU-время потока** (не реальное время) и **калибровку**: фиксированный тест (4 МБ рабочего набора) выполняется между блоками замеров; значение CPU умножается на `эталон / текущая калибровка`.
  * Проверка метода (V7-кодек на хосте, искусственная нагрузка 0/6/12/20 «ядер»): сырой CPU 8,0–8,9 мкс (тихо) → 9,1–9,9 (нагрузка 6–12); **с поправкой 7,4–8,2 мкс во всех режимах (±5%)**. Реальное время при нагрузке 20 выросло вдвое (9 → 19,5 мкс). **Аллокации не зависят от нагрузки** (21 616 Б/событие ровно во всех прогонах).
  * На эмуляторе поправка слабее (разброс 8–50%), потому что нагрузка влияет и на гипервизор. Поэтому везде даны 3 повтора и разброс.
  * Урок: при замере Unity общий CPU процесса оказался непригоден — поток рендера эмулятора (`UnityGfxDeviceW`) прыгает 405 ↔ 775 тиков за 40 с независимо от SDK. Везде ниже считаются **только потоки SDK**.

## 3. Другие SDK: что именно мы видели

* **Firebase Analytics 23.0.0.** Реальные запросы к `app-measurement.com` перехвачены (эмулятор API 25, свой CA в системном хранилище, TLS-приёмник). В боевом режиме: 35 аплоадов на 3003 события (≈86 событий, ≈64 КБ proto в аплоад), **73,1–73,2 Б/событие gzip** (три прогона), 742 Б/событие в proto до gzip. В режиме отладки (`debug.firebase.analytics.app`) 370–600 Б/событие: каждое событие уходит почти отдельным запросом — этот режим не годится для сравнения.
  * **Потери данных:** SDK пишет в лог `Event can't contain more than 25 params` и оставляет только 25 свойств. У ваших событий максимум 28; затронуты 217 277 из 994 564 (21,85%), потеряно 651 831 свойство. Строки длиннее 100 символов (по документации Firebase обрезаются) есть в 22,8% событий (226 893 значения) — эту часть я проверял только по документации, не по payload.
  * **Где считается CPU.** На API 35 основная работа (проверка, база, подготовка аплоада) идёт в процессе `com.google.android.gms`, на API 25 — в приложении. Поэтому для Firebase добавлен CPU процесса GMS. На API 35 он оказался нереалистично большим (≈10 мс/событие), потому что без сети там идёт шторм повторных попыток; надёжнее строка API 25 (940 мкс в приложении + 1538 мкс в GMS).
* **GameAnalytics 7.2.0.** 75,5 Б/событие (gzip, 600+ событий на запрос). При темпе 100 событий/с доставлено 100%, но 5% событий пришли не идентичными: пропали 73 булевых и 2 пустые строки из 34 527 свойств (0,22%). **Залпы без пауз (замер ёмкости, API 35, ждали 4 минуты):** 1500 → 1576 дошло, 3000 → 3145, 6000 → 3524, 12000 → 3940. То есть до 3000 событий в очереди GameAnalytics не теряет ничего, а дальше **держит около 3500–3900 событий и отбрасывает остальное** (при 12 000 событий потеряно 67%; цифры выше 100% — служебные события сессии).
* **Amplitude 2.40.1.** Тело ≈ 2005 Б/событие без сжатия; в залпе загрузка идёт 30 событий за запрос, и за 5 минут уходит лишь 17–34% залпа (при темпе 100/с — 84,7% за 150 с). Свойства сохраняет без потерь. Залп 1500 событий с пакетом 100: за 10 минут дошло 1100 (73%), 11 запросов по ≈ 200 КБ.
* **HyperKit (Gamestoty).** Настоящий код отправки из пакета Puzzle (`Gamestoty.java`, URL заменён на локальный приёмник). Схема фиксирована: событие, level, stage, `context` (строка), поля устройства. Без `context` свойства не передаются вообще (384 Б/событие); с полным JSON в `context` — 1132–1148 Б/событие, данные без потерь. Отправка: первый запрос только после 5 с или события `app_start`; накопленное уходит **одним запросом без ограничения размера** (12 000 событий → один POST около 13,9 МБ, без сжатия, 1155 Б/событие), доставлено 100%.
* **Facebook App Events.** 6 запросов на 600 событий (до 101 события, gzip, 67,4 Б/событие); числа и булевы превращаются в строки.
* **Adjust.** Это не пакетная аналитика: один HTTPS-запрос на событие (тело 2006 Б без сжатия + ≈ 825 Б заголовков), 37,5 мс CPU и 5 МБ аллокаций на событие (включая TLS на эмуляторе API 25).

## 4. Находки в нашей системе (в порядке важности)

1. **Дедлоки при параллельной приёмке** (SQLSTATE 40P01): `INSERT INTO event_catalog … ON CONFLICT DO UPDATE` выполняется в произвольном порядке в разных транзакциях; клиент получает `500 internal_error` (в V7 — «Retry»). Воспроизведено при нагрузке на машину и 4–8 параллельных установках, на тихой машине 0 из 6 прогонов — то есть ошибка зависит от тайминга. Путь общий для V1 и V7, не вносится V7. Заведено как issue #0126; предложение: upsert имён в отсортированном порядке одним запросом. Лог: `results/server/dbg3_v1/pg.log`.
2. **Лимиты приёма зашиты в код** (`internal/ingest/service.go:57–67`): на установку 12 запросов/мин (всплеск 30), на проект 30 запросов/с (всплеск 100), на IP 100/с. Одна установка не может отправить больше ≈ 1200 событий в минуту; залп из 6000 событий выгружается 5 минут (V1 и V7 одинаково). Это нужно знать до больших бэклогов (после офлайна).
3. **V7 кодировщик расточителен по аллокациям** (21,6 КБ/событие, 77% — разбор JSON); на устройстве это даёт на 40% больше сборок мусора, чем V1.
4. **Размер пачки:** клиент, отправляющий по 10 событий, получает 41,9 Б/событие вместо 17,8. Порог отправки стоит выбирать с учётом этого.
5. **Firebase режет 22% событий Puzzle по параметрам** (см. §3) — если событий с более чем 25 свойствами много, Firebase не годится как полная замена.

## 6. Что не измерено или измерено слабо

### 8.1. ARMv7 (закрывает известный пробел)

Отдельная сборка Unity IL2CPP только под `armeabi-v7a` (в APK лежит `lib/armeabi-v7a/libdaliys_zstd.so`) запущена на телефоне как настоящий 32-битный процесс (`primaryCpuAbi=armeabi-v7a`). Нативный zstd загрузился, 1200 событий принято, **12 пакетов V2 дошли до сервера, 1200 событий в базе, откатов на V1 нет**. Значит, 32-битная ветка V7 работает на реальном железе. Не проверено: старые 32-битные ядра Cortex-A7/A53 (на этом чипе 32-битные приложения идут на ядрах, которые это умеют).

### 8.2. V7 против V1 в Unity на телефоне (IL2CPP arm64, 3 повтора, сумма потоков SDK без потока рендера)

| Режим | V1 | V7 |
|---|---|---|
| залп 2800 событий (20 за кадр): CPU SDK, мкс/событие | 864 | 929 (+7%) |
| темп ≈30 событий/с, 1200 событий: CPU SDK, мкс/событие | 7 400 | 7 433 (+0,4%) |
| сборок мусора (залп) | 52 | 74 (+42%) |
| рост PSS, МБ (залп) | +28,3 | +27,0 |
| рост PSS, МБ (темп 30/с) | +15,7 | +15,9 |
| время `Track()` p50 / p99, мкс (залп) | 88 / 1 975 | 100 / 1 488 |
| кадр p99, мс (залп) | 6,6 | 7,9 |
| сервер получил | 2800 событий, 28 пакетов V1 | 2800 событий, 29 пакетов V2 |

* **V7 по CPU неотличим от V1** (в пределах 7%): стоимость кодирования тонет в стоимости очереди. Больше сборок мусора (+42%) подтверждается и на телефоне.
* **Находка про очередь, общая для V1 и V7:** при темпе «событие за кадр» SDK тратит около **7 мс CPU на событие** (в залпе 0,9 мс), `Track()` занимает 430 мкс p50 (в залпе 90–100 мкс). Это ~8-кратная надбавка, которую даёт не кодировщик, а путь записи в очередь (я не профилировал поток; наиболее вероятно — отдельная запись в SQLite на каждое событие). Для игры, шлющей событие каждый кадр, это главный клиентский расход.
* В покое (SDK создан, событий нет, 60 с): пустой плеер 1595 тиков, V1 1636, V7 1646 — SDK добавляет ≈ 0,7–0,8 мс CPU/с (несколько тиков в секунду), и V7 неотличим от V1.

* **Размер в сети на телефоне** совпал с эмуляторным (это свойство SDK, не устройства): GameAnalytics 75,8–75,9 Б/событие, Amplitude 1 980 Б/событие, HyperKit 383 и 1 132 Б/событие.

### 8.4. Что изменилось в выводах

1. Пробел «ARMv7 не проверялся» закрыт.
2. Клиентская цена V7 против V1 на реальном железе — в пределах 7% по CPU и +42% сборок мусора; сетевой выигрыш 9× остаётся.
3. Главный клиентский расход для игры, шлющей событие в каждом кадре, — очередь (≈7 мс/событие на телефоне), её стоит оптимизировать независимо от V7.
4. GameAnalytics и Amplitude на телефоне занимают +100–130 МБ ОЗУ — для устройств с малым объёмом памяти это существенно, а V7/V1 и HyperKit — единицы мегабайт.
