# Глубокий анализ этапов SDK: что, чем и как мерим (подготовлено, не запускалось)

Цель: понять, **где и почему** SDK тратит время (wall и CPU потока), память (управляемая, Java, нативная), задержки и трафик на каждом этапе, а потом решать, что оптимизировать. Начинаем с вопроса «нужна ли оптимизация редких событий (одно в секунду)», потому что это единственный режим, где цена на событие не маленькая (≈3 мс CPU и ≈22 КБ Java-аллокаций на событие при 5 событиях/с против ≈0.1 мс и 5 КБ в пачке).

## 1. Карта этапов (что именно таймится)

Таймеры — `AnalyticsProf` (`Runtime/Internal/AnalyticsProf.cs`), существуют только в сборке с `DALIYS_ANALYTICS_PROFILE`; в обычной сборке вызовы пустые и вычищаются, ничего не стоят. На каждый этап: число вызовов, wall, CPU потока (`CLOCK_THREAD_CPUTIME_ID`), рост управляемой кучи, максимум, p50/p99 по выборке из 4096 вызовов; плюс трасса первых 16 384 событий этапов (поток, начало, длительность) и счётчики. Этапы вложены, их времена перекрываются: читать как дерево.

| Группа | Этапы | Поток | Вопрос, на который отвечает |
|---|---|---|---|
| Запуск | `init.total` ⊃ `init.runtime` ⊃ `init.limiter`, `init.worker` (⊃ `init.device_context`, `init.event_context`, `init.uploader` ⊃ `init.http_client`, `init.v8_session`/`init.v7_session`, `init.timers`), `init.session_tracker`, `init.session_start`, `init.lifecycle` | главный | из чего 180 мс на `Initialize` |
| Первое использование | `bridge.create` (открытие SQLite-очереди), `session.recover`, `counters.load`, `v8.hello`, `v8.catalog`, `v8.dictionary` | воркер / вызывающий | что платится один раз, и кто его платит |
| `Track()` | `track.total` ⊃ `track.validate`, `track.limiter`, `track.encode`, `track.buffer`, `track.pressure_flush`; `batch.encode`, `batch.write` | вызывающий / пул | цена события для игры, давление при всплеске, `TrackBatchAsync` |
| Проход воркера | `worker.pass` ⊃ `worker.idle_check`, `worker.attach`, `worker.write_buffer` (⊃ `worker.buffer_drain`, `jni.enqueue`), `worker.save_session`, `worker.evicted_read`, `worker.upload`, `worker.detach`, `worker.complete` | воркер | фиксированная цена одной записи в очередь, пустые проходы |
| JNI-вызовы | `jni.enqueue`, `jni.get_state`, `jni.read_oldest`, `jni.delete`, `jni.sequence_state`, `jni.meta`, `jni.session`, `jni.other` | воркер | сколько стоит мост сам по себе |
| Выгрузка | `upload.flush` ⊃ `upload.policy`, `upload.pause`, `v8.send` ⊃ `v8.build_encoder`, `v8.encode`, `v8.http`, `v8.interpret`, `v8.persist`, `v8.policy`; `v7.*`, `v1.*` | воркер | кодирование против сети, запись метаданных после каждого пакета |
| Выход из игры | `pause.total`, `pause.persist_now` | главный | лаг при сворачивании |
| Java-очередь | `enq.total` ⊃ `enq.insert_loop` (⊃ `enq.insert_exec`), `enq.meta_sequence`, `enq.expire`, `enq.bounds`, `enq.counters`, `enq.commit`; `read.total` ⊃ `read.query`; `delete.total`, `state`, `sequence_state`, `meta_get`, `meta_set`, `session_save`, `session_load` (wall; CPU и ART-аллокации — на итогах `enq.total`, `read.total`) | воркер (Java) | коммит SQLite против копирования и аллокаций |

Остальное в том же прогоне: CPU по потокам процесса (`/proc/self/task`), CPU всех процессов, PSS/Java/native, число и длительность GC (Mono и ART), кадры (p99, провалы), байты и соединения на проводе (`collector2`), сырые TLS-байты (`tlsmeter`).

## 2. Как это измеряем (два варианта сборки)

* **Профильная сборка** (`PROFILE=1 ./build.sh cmp-prof-arm64.apk`): release, IL2CPP, таймеры включены. Для времени (wall, CPU потока), трассы, JNI/Java, трафика, TLS. Накладные расходы самих таймеров: два вызова `clock_gettime` и `GC.GetTotalMemory` на границу этапа, порядка единиц микросекунд; поэтому сравнивать надо с обычной сборкой, на нескольких этапах (`hz1`, `frame20`) проверим добавку.
* **Development-сборка** (`PROFILE=1 DEV=1 ./build.sh cmp-prof-dev-arm64.apk`): только для аллокаций — счётчики Unity «GC Allocated In Frame» в release не работают, а `GC.GetAllocatedBytesForCurrentThread` под IL2CPP возвращает 0. CPU в ней не использовать.
* **Хост (.NET)** — точные управляемые аллокации по стадиям: `M8_CORPUS_DIR=comparison-run~/data dotnet test --filter V8StageAllocation --logger "console;verbosity=detailed"`.
* Java-аллокации: `art.gc.bytes-allocated` вокруг итогов `enq.total` и `read.total` (общий по процессу, но воркер на низкой частоте почти один).

Уже полученные точные хостовые числа (управляемая часть V8, 3000 событий, `V8StageAllocation`): запись события (тело `Track`) **0 байт** и 0.75–2.7 мкс на событие; валидатор 0 байт; кодирование V8 пачкой 200: casual 126 Б / 1.8 мкс, telemetry 305 Б / 2.3 мкс, Puzzle 1166 Б / 9.1 мкс, midcore **2086 Б / 30.6 мкс** (959 форм события: поиск формы линеен по числу вариантов имени — довод в пользу маски присутствия). «Буфер + слив» в тесте раздут ростом массива за 3000 событий; в работе слив идёт каждые 200 мс.

## 3. Сценарии (`tools/matrix_profile.py SERIAL SET STACK [группы] [повторы]`)

| Группа | Что | Зачем |
|---|---|---|
| `init` | холодный старт, 0 событий, 90 с хвоста; V8, V7, V1, `none`, `noop`; 5 повторов | разложить 180 мс; первое обращение к очереди, hello/каталог/словарь; фон (таймеры, heartbeat) |
| `rate` | 0.2 / 1 / 5 / 30 событий/с, 1 и 20 на кадр; V8, V7, V1; таймеры по умолчанию | **главный вопрос**: стоимость события в зависимости от частоты, разложенная по стадиям |
| `profile` | Realtime / Standard / TrafficSaver при 1 и 5 событиях/с, по 10 минут | запросы, соединения, трафик и пробуждения за час |
| `batch` | `TrackBatchAsync` 100 / 500 / 5000 / 20 000 | длина кадра, мусор, время до записи на диск |
| `burst` | `Track()` в одном кадре 500 / 1500 / 5000 / 20 000 | путь «буфер полон» (давление), число сбросов, лаг |
| `backlog` | оффлайн-накопление 2k / 10k / 50k, затем разгребание; пакет 200/500, адаптивный размер, пауза | скорость разгребания, `v8.*`, `upload.pause`, трафик |
| `tls` | HTTPS через `tlsmeter` при 1 и 5 событиях/с | сырые TLS-байты на соединение, возобновление сессии, число соединений на выгрузку |
| `dev` | Development-сборка: 1/с, 5/с, 20 на кадр, V8 и V1 | распределение управляемых аллокаций |

Анализ: `python3 tools/analyze_profile.py SET > results/SET/PROFILE_TABLES.md` (на событие: вызовы, wall, CPU, рост кучи; Java-этапы; счётчики; потоки; таймлайн первого запуска).

## 4. Гипотезы, которые должны подтвердиться или нет

1. **Редкие события.** Фиксированная цена прохода воркера (подключение к JVM, транзакция SQLite, сохранение состояния сессии) делится на 1 событие; при 5 событиях/с это ≈3 мс. Проверка: доля `worker.attach`+`worker.detach`+`jni.enqueue`+`enq.commit` от `worker.pass`; зависимость от частоты (0.2 → 60/с). Если цена почти вся в атташе и коммите — окно записи по частоте и постоянно прикреплённый поток; если в Java-аллокациях — их правка.
2. **22 КБ Java-аллокаций на событие** при низкой частоте: `enq.total` ART-байты на вызов против размера пачки (одна запись → копия записи, строка UUID, строка счётчиков JSON, объекты SQLite).
3. **Инициализация 180 мс**: ожидаем, что основной вклад дают `init.http_client` и/или `init.device_context`; `bridge.create` приходит позже, на воркере.
4. **Задержки `Track()`**: p99 на телефоне ≈0.9 мс при 5 событиях/с против 0.19 мс в пачке — подозрение на частоты процессора (DVFS) и блокировку `_sync` при сливе. Проверка: `track.buffer` p99 против `worker.buffer_drain`, цена `track.total` при загрузке ядра.
5. **Сеть на редких событиях**: при 1 событии/с и интервале 120 с — 30 запросов в час; доля TLS-рукопожатия в трафике (116 байт/событие с TLS против 27); сколько соединений на выгрузку и возобновляется ли TLS-сессия (`tlsmeter`: `resumed`, `handshake_in/out`).
6. **Оффлайн-накопление**: цена разгребания 10k событий по стадиям; влияет ли пауза между пакетами на кадры; даёт ли адаптивный размер выигрыш на плохой сети (матрица сетей — отдельный набор).
7. **Форм-взрыв**: `v8.encode` растёт с числом форм (959 форм: ≈2 КБ и 30 мкс на событие) — подтвердить на телефоне.

## 5. Что НЕ перемеряем из уже сделанного

Сравнение с конкурентами, сохранность полей, сбои (kill, плохая сеть, оффлайн 3–5 минут), нагрузка на сервер — результаты в `comparison-run~/REPORT.md`; в большом прогоне повторяем только матрицу CPU/байт на новой сборке, чтобы увидеть влияние изменений.

## 6. Что нужно перед запуском

* Телефон Nothing A142 по USB, Wi-Fi включён, экран не гаснет (`svc power stayon true`), эмуляторы (2) для сетевых наборов.
* `PROFILE=1 ./build.sh cmp-prof-arm64.apk` и `PROFILE=1 DEV=1 ./build.sh cmp-prof-dev-arm64.apk` (~4 мин каждая).
* Стек сервера (`tools/stack_start.sh cpu 54411 18111 seed-v7`, прогреть V8 словарь, как в `STATE.md`), лимиты приёма поднять переменными окружения для нагрузочных наборов.
* Миграция сервера 0035 **не нужна** для замеров (сервер работает без неё).
