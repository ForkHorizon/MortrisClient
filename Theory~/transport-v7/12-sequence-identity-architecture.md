# Архитектурное решение: Замена случайных Event UUID на монотонные Sequence Numbers

**Статус:** Утверждённое архитектурное решение (ADR) для перехода от V1 к V7/V8.  
**Контекст:** Решение проблемы несжимаемого оверхеда случайных GUID (16 байт на каждое событие) в пользу сверхкомпактного монотонного счётчика.

> **Уточнение 19 октября 2026 (по аудиту, H4): что реализовано на самом деле.** Текст ниже — исходное
> решение; в реализации V7 он изменён в трёх местах, ориентируйтесь на этот блок и `Documentation/V7Transport.md`.
>
> 1. **Ключ события** — `(project, install, epoch, sequence)`, а не `(install_id, sequence)`. `epoch` растёт при откате
>    счётчика (переустановка, restore), иначе новые события с теми же номерами были бы приняты за дубликаты.
> 2. **Производный id считает и клиент.** Формула: SHA-1 от фиксированного namespace и строки ключа, с
>    принудительной версией 4 (валидаторы принимают только v4-подобные UUID), а не UUIDv5. Клиент вычисляет id
>    (`V7Identity`) и подставляет его в строки V1, пока открыт поток V7, поэтому одно событие не сохранится дважды
>    при смене транспорта. Сервер вычисляет тот же id при приёме пакета V7.
> 3. **Стоимость на проводе не «1–2 байта на пачку».** Номера строго подряд занимают в колонке немного, но
>    заголовок M7 (alias epoch, id каталога, id словаря, счётчики) и режим кодирования добавляют переменное число
>    байт (varint), так что оценку «1–2 байта» нужно читать как «порядка единиц байт на пачку», а не как гарантию.

---

## 1. Проблема: Почему случайные UUID больше не используются на клиенте

В текущем продакшене (V1) каждое событие создаёт случайный 36-значный UUID:
```csharp
event_id = Guid.NewGuid().ToString("D"); // 36 символов UTF-8 или 16 байт бинарного шума
```
* **Математическая проблема:** Случайный UUID — это чистая энтропия. Ни zstd, ни gzip, ни LZ4 не могут сжать случайные байты.
* **Сетевой оверхед:** На каждые 100 событий в пакете мы тратим **1600 байт** только на передачу идентификаторов событий.
* **Скрытый дефект:** Случайные UUID не позволяют серверу обнаружить пропажу событий при сетевом сбое (если выпало событие №42, сервер не знает о его существовании).

---

## 2. Новая архитектура: Монотонный Sequence ID (1, 2, 3...)

События никогда не генерируются в отрыве от устройства. У каждого клиента есть подтверждённый `install_id` (или `origin_id`).

Поэтому глобальным уникальным идентификатором события во вселенной является составной ключ:
$$\text{GlobalEventKey} = (\text{project\_id}, \text{install\_id}, \text{sequence\_number})$$

### Как это работает на клиенте:
1. **Генерация на телефоне:**
   * При возникновении события клиент не создаёт UUID.
   * Локальная база SQLite на телефоне присваивает событию инкрементный целочисленный номер `sequence_number` (1, 2, 3, 4...).
   * Номер сохраняется на диск в SQLite до помещения в сетевую очередь (Crash-Safe).
2. **Передача по сети (Wire Format):**
   * В пачке из 100 событий номера идут строго подряд: `101, 102, 103, 104 ... 200`.
   * В колоночном упаковщике V7/V8 дельта между соседними номерами всегда равна $+1$.
   * После дельта-кодирования массив превращается в `[база: 101, шаг: 1, длина: 100]`.
   * **Размер на проводе:** Вместо 1600 байт на 100 событий мы тратим **всего 1–2 байта на всю пачку!**

## 3. Обработка на сервере и обратная совместимость с дашбордами

Если существующая инфраструктура (ClickHouse, BigQuery, BI-дашборды) жёстко завязана на колонку `event_id` в формате UUID:

* **Решение:** Сервер генерирует детерминированный UUID при приёме пакета (на этапе Ingestion):
  ```go
  // Сервер генерирует тот же самый UUID без передачи его по воздуху:
  eventUUID := uuid.NewV5(MortrisNamespace, fmt.Sprintf("%s:%d", installID, sequenceNumber))
  ```
* Телефон **не платит** мобильным интернетом и батарейкой за генерацию и передачу случайных строк. Сервер делает это мгновенно в оперативной памяти.

## 4. Защита от сбоев и граничные случаи (Edge Cases)

Следующий агент при реализации в C# SDK и Go Backend обязан учесть три критических правила:

### Правило 1: Надежность сохранения при крэшах (Crash Resilience)
* Счётчик `sequence_number` должен вестись локальным хранилищем SDK (SQLite с включённым WAL-режимом).
* Нельзя хранить счётчик только в оперативной памяти или полагаться на отложенный `PlayerPrefs.Save()`.
* При внезапной перезагрузке телефона или падении игры следующее событие гарантированно получает номер `N + 1`, без повторения старых номеров.

### Правило 2: Переустановка игры или сброс личности (ResetIdentity)
* Если игрок переустановил игру или вызван `Analytics.ResetIdentity()`:
  * Счётчик может начаться снова с `1`.
  * **Обязательное условие:** Сервер обязан выдать клиенту новый `install_id` или инкрементировать `install_epoch`.
  * Для базы данных `(install_1, seq_1)` и `(install_2, seq_1)` — это абсолютно разные неконфликтующие записи.

### Правило 3: Детекция потерь (Loss / Gap Detection)
* Сервер проверяет последовательность `sequence_number` для каждого `install_id`:
  * Если пришли события `[101, 102, 104]`, сервер фиксирует пропуск (gap) события `103`.
  * Сервер отправляет в ACK статус: `ACK 102` (подтверждены только непрерывные), заставляя клиент повторить отправку `103`.

## 5. Итог для команды реализации

1. В Unity C# SDK: Полностью убрать генерацию случайных `event_id` GUID в методе `Track()`. Использовать `long sequence_number` из локальной SQLite таблицы.
2. В сетевом пакете M7/M8: Флаг `preserve_original_event_uuid` выставлять в `0`. Передавать только колонку `sequence`.
3. На Go сервере: Настроить генерацию детерминированного `event_id = UUIDv5(install_id, seq)` для легаси-потребителей, пока БД не переведена на первичный ключ `(install_id, sequence_number)`.
