# Задача: независимый аудит, тестирование и глубокий анализ V7 (клиент + сервер)

Ты — независимый инженер-аудитор. Твоя цель — **найти реальные дефекты, пробелы и
необоснованные утверждения** в реализации транспорта V7 (клиент Unity/Android и
сервер Go), а не подтвердить, что всё хорошо. Работа долгая и глубокая: не
останавливайся на первом прохождении тестов. Приоритет — корректность данных
(потеря, дубликаты, пропуски, подмена), безопасность, отказоустойчивость, затем
производительность и поддерживаемость.

Ты НЕ чинишь код по умолчанию. Ты находишь, воспроизводишь, классифицируешь и
описываешь. Исправлять можно только если пользователь явно попросит; тогда —
отдельным коммитом в отдельной ветке от проверяемой.

## 2. Что такое V7 (минимум контекста)

- **Каталог проекта** (формы событий), **per-process alias-таблицы**, колоночное
  кодирование, **zstd 1.5.7 со словарём проекта**, кадр M7: `M7`, flags, mode,
  catalog id, alias epoch, dict id, count, raw size, body, CRC32.
- **Идентичность события** = (project, install, epoch, sequence). Сервер хранит
  событие под производным UUID: SHA-1 от фиксированного namespace
  `4afdc7a7-de1e-45d3-a74f-d6061efed25e`, версия-ниббл принудительно 4 (валидаторы
  принимают только v4-подобные id). Пока поток V7 открыт, строки V1 тоже
  отправляются с производными id — так одно событие не может сохраниться
  дважды по разным транспортам.
- **Поток**: подтверждение `ack_through`, диапазоны `received` / `dropped`,
  `missing`, эпохи, обнаружение отката (`409 stream_rollback`), alias epoch,
  откат на V1.
- Эндпоинты: `POST /v2/streams/sync`, `PUT /v2/streams/aliases`,
  `POST /v2/events/packet`, `GET /v2/assets/{kind}/{id}`.
- Сервер: Go 1.26, PostgreSQL, `CGO_ENABLED=0` → декодер на чистом Go
  (`klauspost/compress` v1.18.0).
- Клиент: C# 9, без `unsafe`; нативный `libdaliys_zstd` (arm64-v8a, armeabi-v7a,
  universal macOS dylib; сборка `Native~/zstd/build.sh` из закреплённого
  tarball с проверкой SHA-256); очередь — Java SQLite в AAR через JNI.

## 4. Фазы работы

### Фаза A — Базовая проверка воспроизводимости (чтобы знать, на чём стоишь)
1. Зафиксируй хэши коммитов обеих веток и `git status`.
2. Запусти и сохрани вывод **каждого** набора, без пропуска:
   - Сервер: `gofmt -l .`, `go vet ./...`, `go build ./...`, полный
     `go test ./cmd/... ./internal/... ./contracts/...` против PostgreSQL
     (поднимай throwaway-инстанс: `LANG=en_US.UTF-8`, `unix_socket_directories=`
     пустой из-за длины пути сокета, создай нужные роли), затем отдельно
     `go test -race` для `internal/transportv7` и V7-тестов `internal/httpapi`.
   - Известный **ранее существовавший** флейк: `TestUnchangedReferenceIsNotUploadedAgain`
     и `TestChangedReferenceTableCreatesANewSnapshot` в `internal/exporter` падают
     в параллельном прогоне. Проверь сам, что это воспроизводится на `origin/main`
     без изменений V7 (worktree от `origin/main`), и что они проходят изолированно.
   - Клиент: `dotnet test` в `Native~/transport-tests` (нужен `M7_PYTHON`),
     `e2e/run-e2e.sh`, Unity EditMode (batchmode), Java unit + instrumentation,
     проверка, что AAR побайтно совпадает со сборкой.
3. Повтори каждый набор минимум 3 раза и отметь любую нестабильность.
4. Проверь, что нативные библиотеки соответствуют `SHA256SUMS` / пересобираются
   детерминированно (или честно зафиксируй, что нет).

### Фаза B — Глубокий аудит корректности протокола и идентичности
Для каждого пункта: найди код, построй гипотезу отказа, напиши воспроизводящий
тест (в своём каталоге, не в продуктовых тестах), зафиксируй результат.

1. **Идентичность**: `DerivedEventID` на клиенте и сервере побайтно идентичны
   (версия-ниббл 4, variant bits, порядок байтов, endian). Проверь на границах:
   `sequence=0`, `2^31`, `2^32`, `2^53`, `2^63-1`, отрицательные/переполнение,
   эпоха > 0, пустой/длинный install id, регистр UUID. Совпадают ли векторы между
   Python, C# и Go?
2. **Диапазоны**: алгебра `Ranges.Add/Missing/AckThrough` — перекрытия, смежные,
   вложенные, неупорядоченные, огромные значения, переполнение `uint64`,
   лимит `maxStreamRanges=4096`. Property/fuzz-тесты по сравнению с наивной
   моделью (множество целых).
3. **Гонки и повторы**: два одновременных идентичных пакета; частично
   пересекающиеся пакеты; повторная отправка после потерянного ack; пакет с
   sequence ниже `stream_base`; пакет из будущей эпохи; откат счётчика на
   клиенте (переустановка/restore backup); два процесса одного install.
4. **Смешанные транспорты**: V7 открыт → V1 отправляет производные id; V1 resend
   того, что уже записал V7 → дубликат, а не копия; V7 после V1; V1-строки,
   записанные до открытия потока (старые случайные id) — как ведёт себя система?
   Есть ли путь, где одно событие сохраняется дважды или теряется?
5. **Журнал dropped** на клиенте: eviction, expiry, clear, `deleteAcknowledged`
   при epoch > 0 и epoch = 0; миграция схемы v2→v3 с данными; падение процесса
   между удалением строки и записью журнала (атомарность в одной транзакции?).
6. **Alias-протокол**: рассинхрон alias epoch, пакет с неизвестным alias,
   параллельный `PutAliases`, переполнение таблицы, перезапуск процесса,
   смена версии каталога посреди потока.
7. **Ассеты**: загрузка с неверным/подменённым content id, обрыв на середине,
   кэш на диске повреждён, смена словаря, `no catalog` fallback на V1.
8. **Коды ошибок**: каждый путь `V7Session` для 401/403/404/409/413/429/5xx и
   сетевых ошибок — ведёт ли к корректному состоянию (retry/backoff/fallback/
   disable) и не к бесконечному циклу? Проверь no-progress guard.
9. **Декодер**: полнота валидации: несоответствие `count`/`raw size`, CRC,
   zstd-бомбы (окно, коэффициент), усечённые/переупорядоченные колонки,
   неизвестные flags/mode, строгие правила каталога, ограничения 256 KiB /
   100 событий / 2 MiB. Какие входы приводят к панике, OOM или долгому CPU?
10. **Клиентский кодек против референса**: расхождения классификации типов
    (`_vtype` в Python vs `M7Event`), числа (int/float/большие/NaN/Infinity/
    -0/экспоненты/лексемы), строки (суррогаты, невалидный UTF-8, нулевой байт,
    очень длинные), булевы/null/вложенные объекты/массивы, пустые свойства,
    дубли ключей, порядок ключей. Прогон дифференциального fuzz: случайные
    события → C# encoder → Go decoder и Python decoder → сравнение с исходным
    JSON (с учётом документированных нормализаций).
11. **Хранение**: что именно попадает в таблицу `events` — совпадает ли с V1 для
    тех же событий (поля, типы, время, clock quality, session), не ломает ли
    дашборды/экспорт; миграция `0033` (идемпотентность, откат, FK cascade,
    права), purge проекта, retention-sweep.

### Фаза C — Безопасность
- Аутентификация и изоляция проектов/установок на каждом `/v2` эндпоинте:
  доступ к чужому потоку/ассету/aliases, подмена project/install в теле.
- Rate limiting и защита от истощения ресурсов (кэш ассетов, число потоков,
  число диапазонов, размер alias-таблицы, декомпрессия).
- Инъекции в SQL/логи через имена событий и свойства; утечки данных в логах и
  ошибках; тайминги.
- Целостность нативной сборки (supply chain): закреплённый tarball + SHA-256,
  лицензии (`LICENSE-zstd.txt`), `go.sum`, лицензия `klauspost/compress`.
- Разрешение plain HTTP только для localhost/127.0.0.1/10.0.2.2 — нет ли обхода
  (например `localhost.evil.com`, userinfo в URL, IPv6, редиректы).

### Фаза D — Клиентская надёжность и жизненный цикл
- Потокобезопасность `V7Session`/`AnalyticsUploader`: вызовы из разных потоков,
  отмена, повторный вход, остановка во время отправки.
- Жизненный цикл Android: kill процесса, no network, смена сети, low storage,
  стресс очереди (очень много событий, очень большие события), поведение при
  отсутствии нативной библиотеки (должен тихо уйти на V1).
- Память/GC: аллокации на пакет в горячем пути (`M7Columns`, `MiniJson`) —
  оценить статически и замерить на эмуляторе (**пометить как EMULATOR**, не
  как телефон).
- Платформы: iOS / WebGL / Standalone — что происходит при включённом V7 там,
  где нет нативной библиотеки? Нет ли ошибок компиляции/линковки?
- IL2CPP stripping: не вырезаются ли нужные типы/рефлексия; `link.xml`.

## 5. Методика

- Для каждой найденной проблемы — **минимальный воспроизводящий пример** (тест,
  скрипт или точная последовательность запросов) и точные команды запуска.
- Различай: `CONFIRMED` (воспроизведено), `PLAUSIBLE` (по коду, не
  воспроизведено — укажи, чего не хватило), `REFUTED` (проверено и не
  подтвердилось). Не поднимай PLAUSIBLE до CONFIRMED без запуска.
- Различай измерение и оценку: `MEASURED` / `EMULATOR` / `MODELED` /
  `NOT_MEASURED`. Данных с физического телефона нет — не выдумывай.
- Используй дифференциальные и property-based тесты там, где пространство входов
  большое (диапазоны, кодек, декодер).
- Для нестабильных результатов — не менее 10 повторов с фиксацией частоты.
- Если упёрся в ограничение окружения — запиши это в «Не удалось проверить»,
  а не обходи молча.
- Если нашёл критическую проблему целостности данных — сообщи сразу, не жди
  конца работы.

Сортируй находки по серьёзности. Отдельно перечисли: (а) что подтверждено как
работающее с доказательством, (б) известные пробелы, которые уже документированы
(не дублируй их как новые находки, но оцени полноту описания), (в) расхождения
между документацией и кодом.
