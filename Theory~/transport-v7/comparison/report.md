# Независимая проверка Transport V7 — отчёт

17 октября 2026. Это внутренняя проверка, не сертификация и не внешний аудит.
Методика зафиксирована в [protocol.md](protocol.md) до измерений; пробелы — в [inventory.md](inventory.md).

## Итог в одном абзаце

**Доказано (на одном дне Puzzle, на хосте):** размеры V7 17,425535 / 9,057567 Б/событие и
V1 JSON+gzip1 122,5695 Б/событие воспроизведены байт-в-байт из чистой копии скриптов
(реальные C# packets, 653 пакета + 200 событий V1-fallback). **Измерено дополнительно (эмулятор, локальный HTTP):** реальные Android-SDK Amplitude 2.40.1 и GameAnalytics 7.2.0 — тела запросов на тех же 600 событиях (раздел 8).
**Не доказано:** сравнение с Firebase и HyperKit (найдены в Puzzle, runtime не запускался; только модельные оценки в code-size-estimates.md), TLS/DNS-экономия, CPU/FPS/батарея на телефоне, независимое подтверждение на другом дне. Sequence identity из ADR 12
в SDK **не реализована**; harness выявил пять мест, где ADR неточен (раздел 5).

## 1. Воспроизведение (MEASURED/REPRODUCED)

Окружение: Apple M5, macOS 27.0.1, Python 3.14.8, .NET 10.0.201, zstandard 0.25.0, commit `688da5d`
(+ незакоммиченные `Theory~/transport-v3..v7`). Dump SHA256 `abf84a30…8e6e68ec` совпал.

Holdout: 63 943 события, 124 установки (не независимое подтверждение — выборка использовалась при выборе моделей).
Тела V1 **восстановлены** из DB jsonb, не оригинальные HTTP-запросы.

Ablations (те же данные, один слой за раз):
- Игровая очистка: V1 122,57 → 102,70 (−16,2 %); V7 dict32 19,11 → 10,61 (−44,5 %). **Очистка доступна и V1**; выигрыш V1→V7 нельзя целиком приписывать кодеку.
- Identity: V7 dict16 с UUID 36,07 против 19,45 при sequence → **16,6 Б/соб.** (46 % остатка) даёт отказ от случайного event UUID — это изменение протокола/сервера, не кодека.
- Кодек при UUID: V1 122,57 → V7 36,07 (−70,6 %) — честное сравнение «с теми же идентификаторами».
- Каталог/колонки/словарь по отдельности: V6 zstd1 22,88 → V7 без словаря 23,37 (колонки/каталог сами не выигрывают у V6), словарь даёт −3,9 Б (dict16) / −4,3 Б (dict32). Числовые/строковые модели: 19,11 → 17,43.

Итого V1 as-is → V7 кандидат: ×7,03 (−85,8 %) на raw; V1 as-is → V7 clean: ×13,5 (−92,6 %), но это сумма очистки, identity и кодека. При равной очистке (V1 clean 102,70 → V7 clean 9,06) ×11,3, всё ещё включая identity.

Все 653 нативных пакета на каждый вариант декодируются независимым Python-декодером; host managed GC в упаковке = 0 байт (калибровка из отчёта 09).

### Cold start / setup (MODELED — доставка каталога/словаря не реализована)

Assets ≈ каталог 10 395 Б + dict32 32 768 Б + alias setup 34 679 Б / 124 установки (≈280 Б). Если новый
install качает assets без сжатия: ≈43,4 КБ, окупается за **≈413 событий** (raw, экономия 105,1 Б/соб.) и **≈454** (clean, 93,6 Б/соб.).

## 3. Конкуренты — что установлено и что нет

**Обновление:** Amplitude и GameAnalytics затем были запущены (раздел 8). Firebase и HyperKit — по-прежнему NOT_MEASURED. Документально
(inventory.md): Amplitude HTTP API — JSON `{api_key, events[]}`, `insert_id` для дедупа, сжатие не документировано;

выходит за лимит 100 символов — **fidelity/capabilities report** обязателен при реальном сравнении. HyperKit публично недоступен, но его исходники найдены в соседнем проекте Puzzle (см. inventory.md и code-size-estimates.md).

## 4. CPU / GC / телефон

Новых замеров нет. Сохранённые результаты (отчёты 06, 09): Unity Editor и Android ARM64 Development IL2CPP **на эмуляторах**
(4/16 КБ), среднее упаковки 100–500 событий ≈0,12–0,20 мс, калиброванный GC.Alloc = 0 (положительный контроль 4096 Б дал 1 событие;
поле `allocation_counter_control_bytes` в JSON названо неоднозначно — полагаться на текст отчёта 06). Это pretyped-стадия «колонки+zstd»:
без ingress/boxing/validation, JNI, очереди, HTTP; без p95/p99, температуры, FPS. **Физический телефон: NOT_MEASURED.**
Фраза «0 микрофризов — гарантия» не используется.

## 5. Надёжность sequence identity (harness, не SDK)

`scripts/identity_harness.py`: SQLite WAL, `synchronous=FULL`, выделение seq и enqueue в одной `BEGIN IMMEDIATE`; сервер-модель с ключом
(project, origin, epoch, seq). Результаты `results/identity-harness.json`.

| Проверка | Результат |
|---|---|
| SIGKILL после commit / внутри открытой транзакции (по 50 событий) | 50 строк, без дыр и дублей, counter = max+1; рестарт продолжает с 51 |
| 4 процесса × 200 событий в одну БД | 800 уникальных, подряд |
| ResetIdentity при непустой очереди, сервер недоступен | работает локально; старые строки сохраняют origin; один и тот же seq=1 у разных origin не конфликтует |
| Переполнение int64 | эпоха сменяется, без wrap (**нашёл баг в моём первом прогоне**: хранение next=2^63 не помещалось в INTEGER) |
| Повтор / тот же ключ с другим содержимым | NEW / DUP_SAME / CONFLICT |
| Восстановление старого backup | ключ (epoch 0, seq 4) повторно выдан с другим payload — обнаруживается **только сервером**; нужен handshake с серверным high-water и смена epoch |

Уточнения к ADR 12 (проверено в harness):
1. Формула `uuid5(installID:seq)` не содержит project и epoch → коллизии между проектами/эпохами; UUID оставить как legacy-alias, первичный ключ — кортеж.
2. «1–2 Б на пачку»: base/step/count по varint = 3 Б (base 101), 5 (20 000), 6 (3·10⁶), 8 (2⁴⁰).
3. ACK «непрерывный» зависает на локально удалённом событии без skip-диапазонов (с skip 103: 102 → 104).
4. Потеря хвоста (98–100) сервером не видна без отправленного клиентом high-water.
5. При eviction/фильтрации seq не подряд — дельта ≠ +1.

Не проверено: потеря питания, fsync-lies, Android/Unity-реализация, backup-restore на устройстве, Puzzle durable interaction index,
восстановление truncated/mismatched hash (игровые преобразования отдельны от SDK).

## 8. Реальные SDK Amplitude и GameAnalytics (Этап 3, частично)

**Метод.** Открытые Unity-пакеты (`amplitude/unity-plugin` @ `599146150d11`, `GameAnalytics/GA-SDK-UNITY` @ `7f661deab09d`) — тонкие обёртки над нативными
Android-библиотеками; запускались сами эти библиотеки (Amplitude `com.amplitude.android-sdk` 2.40.1 + OkHttp 4.2.2; GameAnalytics `gameanalytics.aar`, sdk_version `android 7.2.0`)
в минимальном Java-приложении (`harness/android`), по одному SDK на процесс (`pm clear` перед каждым запуском). Единственное изменение — адрес сервера:
`setServerUrl` (Amplitude), `setBaseUrl` + reflection на `remoteConfigsBaseUrl` (GameAnalytics); фиктивные ключи, фиктивный user id. Локальный коллектор
(`harness/collector.py`) считает байты на сокете (заголовки + тело запроса + ответ), cleartext HTTP. Эмуляторы Android 15 ARM64 (6 штук параллельно, DNS закрыт), 10 событий/с,
600 событий (2 установки × 300), 45 с ожидания после replay, пачки/интервалы — **настройки SDK по умолчанию**; для Amplitude дополнительно режим «пачка 100» (threshold=100,
max batch=100). 5 повторов каждой ячейки, порядок — перемешанные блоки (seed 20261017). Данные: публичный синтетический replay (low/high entropy), не Puzzle.
Это измененный транспорт адреса, а не немодифицированный продакшн-путь: тайминги не равны реальному SDK.

**Доставка:** во всех 30 прогонах коллектор принял 600/600 целевых событий (`observed_target_events`); ни дропа, ни сэмплирования. Сервер всегда отвечал 200 — ретраи/ошибки не проверялись.

Тело, Б/событие. Mortris-события включают session_id, session_elapsed_ms, ts и поля устройства; метаданные SDK конкурентов — стоимость их протокола, не удалялись.
V7 — Python reference encoder, заданный dict32/каталог обучены на отдельных синтетических seed (не на replay); C# parity на этом наборе не проверялась.

**Что это значит (на этой нагрузке, эмулятор, localhost):**
- V7 тело меньше GameAnalytics в ≈10 раз (low) и ≈1,9 раза (high); V1 хуже GameAnalytics (43,5 против 59,9 на low, 135,9 против 162,3 на high) — GameAnalytics оказался компактнее нынешнего V1.
- Amplitude Android 2.40.1 примерно в 15–250 раз тяжелее по телу (нет сжатия).
- **Холодный старт проигрывает:** каталог+словарь+alias ≈35 КБ на установку (расчёт, доставка не реализована). Для одной сессии из 600 событий это +58 Б/соб.: V7 cold ≈62 Б/соб. (low) — хуже GameAnalytics (43,5) и V1 (59,9); на high ≈131 против 135,9 — почти ничья. Окупаемость setup против GameAnalytics ≈880 событий (low) / ≈560 (high), против V1 ≈620 / ≈390, против Amplitude ≈30. Если assets вшиты в сборку или кэшируются между сессиями — setup не платится.
- Это только тело запроса. Накладные HTTP-заголовки (≈360 Б на запрос; у V7 запросов при пачке 100 было бы 6) и TLS не учтены для V7/V1 (в колонках SDK они учтены только в последней колонке таблицы выше).

**Ограничения:** эмуляторы; cleartext HTTP; Android-библиотеки без Unity-обёртки (она добавляет C#→JNI вызов, не меняя тело); версия Amplitude 2.40.1 — та, что вшита в Unity-плагин, более новые Amplitude SDK могут сжимать иначе;
GA-интервалы ≈8 с и порог Amplitude 30 событий — дефолты этих версий; Mortris-пачки подобраны (10/100) и не получены от реального SDK; доставка только до локального приёмника, TLS/DNS/ретраи не измерялись.
Время вызова `Track` на эмуляторе (среднее 26 мкс GA, 54–74 мкс Amplitude, Java main thread, 6 эмуляторов одновременно) — только индикатор, **не публиковать**: шумно из-за параллельного запуска и не относится к телефону.
Во время отладки один запрос `remote_configs/init` с фиктивным ключом ушёл на сервер GameAnalytics (ответ 401), потому что `setBaseUrl` не перенаправляет `remoteConfigsBaseUrl`; после этого адрес перенаправлен reflection-ом, а DNS эмуляторов закрыт, чтобы наружу ничего не уходило. В бинарнике SDK также найден захардкоженный URL `pipedream.net` (назначение не выяснялось, запросов к нему не делалось).

## 11. Оценки для Firebase и HyperKit там, где измерений нет

Это **оценки, не замеры** (`results/firebase-fidelity-estimate.json`, `code-size-estimates.md`).
- **Сохранность полей:** по данным Puzzle и документированным лимитам Firebase (значение ≤100 символов, ≤25 параметров, нет булевых параметров): строки >100 символов есть в ≈13,4 % событий большого holdout (18,8 % в replay из 600), >25 параметров — ≈0,1 %, булевы поля — ≈9,2 % (11,2 %); хотя бы одно из трёх — ≈20–25 %. Обрезка теряет данные, bool меняет тип. HyperKit по коду делает то же (обрезка >100, bool→строка).
- **Холодный старт:** у обоих нет словарей, поэтому оценка равна тёплому размеру; init-запросы Google и других каналов не учтены.
- **CPU/память:** порядок величин от стоимости C#→JNI на параметр и сборки JSON (Firebase ≈0,2–0,7 мс, ≈10–50 КБ; HyperKit с несколькими каналами ≈0,5–2 мс, ≈20–80 КБ); ориентиры — измеренные GameAnalytics (0,67 мс, 47 КБ) и Amplitude (2,6 мс, 83 КБ). Реальные значения могут лежать вне диапазона.
- **ID события:** у Firebase его задаёт SDK, приложение не контролирует; у HyperKit Gamestoty — 16 случайных символов (по коду).
