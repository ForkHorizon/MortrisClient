## 1. Вводная: история версий и текущая точка

В процессе эволюции транспорта аналитики было исследовано несколько поколений протоколов:
* **V1 (Продакшен сейчас):** Обычный JSON, пакуемый в gzip (уровень Fastest). Размер в проде: ~800–850 Б/событие. Высокие накладные расходы, мусор в Garbage Collector при сериализации строк.
* **V4 (zstd-19 + 64KB обученный словарь):** 16.62 Б/событие на корпусе `base`. Байтовое сжатие общего назначения упёрлось в потолок из-за отсутствия понимания типов полей.
* **V5 (MTB5 Range Coder + контекстная модель):** 13.19 Б/событие stateless. Выжал максимум математического сжатия, но оказался **опасен для мобилок**: побитовое арифметическое кодирование греет CPU (26–90 мс на пачку из 100 событий) и сажает батарею.
* **V6 (Схемно-колоночный бинарный упаковщик):** Радикально ускорил упаковку (до 3.5 мс, в 7–10 раз быстрее V5) и создал основу для Zero-GC в C#, но по чистому размеру уступил V5 (18.69 Б против 13.19 Б). Причина: колоночный буфер сжимался «голым» `zstd-1` без обученного словаря.

## 2. Разведка на живом проекте: находки в `Puzzle`

В отличие от версий V2–V6, которые тестировались на синтетических генераторах (`gen.py`), для V7 был исследован **реальный игровой проект**:

* **Ключевой файл аналитики игры:** `/Users/daliys/Daliys/UnityProjects/Puzzle/Assets/Scripts/DI/Services/Analytical/PuzzleAnalyticsService.cs`
* **Репозиторий нашего SDK:** `/Users/daliys/Daliys/UnityProjects/MortrisUnity/Assets/MortrisClient`
* **Текущий аплоадер SDK:** `/Users/daliys/Daliys/UnityProjects/MortrisUnity/Assets/MortrisClient/Runtime/Internal/AnalyticsUploader.cs`

### Находка №1: Раскрыта «загадка» `placed_state_hash` (55% веса в тестах V5/V6!)
В отчётах V5 и V6 исследователи безуспешно пытались сжать поле `placed_state_hash`, которое забирало **6.4 байта из 13–18 байт** (более половины всего размера события). Они считали его скрытым хешем игрового поля.

В реальном коде игры ([PuzzleAnalyticsService.cs, строки 400–407](file:///Users/daliys/Daliys/UnityProjects/Puzzle/Assets/Scripts/DI/Services/Analytical/PuzzleAnalyticsService.cs#L400-L407)):
```csharp
private static void AddPlacedState(Dictionary<string, object> properties, List<int> placed)
{
    var compactState = string.Join(",", placed); // Список ID блоков, например: "1,2,5,7"
    properties["placed_state_hash"] = Sha256(compactState); // Хеш от этой же строки!
    properties["placed_block_count"] = placed.Count;
    if (Encoding.UTF8.GetByteCount(compactState) <= 1024) 
        properties["placed_block_ids"] = compactState; // И САМА ЭТА СТРОКА!
    else 
        properties["placed_block_ids_truncated"] = true;
}
```
* **Факт:** Клиент шлёт **И** сам список блоков (`placed_block_ids` = `"1,2,5,7"`), **И** SHA-256 хеш от него же (`placed_state_hash` = 64 символа hex)!
* **Вывод для V7:** Это 100% избыточные данные. Сервер, зная `placed_block_ids`, может сам пересчитать этот SHA-256 за доли микросекунды в базе данных. Передавать 64-символьный хеш по сети не имеет никакого смысла.

### Находка №2: Дублирование и тяжеловесные GUID
В каждом игровом событии в методе `CommonContext()` ([PuzzleAnalyticsService.cs, строки 346–371](file:///Users/daliys/Daliys/UnityProjects/Puzzle/Assets/Scripts/DI/Services/Analytical/PuzzleAnalyticsService.cs#L346-L371)) передаются:
* `attempt_id`: `Guid.NewGuid().ToString("D")` (36 символов).
* `wave_attempt_id`: ровно то же самое значение `_attemptId` (36 символов — **полный дубликат**!).
* `house_run_id`: `Guid.NewGuid().ToString("D")` (36 символов).
* `interaction_id`: `Guid.NewGuid().ToString("D")` (36 символов).
* **Факт:** Каждое событие тащит ~150 байт чистого энтропийного шума (случайные UUID), который не сжимается архиваторами.
* **Вывод для V7:** Внутри сессии `interaction_id` избыточен, если уже передаётся порядковый номер `interaction_index` (1, 2, 3...). Связка `(attempt_id, interaction_index)` абсолютно уникальна на сервере.

### Находка №3: Координаты уже квантованы в игре
В [PuzzleAnalyticsService.cs, строки 380–390](file:///Users/daliys/Daliys/UnityProjects/Puzzle/Assets/Scripts/DI/Services/Analytical/PuzzleAnalyticsService.cs#L380-L390) координаты пальца уже переводятся в целые числа:
```csharp
properties["nearest_target_distance_milli"] = Quantize(nearestDistance);
properties["release_x_milli"] = Quantize(releasePosition.x); // Mathf.RoundToInt(x * 1000f)
properties["release_y_milli"] = Quantize(releasePosition.y);
```
Это означает, что для колоночной упаковки целых чисел не требуется эмулировать дроби — данные уже целочисленные!

## 3. Двухуровневая архитектура V7

Главное требование: **SDK `MortrisClient` создаётся для множества разных проектов (не только для Puzzle). В него нельзя вшивать специфику одной игры.**

Архитектура разделяется на два строгих слоя:

```
┌────────────────────────────────────────────────────────────────────────┐
│                   УРОВЕНЬ 2: Оптимизация на стороне Игры               │
│                     (Puzzle, будущие проекты Action/RPG)               │
│                                                                        │
│  - Исключение явных дублей (убираем duplicate wave_attempt_id)         │
│  - Удаление вычисляемых на сервере хешей (placed_state_hash)          │
│  - Использование локальных числовых счётчиков вместо случайных GUID   │
│  - Квантование игровых метрик                                          │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ Analytics.Track(name, properties)
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                   УРОВЕНЬ 1: Универсальный SDK (MortrisClient)         │
│                                                                        │
│  - Реестр бинарных схем по project_id (Build-time / Handshake)        │
│  - Сессионные алиасы устройств и пользователей (2 байта вместо UUID)   │
│  - Колоночный бинарный упаковщик (Zero GC в C#/Burst)                  │
│  - Компрессор с предварительно обученным словарём проекта (16–32 КБ)  │
│  - Надёжная доставка, локальная SQLite очередь, повторные попытки      │
└────────────────────────────────────────────────────────────────────────┘
```

## 4. Конкретные задачи и план действий для Исследователя V7

### Задача А: Верификация и аудит избыточности в `Puzzle`
1. **Проверить серверное использование `placed_state_hash`:**
   * Проверить в коде бэкенда/пайплайна аналитики: использует ли дашборд/BI поле `placed_state_hash` напрямую, или оно нужно только как уникальный маркер состояния?
   * Подтвердить, что сервер может сам вычислить `Sha256(placed_block_ids)` при вставке в базу данных.
2. **Проверить `wave_attempt_id`:**
   * Убедиться, что `wave_attempt_id == attempt_id` всегда истинно в `PuzzleAnalyticsService.cs`. Убрать дублирующее поле.
3. **Оценить выигрыш на реальных событиях:**
   * Собрать реальный дамп событий из `Puzzle` (1–2 сессии игры) и замерить размер JSON «как есть» vs «после очистки от дублей».

### Задача Б: Разработка универсального транспорта V7 в `MortrisClient`
1. **Схемы проектов (Project Schema Catalog):**
   * Для каждого `project_id` создаётся таблица соответствий:
     * `event_name` -> 1-байтовый enum (`0x01 = detail_taken`, `0x02 = placement_resolved`...).
     * `property_keys` -> битовая маска присутствия полей.
   * Никаких строк с именами полей в теле пакета.
2. **Колоночный упаковщик (из V6):**
   * Сохранить супер-быструю архитектуру V6: раскладка чисел, булевых флагов и строк по отдельным колонкам.
   * Обеспечить $O(n)$ сложность и 0 аллокаций в памяти (Zero GC в C#).
3. **Обучение словаря под проект (V6 + Columnar Dictionary):**
   * Взять бинарный колоночный вывод V6 и обучить компактный `zstd` словарь (16–32 КБ) на реальных/синтетических данных проекта.
   * Замерить сжатие: V6 без словаря давал 18.7 Б. С обученным словарём ожидается **11–13 Б** на грязных данных и **4–7 Б** на очищенных от лишних хешей данных!

### Задача В: Сравнительный бенчмарк и доказательная база
Провести сквозной замер на 4 сценариях:
1. **Текущий прод:** V1 JSON + Gzip fastest.
2. **V4 baseline:** zstd-19 со словарём на строках.
3. **V6:** Чистый схемно-колоночный бинарный поток.
4. **V7:** Универсальный схемно-колоночный кодек + словарь проекта + семантическая очистка дублей.

Метрики для подтверждения успеха:
* **Размер тела:** < 5–7 байт на событие (с очисткой) или < 11–12 байт (без очистки).
* **CPU на клиенте:** < 3–5 мс на пачку из 100 событий.
* **GC Allocations:** 0 байт аллокаций в C# куче при упаковке.
