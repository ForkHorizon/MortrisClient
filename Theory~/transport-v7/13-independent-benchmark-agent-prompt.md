# Задание агенту: независимая проверка Transport V7 и сравнение SDK

## Цель и критерий завершения

Построй воспроизводимое сравнение Mortris V7 с Mortris V1, Firebase Analytics,
GameAnalytics, Amplitude и Hypercell HyperKit, если последний доступен.
Нужно установить, какие преимущества можно публично доказать, а не заранее
подтвердить превосходство Mortris. Отрицательные результаты также обязательны.
Не заменяй недоступные измерения предположительными числами.

Результат — проверяемые артефакты, отчёт и готовые формулировки для презентации.
Если SDK, аккаунт или телефон недоступны, закончи доступную часть и явно обозначь
пробел. Не объявляй тестирование всех SDK завершённым при наличии таких пробелов.

## Этап 1. Зафиксировать методику до измерения

Создай `comparison/protocol.md` до запуска сравнительных бенчмарков:

- точные версии SDK/Unity/OS, commit V7, устройства, backend regions;
- происхождение и SHA корпусов, train/validation/test split, seeds;
- матрицу нагрузок, число повторов, warmup, длительность и критерии исключения;
- способы измерения CPU/GC/сети и ограничения каждого;
- одинаковые параметры окружения и общие отключаемые необязательные функции;
- список заранее проверяемых публичных утверждений и соответствующих метрик.

Выбор основной конфигурации V7 и словаря закончи на train/validation, затем
заморозь. После просмотра нового test не подстраивай её под победу; новые варианты
считай exploratory. Порядок запусков SDK рандомизируй или чередуй блоками.
Используй минимум5 независимых запусков каждого основного доступного сценария,
увеличивая число лишь при существенной нестабильности. Повторы одного корпуса
характеризуют вариативность выполнения, а не независимость игровых данных.

## Этап 2. Данные и честная эквивалентность

Сначала используй сохранённый private day для воспроизведения. Для независимого
подтверждения получи доступный другой день/когорту через read-only export,
если это разрешено имеющимся доступом. Не угадывай реквизиты подключения.
Если их нет — запроси доступ и продолжай на локальных данных, без статуса
independent confirmation. Физический телефон запрашивай только если отсутствует.

Не отправляй реальные install/user IDs и private payload в сторонние сервисы.
Для них подготовь обезличенный replay с одинаковым входом для всех SDK;
сохрани зависимости, длины, кардинальности и распределения значений, важные для
сжатия. Проверь, что обезличивание не превращает высокоэнтропийные данные в
удобные константы. Если распределение изменилось, покажи разницу размеров V1/V7
до/после локально и ограничь выводы. Данные и обученные реальные dictionaries
не включай в публичный пакет.

Сравнение веди двумя отдельными треками:

**A. Транспорт при одинаковой семантике.** Одни события и пользовательские поля,
одинаковая игровая очистка либо её отсутствие у всех SDK. Проверяй типы, диапазоны,
строки, количество событий и реальные ограничения SDK. Несовместимые поля
не удаляй молча: вынеси common-subset test и отдельный fidelity/capabilities report.
Внутреннюю служебную metadata SDK сохраняй как часть реальной стоимости,
но отдельно покажи её состав. Укажи, если равная гарантия dedup/order/retention
между SDK недостижима. Аналогичный идентификатор в custom property добавляй
лишь в отдельном явно названном сценарии семантической эквивалентности.

**B. Итоговая архитектура продукта.** V1 как есть → V1 с игровой очисткой →
V7 с той же очисткой и sequence identity. Добавь промежуточные ablations,
чтобы отдельно оценить очистку, identity, каталог, колонки и словарь.
Не приписывай выигрыш удаления полей одному codec. Очищенный корпус также
прогони через конкурентов там, где API позволяет: очистка доступна не только V7.

Данные: реальные raw/clean, другой доступный проект или независимый synthetic
project без Puzzle keys, schema drift, Unicode/длинные строки, UUID/high entropy,
короткие сессии и пачки1/10/100/500 там, где SDK это поддерживает.
Частоты:1/10/60 событий в секунду плюс ограниченный burst. Для60Hz используй
отдельный набор trajectory events и учитывай, что его размер не равен среднему
Puzzle event. Не экстраполируй9Б на произвольную физику/координаты.

## Этап 3. Что действительно отправляют конкуренты

Используй официальные SDK и первичные источники: документация, открытый код,
release notes. Запиши URL, дату проверки и версию. Не подменяй мобильный SDK
самодельным REST client. Для HyperKit сначала установи доступность SDK;
если кода/сборки нет, статус NOT_MEASURED, без выдуманного формата или времени.

Построй изолированный Unity harness: отдельная сборка на SDK либо режимы,
исключающие влияние остальных SDK. Сохрани конфигурацию и baseline без analytics.
Используй отдельные тестовые проекты/потоки; не загрязняй production-аналитику.
Не создавай платные ресурсы и не запускай дорогой объём без согласованного бюджета.
Если тестового аккаунта нет, локальные проверки продолжаются; внешнюю доставку
не считай доказанной. Соблюдай documented quotas и ограничивай burst.

Определи фактический payload через instrumented test transport, debug proxy
в своей сборке или SDK hooks, если доступны. Для TLS traffic capture без
расшифровки измеряй bytes/packets, но не объявляй известным plaintext формат.
Не обходи pinning стороннего приложения. Изменённый transport годится для
изучения payload, но его performance нельзя выдавать за unmodified SDK.

Разделяй три метрики:

1. Encoded/compressed application body bytes на принятые события.
2. HTTP headers + body bytes на запросы, если они наблюдаемы.
3. Полный сетевой обмен на выбранной capture boundary: оба направления,
   TLS/connection/ACK/retry; запиши учёт DNS, setup и фоновых запросов.

Для каждого SDK измерь default shipping configuration; отдельно — согласованный
batch/latency режим, если настройки поддерживаются. Не форсируй V7 пачку100,
оставляя конкурентам singles без пояснения. Учитывай flush после конца replay,
время доставки p50/p95, интервалы и заполненность пачек, backlog/потери.
Общие bytes/events не заменяй средним средних пачек. Покажи request count,
total bytes, events attempted/accepted/uploaded/observed at destination.
Если приём всех событий не подтверждён, не называй меньший трафик победой:
он может быть следствием дропа, сэмплирования или отложенного flush.

Отдельно: cold first session с catalog/dictionary/setup и warm steady state;
короткие сессии должны оплачивать реалистичную стоимость распространения assets.
Если delivery каталога ещё не реализована, явно отдели рассчитанный setup от
измеренного. Экстраполяцию на1000 событий помечай как расчёт.

## Этап 4. CPU, память, FPS и телефон

Основной аппаратный результат получи на физическом Android ARM64 с IL2CPP,
желательно на двух уровнях устройств. При наличии только эмулятора пометь всё
EMULATOR; не называй это phone benchmark. Не задерживай остальной отчёт.

Разделяй:

- стоимость вызова Track на main thread;
- подготовку/boxing/validation/serialization и работу background worker;
- непосредственно columns+compression;
- full framing/queue persistence/transport;
- wall time и CPU time, startup и steady state.

Для GC учитывай все относящиеся к SDK managed threads, а native allocations/
resident memory — отдельно. Калибруй измеритель положительной аллокацией и
пустым контролем. В Unity прежний GetAllocatedBytesForCurrentThread был stub;
не принимай0 без контроля. Не сравнивай Unity managed GC с native allocation
другого SDK как с одной метрикой.

Покажи p50/p95/p99, maximum и число samples для достаточных по объёму метрик,
GC bytes/event, bytes/batch, GC collections, process memory/native allocations.
Сначала проведи инструментированные профили, затем менее инструментированные
Release IL2CPP замеры: profiler/debugger меняют производительность.
При разных платформах/build settings не строй прямой рейтинг.

FPS тест: одинаковая воспроизводимая игровая сцена без analytics и с каждым SDK,
frame time distribution, main-thread stalls, температурное состояние и throttling
на продолжительном ограниченном replay. Контролируй питание, сеть, фоновые
процессы и cooldown. Батарею/энергию оценивай только подходящим измерением;
скорость упаковки сама по себе не доказывает экономию батареи.
Не обещай «0 микрофризов — гарантия» даже при0GC в одном тесте.

## Этап 5. Надёжность принятой sequence architecture

Для размеров используй принятое решение без случайных event UUID, но отдельно
докажи реализацию identity. Не внедряй изменения в production по этому заданию;
нужный минимальный vertical slice собирай в исследовательском harness.
Если полноценная реализация требует отдельной работы, зафиксируй пробел,
не выдавай pretyped encoder за готовый SDK.

Проверки: атомарность выделения sequence и enqueue в durable транзакции,
crash в точках записи/commit/send/ACK, перезапуск, offline/retry/дубликаты,
ResetIdentity с непустой очередью, новое origin/epoch, переполнение счётчика,
конкурентные producers, недоступный сервер при reset, восстановление backup.
Старые queued events сохраняют immutable origin, dedup key включает project и
origin/epoch/sequence. SQLite WAL сам по себе не доказывает все эти свойства;
запиши durability settings и границы process-crash/power-loss проверки.

Проверь допущения ADR: номера не обязаны быть подряд при eviction/filtering;
размер base/step/count не всегда1–2Б; gap не всегда означает сетевую потерю;
последний пропавший suffix не обнаруживается без дополнительного знания.
Continuous ACK не должен бесконечно ждать локально удалённое событие:
нужны documented gap/skip semantics. Если используется deterministic UUID,
проект и epoch должны входить в namespace/input согласно identity contract;
сам UUID не заменяет строгую уникальность составного ключа.

Для Puzzle сохраняй truncated/mismatched hashes; докажи durable interaction
index перед удалением GUID. Проверяй восстановление нужных backend/UI значений.
Не смешивай эти игровые преобразования с универсальным SDK.

## Этап 6. Статистика и публичные выводы

Считай отношения по одним событиям и одинаковому измеряемому слою.
Для трафика показывай totals и разброс по сессиям/пачкам, а не только среднее.
При оценке обобщения доверительные интервалы строй по независимым installations/
sessions или runs, не объявляй соседние события независимыми наблюдениями.
Покажи результаты на менее выгодных данных, fallback и потерю преимущества
при высокой энтропии/коротких сессиях/дорогом setup.

Составь claims ledger:

| Утверждение | Evidence/command/artifact | Условия | Статус | Допустимая публичная формулировка |
|---|---|---|---|---|

Статусы: MEASURED, REPRODUCED, MODELED, DOCUMENTED_ONLY, NOT_MEASURED,
FAILED. Не называй внутреннюю проверку сертификацией или независимым внешним
аудитом. «Лучшие» заменяй конкретным измеримым преимуществом среди проверенных
версий на указанной нагрузке. Потенциальные результаты можно показывать только
как prototype/model с перечисленными предпосылками, отдельно от shipping facts.

Кандидаты формулировок, подлежащие проверке:

- «На [корпусе] V7 уменьшил [body/full wire] на X% относительно [SDK/version]
  при одинаковых полях, [batch/latency] и подтверждённой доставке N событий».
- «Проверенный этап упаковки имеет0 managed GC после warmup; входной API,
  native memory и доставка измерены отдельно».
- «На [телефон/OS/Release IL2CPP] p95 упаковки100 событий составил X мс».

Если преимущество не воспроизводится, так и напиши. Не подбирай baseline,
поля или частоту задним числом ради победы.
