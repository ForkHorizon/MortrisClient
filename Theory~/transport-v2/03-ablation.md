# 03. Абляция: вклад каждой оптимизации

Все цифры, кроме помеченных иначе, **[измерено]** на синтетике (`04-experiments/`, `sh run_all.sh`). Единица:
байт итогового тела HTTP-запроса на одно событие (сумма сжатых тел / число событий), если не сказано иное.
Два профиля данных (подробно в `04-experiments/README.md`):

- **base**: 838 Б сырого JSON на событие, 113 Б после gzip-1. Повторяемее реальных данных.
- **rich**: 1 025 Б сырого, 171 Б после gzip-1; откалиброван под отчёт игры (~1 096 / ~170 Б) добавлением шумных
  полей. Ближе к реальности по энтропии, но поля выдуманы.

Пачки нарезаны так, как это делает `AnalyticsUploader` (30 с или ≥ 50 событий, ≤ 100): средняя пачка 29 событий.
Базовая линия = то, что SDK отправляет сейчас: V1 JSON + gzip `CompressionLevel.Fastest` (= gzip-1) [код:
`AnalyticsUploader.GzipContent`]. **Отчёт игры, вероятно, считал gzip уровня по умолчанию; SDK шлёт Fastest, а это
на 14–16% больше** [измерено: gzip-1 vs gzip-6].

## 1. Где сидят байты сегодня (V1, leave-one-out)

Сколько байт на событие исчезнет из сжатого тела, если убрать только это поле (`run_size.py` §7):

|---|---:|---:|---:|
| `event_id` (UUID v4 текстом) | 50,0 | **27,9** | **29,4** |
| `properties.placed_state_hash` (SHA-256 hex) | 39,4 | 11,2 | 12,7 |
| контекст устройства (7 полей) | 246,8 | 10,5 | 12,0 |
| `session_elapsed_ms` | 27,7 | 7,0 | 7,7 |
| `occurred_at_client` (ISO-строка) | 48,0 | 6,1 | 6,9 |
| `name` | 25,0 | 5,3 | н/д |
| `sequence` | 15,1 | 3,8 | н/д |
| `session_id` | 52,0 | 2,0 | н/д |
| `properties.wave_attempt_id` (дубликат) | 56,0 | 0,4 | н/д |
| `properties.app_version` (дубликат) | 23,0 | 0,4 | н/д |

Вывод: после gzip дорого то, что **случайно** (UUID на событие, хеши, float-ы, время), а не то, что **длинно**.
Контекст устройства занимает 29% сырого JSON и 9% сжатого. Дубликаты из отчёта игры почти бесплатны после gzip.
Сумма строк ≠ итог: поля взаимодействуют через окно компрессора.

это аргумент за то, чтобы сначала уменьшать вход (MTB2), а потом сжимать: на MTB2 zstd-19+словарь стоит 50–70 мкс (шум между прогонами).

Размер словаря (zstd-19, base / rich, MTB2): нет 42,0 / 70,7; 2 КиБ 27,1 / 55,4; 4 КиБ 25,0 / 52,5; 16 КиБ 22,7 /
47,4; 64 КиБ 21,6 / 44,4. После 16 КиБ отдача мала: 16 КиБ выбран как компромисс размера SDK.

## 4. Формат кадра (лучший компрессор для каждого = zstd-19 + словарь 16 КиБ)

| Формат | без сжатия | gzip-6 | zstd-19 | zstd-19+словарь base | rich | vs сегодня base / rich |
|---|---:|---:|---:|---:|---:|---:|
| V1 JSON | 838 | 97,0 | 84,8 | 62,1 | 96,5 | −45% / −43% |
| MessagePack, та же структура | 736 | 101,3 | 88,0 | 64,1 | 97,5 | −43% / −43% |
| CBOR, та же структура | 741 | 101,4 | 88,3 | 64,8 | 100,2 | −43% / −41% |
| JSON со всеми JSON-оптимизациями | 177 | 54,4 | 49,7 | 31,2 | 63,0 | −72% / −63% |
| MessagePack компактный (строки) | 81 | 37,8 | 35,8 | 27,2 | 55,3 | −76% / −68% |
| Protobuf общий `Prop{key,value}` | 122 | 42,7 | 38,0 | 27,1 | 56,5 | −76% / −67% |
| Protobuf с кодогенерацией | 87 | 39,6 | 37,8 | 27,7 | 56,8 | −75% / −67% |
| MTB2 построчный (те же токены) | 57 | 43,8 | 43,4 | 24,9 | 51,1 | −78% / −70% |
| **MTB2 колоночный** | 57 | 42,4 | 42,0 | **22,7** | **47,4** | **−80% / −72%** |

Выводы:
- Замена JSON на MessagePack/CBOR **без** перестройки не даёт ничего (а без словаря даже хуже JSON+gzip-6).
- Protobuf, MessagePack-компакт и MTB2 почти равны **без словаря** (37–42 Б). Разницу делает связка
  «колонки + словарь»: колонки дают словарю и LZ однородные потоки.
- Колоночный layout против построчного с теми же байтами: −9% base, −7% rich со словарём; −3…−4% без словаря.

## 5. MTB2: выключение каждой функции по одной (zstd-19 + словарь)

| Вариант | base | Δ | rich | Δ |
|---|---:|---:|---:|---:|
| MTB2 полный | 22,7 | | 47,4 | |
| без колонок (построчно) | 25,7 | +13% | 52,6 | +11% |
| без ALIAS/CTXREF (авто-дубликаты) | 23,2 | +2% | 47,6 | +0,4% |
| без delta для INT | 24,4 | +7% | 50,1 | +6% |
| + `install_id` не передаётся (из авторизации) | 22,2 | −2% | 46,8 | −1% |

| + `placed_state_hash` не передаётся (сервер вычисляет) | 16,5 | −27% | 40,7 | −14% |

Выводы:
- Кэш контекстов/форм вреден при словаре: случайный 8-байтный отпечаток не сжимается, а строки формы словарь
  сжимает почти в ноль. Без словаря кэш давал −6%. **Реестр схем ради байтов не нужен.**
- Удаление вычислимого хеша самый крупный оставшийся рычаг, но это игровая логика (02, агрессивный вариант).

## 6. Состояние между пачками

`run_stateful.py`, MTB2 без `install_id`, zstd-19 + словарь, кадр минимальный.

| Вариант | base | rich |
|---|---:|---:|
| A: без состояния | 21,86 | 46,52 |
| B: + предыдущая подтверждённая пачка как добавка к словарю | 20,60 (−5,8%) | 45,52 (−2,2%) |
| C: кэш контекстов/форм по отпечатку | 22,64 (+3,5%) | 46,58 (+0,1%) |
| D: B + C | 21,01 (−3,9%) | 45,11 (−3,0%) |

Цена B: сервер хранит последнюю пачку каждой установки, клиент хранит её копию, потеря ответа или порядок пачек
требуют протокола ссылок и ресинка, повтор после отказа нельзя отправить тем же кадром. За 2–6% это не окупается.
**Отвергнуто.** Безопасный ресинк, если когда-нибудь понадобится: ссылаться только на пачку, подтверждённую ack, по её
`(first_seq, n)`; при `REF_UNKNOWN` отправлять без ссылки. Ни одна потеря не приводит к потере данных, только к +1 RTT.

## 7. Размер пачки

Те же события, нарезанные в фиксированные пачки по одной установке (`run_size.py` §6), base / rich:

| Кодек | n=1 | n=5 | n=10 | n=25 | n=50 | n=100 | n=500 |
|---|---:|---:|---:|---:|---:|---:|---:|
| V1 gzip-1 | 628 / 735 | 218 / 290 | 156 / 219 | 117 / 176 | 105 / 162 | 99 / 155 | 93 / 150 |
| V1 zstd-19+словарь | 206 / 252 | 90 / 131 | 74 / 112 | 64 / 98 | 60 / 94 | 58 / 92 | 57 / 90 |

| MTB2 zstd-19+словарь | 216 / 275 | 67 / 105 | 41 / 72 | 25 / 50 | 21 / 45 | 18 / 41 | 15 / 37 |

Выводы:
- Словарь важнее всего на маленьких пачках: n=1 у MTB2 216 Б со словарём против 476 без.
- Рост пачки 25 → 100 даёт ещё −28% (base) / −18% (rich) на MTB2. Сегодня средняя пачка 29 событий, потому что
  таймер 30 с срабатывает раньше порога 50 (взаимодействие ≈ 4 события за ~4 с) [оценка по `gen.py` + код таймера].

## 9. Заголовки, TLS, TCP (`run_http.py`, `results/tls.txt`)

Тёплое соединение, средняя пачка 31 событие (base), всё на проводе вверх / вниз, байт на событие:

| Сценарий | вверх | вниз | всего | vs сегодня |
|---|---:|---:|---:|---:|
| V1 сегодня, HTTP/1.1 keep-alive | 127,7 | 54,9 | 182,6 | |
| V1, HTTP/2 | 119,7 | 51,4 | 171,1 | −6% |
| MTB2, HTTP/1.1 | 30,1 | 6,8 | 36,9 | −80% |
| MTB2, HTTP/2 | 26,4 | 5,3 | 31,7 | −83% |

- Заголовки запроса V1 HTTP/1.1: 236 Б (+22 Б при `Expect: 100-continue`); V2: 141 Б; HTTP/2 после первого
  запроса: 10–12 Б [измерено, `hpack`].
- Холодное соединение: TCP ~192 Б + полный TLS 1.3: клиент→сервер 302–319 Б (X25519) или 1 500–1 728 Б
  (гибрид X25519MLKEM768), сервер→клиент 2,8–5,2 КиБ [измерено на 4 публичных хостах, `openssl s_client`].
  Одна пачка MTB2 по холодному соединению: тело = **12%** всех переданных байт.
- Поэтому для редких отправок важнее держать соединение и TLS-сессию (возобновление без цепочки сертификатов,
  [оценка] 400–700 Б вверх / 200–400 Б вниз), чем ужимать тело дальше.

| Энтропийный предел генератора base | ~11 | н/д | [оценка: `entropy_floor.py`] |

Ответ сервера: 44,8 → ~0,2 Б/событие во всех вариантах с новым ack.

**Насколько это предел.** Для base генератора информационный минимум ~11 Б/событие, из них ~6 Б это хеши SHA-256 и
~2 Б float-ы [оценка]. MTB2 + словарь = 22 Б, т.е. ~2× от предела. Оставшийся зазор: varint-ы без энтропийного
кодирования, таблицы строк в каждой пачке, UUID сессии/попытки (16 Б на пачку), сериализация float без
предсказания. Кастомный энтропийный кодер по колонкам (ANS/арифметический) мог бы забрать **[гипотеза]** ещё
20–35%, но это свой кодек на двух языках ради ~5 Б/событие. Для реальных данных предел неизвестен (07 Q1).
