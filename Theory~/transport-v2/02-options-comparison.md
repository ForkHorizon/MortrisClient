# 02. Варианты: консервативный, рекомендуемый, агрессивный

Размеры: байт тела запроса на событие, **[измерено]** на синтетике base / rich (`03-ablation.md`). Сегодня:
112,8 / 170,8 Б тело + 44,8 Б ответ на событие. «Сложность» и «стоимость поддержки» это **[оценка]** автора, не
измерение; строки кода посчитаны по эталонному Python и умножены на типичный коэффициент для C#/Java/сервера.

## Вариант 1. Консервативный «JSON+»

Остаёмся на JSON, сервер почти не меняется.

1. `CompressionLevel.Fastest` → `Optimal` (одна строка в `AnalyticsUploader.GzipContent`): −14…−16%,
   серверу ничего не нужно [измерено]. **Можно сделать сразу в 0.2.0.**
2. Убрать `event_id` из тела, дедуплицировать по `(install_id, sequence)` (поле `sequence` уже в теле [код]); сервер
   выводит `event_id = UUIDv5(install_id, sequence)`. Накопительно −31…−36%.
3. Таблица контекстов устройства + `base_time` и дельты в JSON (`schema_version: 2`): −37…−43%.
4. Сжатие: Brotli-11 (−51…−55%) или zstd-19 с вшитым словарём (−60…−69%). Brotli не требует словаря, но дорог по
   CPU на 25 КиБ JSON; zstd со словарём требует нативной библиотеки zstd в Android-плагине (≈ 300–700 КиБ на ABI
   [оценка], 07 Q5).
5. Ответ: `{"ok":[first_seq,count],"rej":[...],"pe":<policy_epoch>}` вместо списков UUID: −44 Б/событие вниз.

Когда выбирать: если команда не готова поддерживать бинарный формат или сервер должен оставаться «JSON на входе».

## Вариант 2. Рекомендуемый «MTB2»

Полная спецификация: `01-protocol-spec.md`. Суть:

- колоночная пачка с формами событий внутри пачки, таблицами строк/UUID/hex, дельтами времени и целых;
- zstd-19 со словарём 16 КиБ, вшитым в SDK; запасной кодек raw DEFLATE;
- **никакого состояния между запросами**, никакого реестра схем, никакой кодогенерации;
- идентичность `(install_id, sequence)`, ack одним статусом на кадр, политика по эпохе внутри ack;
- упаковка из существующей очереди (`payload_json`), миграция SQLite не нужна;
- V1 остаётся как fallback на тех же строках очереди.

Почему не Protobuf, хотя он близок: «Protobuf общий + словарь» = 27,1 / 56,5 Б против 22,7 / 47,4 у MTB2 (+19%)
[измерено]. Protobuf с кодогенерацией не лучше общего (27,7 / 56,8), а требует схемы на каждую игру. Если команда
предпочтёт стандартный инструмент, **Protobuf общий + zstd-словарь** приемлемая замена с потерей ~19% байтов; всё
остальное (идентичность, ack, словари, fallback) из спецификации переносится без изменений.

Когда кастомный формат оправдан: (а) нужен колоночный layout, которого нет в Protobuf/MessagePack без вложенных
повторяющихся полей на каждую колонку; (б) формат маленький (здесь ~12 типов, ~450 строк эталона с декодером);
(в) есть эталон, тест эквивалентности «байт в байт» и fuzz. Все три условия здесь выполнены.

Батарея и запросы (общая часть вариантов 2 и 3):
- Держать соединение тёплым внутри сессии: при 30-секундной отправке keep-alive сервера должен быть ≥ 60 с, иначе
  каждая пачка платит полный TLS (2,8–5,2 КиБ вниз, больше самой пачки) [измерено].
- Отправка на `OnApplicationPause(true)` / уход в фон уже логична; в фоне MAY использовать WorkManager с
  `NetworkType.CONNECTED` для остатка [источник: Android, оптимизация сетевого доступа].
- Таймер 30 с → 60 с при активной игре: средняя пачка вырастет с ~29 до ~55 событий, тело MTB2 −18% base / −10% rich на событие (n=25 → n=50),
  радио просыпается вдвое реже [измерено §7 для размера; для батареи **гипотеза**, нужен замер Battery Historian, 07 Q4].

## Вариант 3. Агрессивный «MTB2+»

Рекомендуемый плюс:

1. **Вычислимые поля на сервере (игровое).** Схема игры объявляет, что поле выводится из предыдущих событий
   (например `placed_state_hash = H(state_before, block_id, cell)`); клиент его не шлёт, сервер вычисляет плагином
   игры и сверяет по редким контрольным точкам (каждое N-е событие несёт поле). −27% base / −14% rich [измерено
   при полном удалении хеша]. Риск: расхождение логики клиента и сервера искажает аналитику молча, поэтому
   контрольные точки обязательны.
2. **Пачки 100–500 событий**: отправка при паузе/фоне и раз в 2–5 мин в игре. −20…−30% к телу и в разы меньше
   запросов [измерено §7]. Цена: задержка данных до минут, больше событий в окне потери при удалении приложения
   (очередь на диске, так что не теряется при убийстве процесса [код]).
3. **Шаблоны составных событий** (interaction frames) явно, а не через колонки: даёт мало сверх колонок, потому что
   колонки + дельты уже убирают повтор `block_id`, атрибутов попытки и т.п. (−13% от колоночности, −7% от delta)
   [измерено]. Явные шаблоны стоит делать только для полей, которые вычисляются из времени (например `drag_ms` =
   `t(released) − t(taken)` в синтетике), а это опять «вычислимые поля» из п.1.
4. **Ссылка на прошлую подтверждённую пачку** (stateful): −2…−6% [измерено]. Включать только если всё остальное уже
   сделано.
5. **Свой энтропийный кодер по колонкам** вместо zstd: [гипотеза] −20…−35%; синтетика base в ~2× от своего
   информационного предела (22 vs ~11 Б), из них ~6 Б хеши.

## Отвергнутые варианты

| Вариант | Почему отвергнут | Доверие |
|---|---|---|
| MessagePack/CBOR вместо JSON без перестройки | 101 Б vs 97 Б у JSON при gzip-6; со словарём ±3% | [измерено] |
| FlatBuffers / Cap'n Proto | zero-copy layout с выравниванием и offset-таблицами крупнее varint-форматов; zero-copy чтение бесполезно для пачки, которую всё равно распаковывают | [источник: документация форматов] + [гипотеза], не измерено |
| Avro container | схема в заголовке файла, по сути то же, что формы в пачке, но схема как JSON-текст и без колонок | [гипотеза], не измерено |
| Реестр схем и числовые ID | со словарём выигрыш 0…+4% против форм в пачке; цена: синхронизация клиента и сервера, неизвестные схемы, версии | [измерено §5] |
| Кэш контекстов/форм по отпечатку (CAS) | +3,5% base, +0,1% rich при словаре | [измерено] |
| Состояние компрессора между пачками | −2…−6%, сложный ресинк | [измерено] |
| Динамическая загрузка словаря с сервера | новый запрос, новое состояние, вектор атаки; вшитый словарь даёт то же | [оценка] |
| Compression Dictionary Transport (RFC 9842, `dcz`/`dcb`) | стандартный путь для ответов браузерам; для загрузок клиент→сервер и без браузера не даёт ничего сверх своего `dict_id` | [источник] |
| HTTP/3, QUIC 0-RTT | размер почти не меняется, 0-RTT повторяем атакующим; второй стек на Unity/Android | [источник] + [оценка] |
| WebSocket/долгое соединение | держит радио и сокет; аналитике не нужна низкая задержка | [источник: Android] |
| Отказ от сжатия, только бинарь | MTB2 без сжатия 57 Б vs 22,7 Б со словарём | [измерено] |
