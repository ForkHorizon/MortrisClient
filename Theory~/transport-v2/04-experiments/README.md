# 04. Эксперименты

Скрипты здесь это **доказательства, а не продуктовый код**. Python 3.11+ (проверено на 3.14.8, macOS arm64).

## Как воспроизвести всё

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
PY=.venv/bin/python sh run_all.sh
```

Время: ~10 мин на ноутбуке (Brotli-11 доминирует). Всё детерминировано (фиксированные seed), кроме таймингов CPU и
TLS-замеров. Сырой вывод: `results/`. Версии библиотек, на которых получены числа в отчёте: `requirements.txt`.

## Данные: `gen.py`

**Как генерируется.** Игра-головоломка с SDK 0.2.0:
- формат V1 события и пачки скопирован с кода SDK: `PersistenceEventSerializer.cs` (поля, порядок, формат времени),
  `AnalyticsQueue.java` (добавляет `sequence`, Android `org.json` экранирует `/` как `\/`), `AnalyticsUploader.cs`
  (конверт пачки, gzip `Fastest`);
- сессии → попытки (1–3) → волны (3–5) → взаимодействия (5–12 на волну), каждое = `detail_taken`,
  `detail_released`, `placement_resolved`, `state_checkpoint`; плюс редкие `session_start`, `attempt_*`, `wave_*`,
  `hint_used`, `ui_click`, `ad_impression`. Доля 4 основных событий 90,8% (отчёт игры: 87,6%);
- дубликаты как в отчёте: `wave_attempt_id == attempt_id`, `app_version` и в контексте, и в properties;
  `placed_state_hash` = SHA-256 hex, меняется при успешной установке;
- время: пауза между взаимодействиями lognormal (медиана ~3 с), drag lognormal (медиана ~730 мс), остальное
  равномерно в узких диапазонах; `session_elapsed_ms` = стенное время + случайное блуждание ±1 мс;
- `build_number` = 32 hex (по умолчанию SDK берёт `Application.buildGUID` [код]); `os_version` в формате Unity
  `SystemInfo.operatingSystem` на Android; 5 устройств, 2 версии приложения;
- пачки: повтор логики `AnalyticsUploader` (30 с или ≥ 50 событий, ≤ 100), 15% сессий офлайн с накоплением до
  следующей сессии. Средняя пачка 29 событий, 5% пачек по 100.

**Профили.** `base` (как выше) и `rich` (`dataset(..., rich=True)`): к 4 основным событиям добавлены шумные поля
(`frame_ms`, `fps`, `free_memory_mb`, `touch_x/y`, `camera_zoom`, `since_last_action_ms`, `ui_layer`; в checkpoint
растущий список `placed_block_ids`, `house_progress`, случайная битовая карта `board_rows`). Цель: попасть в цифры
отчёта игры. Получилось 1 025 Б сырого JSON и 162 Б gzip-1 при пачках по 50 (отчёт: ~1 096 и ~170).

**Что может исказить выводы.**
- Base повторяемее реальности (113 Б vs ~170 Б после gzip): относительный выигрыш на нём завышен. Поэтому каждый
  вывод проверен на rich; диапазоны в отчёте = [rich, base].
- Rich откалиброван по двум числам. Его шумные поля выдуманы: реальная энтропия может сидеть в других полях
  (например, длинные строки, вложенные ID), и тогда колонки/словарь помогут иначе.
- Словари обучены на seed=2, проверены на seed=1: разные установки, UUID, хеши, но **тот же генератор**. На реальных
  данных словарь, обученный на одной версии игры, увидит новые события/ключи: эффект словаря, вероятно, ниже
  (07 Q2).
- Значения float32 случайны по всей мантиссе; реальные координаты могут быть округлены (тогда дешевле).
- Нет многоплатформенности (только Android-форматы строк), нет кириллицы/эмодзи в массовых значениях (есть в тесте
  граничных случаев).

## Эксперимент E1. Эквивалентность и надёжность декодера: `test_roundtrip.py`

- **Вопрос:** восстанавливает ли MTB2 тело V1 без потерь; не падает ли декодер на мусоре?
- **Метод:** 739 пачек / 21 545 событий (base + rich) кодируются, декодируются, из результата собирается тело V1 без
  `event_id` и сравнивается **байт в байт** с настоящим телом V1 без `event_id`. Оба режима: обычный и с кэшем
  отпечатков. Плюс ручные граничные случаи (ulong max, int64 min, decimal с хвостовыми нулями, double vs float,
  null, Unicode, верхний регистр hex, пустые properties, один ключ разных типов, разрывы sequence, две сессии в
  пачке). Плюс 20 000 мутаций (замена/удаление/вставка байт) валидных кадров.
- **Команда:** `python test_roundtrip.py`
- **Результат:** `results/roundtrip.txt`: эквивалентность OK, граничные случаи OK, 0 неожиданных исключений.
- **Ограничения:** fuzz примитивный (без покрытия); «ожидаемые» исключения включают `TypeError`/`StopIteration`,
  продуктовый декодер должен сводить их к одной ошибке `BAD_FRAME`. Лимиты распаковки (бомбы) здесь не проверяются,
  они на уровне zstd-потока (§9 спецификации).

## Эксперимент E2. Матрица формат × компрессор, абляция, размер пачки: `run_size.py`

- **Вопрос:** сколько байт на событие даёт каждый формат и компрессор; вклад каждой оптимизации; где сидят байты;
  как размер пачки влияет на байты/событие; размер ответа V1.
- **Команда:** `python run_size.py 10 base > results/sizes_base.md`, то же с `rich`.
- **Результат:** `results/sizes_base.md`, `results/sizes_rich.md` (разделы 1–8); сводка в `03-ablation.md`.
- **Ограничения:** Protobuf закодирован вручную по wire-формату (без `protoc`), схема описана в docstring
  `wire.py`; это эквивалентно сгенерированному коду по байтам, но не проверено `protoc --decode`. Ответ MTB2 в §8
  посчитан, а не закодирован.

## Эксперимент E3. Консервативный путь на JSON: `run_conservative.py`

- **Вопрос:** сколько даёт путь без бинарного формата, по шагам.
- **Команда:** `python run_conservative.py > results/conservative.md`
- **Результат:** −14…−16% (gzip-6), −31…−36% (+ без `event_id`), −37…−43% (+ контекст/дельты), −51…−55% (+ Brotli-11),
  −60…−69% (+ zstd-19 + словарь).

## Эксперимент E4. Состояние между пачками: `run_stateful.py`

- **Вопрос:** окупается ли stateful-сжатие (прошлая пачка как словарь) и кэш контекстов/форм.
- **Команда:** `python run_stateful.py base|rich`
- **Результат:** `results/stateful_*.md`: прошлая пачка −5,8% / −2,2%; кэш +3,5% / +0,1%.
- **Ограничения:** предполагается идеальная доставка (ссылка всегда на последнюю пачку); в реальности потери ухудшат
  stateful-вариант, т.е. вывод «не окупается» консервативен.

## Эксперимент E5. HTTP/TLS/TCP: `run_http.py`, `measure_tls.sh`

- **Вопрос:** какую долю составляет тело на проводе; сколько стоит холодное соединение.
- **Команды:** `python run_http.py > results/http.md`; `sh measure_tls.sh > results/tls.txt` (нужна сеть).
- **Что измерено:** размеры заголовков HTTP/1.1 (строки) и HTTP/2 (библиотека `hpack`), тела, полный TLS 1.3 / 1.2
  handshake (`openssl s_client`, 4 публичных хоста, OpenSSL 4.0.3).
- **Что взято из стандартов:** 22 Б на TLS-запись (RFC 8446 §5.2), 52 Б TCP/IPv4 на сегмент с timestamps.
- **Что оценено:** TLS-возобновление (счётчики `s_client` для resumption оказались ненадёжными, убраны), чистые ACK.
- **Ограничения:** реальный сервер аналитики, его цепочка сертификатов, keep-alive и HTTP-стек Unity не измерялись.
  Заголовки V1 включают `Expect: 100-continue` как гипотезу (07 Q6).

## Эксперимент E6. CPU: `run_cpu.py`

- **Вопрос:** сколько стоит сжатие/распаковка на пачку.
- **Результат:** `results/cpu.md`. Только десктоп (Apple M, arm64), C-библиотеки через Python. Таймеры шумят ±10–20%.
- **Ограничения:** телефон не измерен; коэффициент 3–10× это **оценка**. Кодировщик MTB2 на Python (~0,5 мс/пачка)
  не показателен для C#.

## Эксперимент E7. Пример для спецификации: `make_example.py`

Одна пачка из 20 событий: V1 JSON → MTB2 → кадр, hexdump по секциям. Файлы `results/example_*`. Проверка кадра
(из папки `04-experiments`):

```python
import zstandard as z, wire
f = open("results/example_frame.bin", "rb").read()
d = z.ZstdCompressionDict(open("results/example_dict.bin", "rb").read())
raw = z.ZstdDecompressor(dict_data=d, format=z.FORMAT_ZSTD1_MAGICLESS).decompress(f[2:], max_output_size=2 << 20)
meta, events = wire.mtb2_decode(raw)   # raw == example_payload.bin, 20 событий
```

## Эксперимент E8. Энтропийный предел генератора: `entropy_floor.py`

Аналитический расчёт информации, которую генерирует `gen.py` (base) на взаимодействие: ~11 Б/событие, из них
~6 Б хеши и ~2 Б float. Это **оценка** (дифференциальная энтропия lognormal с квантованием 1 мс, равномерные
распределения), а не измерение; редкие события учтены грубо (с запасом).
