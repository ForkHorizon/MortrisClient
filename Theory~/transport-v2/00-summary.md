# 00. Итог: Mortris Analytics Transport V2

1. **Рекомендация:** MTB2: колоночная пачка без состояния между запросами, формы событий внутри пачки (без реестра
   схем), zstd-19 со словарём 16 КиБ, вшитым в SDK, идентичность `(install_id, sequence)`, ack 4–6 байт. Спека: `01`.
2. **Тело запроса:** −72…−81% к сегодняшнему (171 → 47 Б/событие rich, 113 → 22 Б base) [измерено на синтетике].
   Ответ сервера: ~45 → ~0,2 Б/событие. Всё на проводе при тёплом соединении: −80% (183 → 37 Б/событие).
3. **Консервативный путь без бинарного формата** (`02`, вариант 1): gzip-6 + убрать `event_id` + zstd-словарь
   на JSON = −60…−69%. Первый шаг (gzip `Fastest` → `Optimal`) даёт −14…−16% одной строкой уже сейчас.
4. **Что важно, по убыванию:** словарь zstd (−43…−45% даже на JSON) > убрать UUID события (−25%) > колоночность и
   дельты (−7…−13%) > контекст и дубликаты (1–5%, исходный документ их переоценивал).
5. **Что отвергнуто по замерам:** реестр схем/числовые ID и кэш контекстов (0…+4% при словаре), состояние между
   пачками (−2…−6% за сложный ресинк), MessagePack/CBOR без перестройки (≈ JSON).
6. **Агрессивно** (`02`, вариант 3): + пачки по 100 (ещё −18…−28%) + вычисление `placed_state_hash` сервером
   (−14…−27%, игровая логика) ≈ −80…−88%. Синтетика base в ~2× от своего энтропийного предела (22 vs ~11 Б).
7. **Без потерь:** декодер восстанавливает тело V1 байт в байт, кроме `event_id` (21 545 событий + граничные
   случаи); 20 000 мутированных кадров без неожиданных исключений.
8. **Главные риски:** (а) синтетика вместо реальных данных, особенно для словаря; (б) `resetIdentity` сейчас
   переписывает `install_id` в очереди, что ломает дедупликацию по `sequence`: нужен `origin_install_id` (`01` §6.3);
   (в) нативный zstd в Android-плагине (размер, сборка); (г) словарь из реального трафика утечёт данными в SDK.
9. **Неизвестно:** реальная энтропия событий; старение словаря между версиями игры; CPU/батарея на телефоне;
   что реально шлёт `HttpClient` Unity (`Expect: 100-continue`, сжатие ответа, HTTP/2). Всё в `07`.
10. **Транспорт:** для редких пачек TLS handshake (2,8–5,2 КиБ вниз) больше самой пачки; держать keep-alive ≥ 60 с
    важнее, чем ужимать тело дальше. HTTP/3 и 0-RTT не нужны.

## Допущения, с которыми сделана работа

Вопросов к пользователю, без которых нельзя продолжить, не было; ниже допущения по умолчанию (каждое отражено в `07`).

| Допущение | Почему | Что изменится, если неверно |
|---|---|---|
| Реальные события похожи на профиль rich (1,0 КиБ сырого JSON, ~170 Б gzip) | единственные реальные числа из отчёта игры | диапазоны выигрыша сдвинутся; направление выводов вряд ли |
| Отчёт игры мерил gzip по умолчанию, SDK шлёт `Fastest` | [код] SDK; отчёт не уточняет | калибровка rich на ~15% |
| Сервер можно менять полностью; V1 остаётся как fallback | условие задачи | — |
| Только Android | только Android хранит и отправляет в 0.1.4/0.2.0 [код] | для iOS нужен тот же кодировщик, контекст другой |
| Сервер дедуплицирует сейчас по `event_id` | кода сервера нет | этап 2 плана нужен в любом случае |
| Код SDK доступен и использовался для проверки | задача говорила «кода нет», но он лежит в этом репозитории; все утверждения о нём помечены [код] | — |
