# 06. План внедрения

Каждый этап выпускается отдельно, обратим и даёт выигрыш сам по себе. Порядок выбран по «байты на риск».

## Этап 0. Данные (до любой работы над форматом)

- Собрать реальные пачки (07 Q1): 500–5 000 подряд идущих событий с границами пачек с 3–5 устройств, тело запроса и
  ответа, заголовки (захват через прокси на тестовой сборке или логирование на сервере).
- Прогнать на них `run_size.py` / `run_conservative.py` (подменить `dataset()` загрузкой реальных пачек).
- **Критерий:** таблица §10 `03-ablation.md` пересчитана на реальных данных; выбран вариант (02).

## Этап 1. Бесплатное (SDK 0.2.x, сервер без изменений)

1. gzip `Fastest` → `Optimal` [−14…−16%].
2. Явно отключить `Expect: 100-continue` (`request.Headers.ExpectContinue = false`), если захват подтвердит, что он есть.
3. Сервер: включить gzip ответов, если `Accept-Encoding` есть; SDK: `AutomaticDecompression = GZip` у `HttpClientHandler`.
4. Сервер: keep-alive ≥ 60–75 с (для 30-секундного таймера SDK).

**Приёмка:** захват показывает уменьшение тела; ни одного нового кода ответа; доля 5xx не выросла.

## Этап 2. Идентичность `(install_id, sequence)` (сервер, затем SDK)

1. Сервер: дедупликация по `(install_id, sequence)` параллельно с `event_id`; сравнение решений обеих схем на
   проде (теневой режим) минимум 2 недели. Хранить CRC32C события для `IDENTITY_CONFLICT`.
2. SDK: колонка `origin_install_id` в `pending_events` (миграция SQLite: копия `install_id`), `resetIdentity` её
   не трогает; регистрация передаёт `previous_install_id`.
3. Сервер: вывод `event_id = UUIDv5(install_id, sequence)` для хранилища.
4. SDK: перестать слать `event_id` (V1 JSON, `schema_version: 2`). [−31…−36% вместе с этапом 1]

**Приёмка:** в теневом режиме расхождений решений «дубликат/новое» 0 или каждое объяснено; тест: отправка → потеря
ответа → `resetIdentity` → повтор → сервер видит дубликат.

## Этап 3. Новый ack и политика по эпохе (сервер + SDK)

Компактный ответ (JSON или сразу бинарный §7) и `policy_epoch`. Ответ ~45 → ~0,2 Б/событие; минус периодический
`/v1/client/policy`.

**Приёмка:** очередь удаляет ровно то, что удаляла бы по старому ответу (тест на записанных парах запрос/ответ).

## Этап 4. MTB2 (сервер, затем SDK за флагом)

1. Сервер: декодер MTB2 по `01-protocol-spec.md`, эндпоинт `/v2/b`, лимиты §9, метрики (размер кадра, raw, коэффициент,
   время декодирования, коды ошибок, доля fallback).
2. Сервер: поле `transport.v2` в register/policy; выключено по умолчанию.
3. SDK: кодировщик MTB2 из строк очереди (`payload_json`); fallback на V1 на 400/404/405/`V2_DISABLED`.
4. Словарь 1: обучить на реальных кадрах этапа 0 (перекодировать V1 в MTB2 на сервере), вшить в SDK.
5. Включение по процентам установок: 1% → 10% → 50% → 100%, по неделе на шаг.

**Приёмка на каждый шаг:**
- доля событий, принятых через V2, совпадает с контрольной группой V1 (±0,1%) по числу событий на установку в день;
- 0 расхождений в тесте эквивалентности на теневом потоке (сервер декодирует V2 и сравнивает с V1, если клиент
  в тестовой когорте шлёт оба);
- медиана байт на событие снизилась не меньше чем на 50% от V1 на реальных данных;
- p99 времени декодирования < 5 мс на кадр; ноль OOM.

## Этап 5. Отправка и батарея

Таймер 30 → 60 с в активной игре, отправка на паузе/выходе в фон, WorkManager для остатка в фоне. Замер Battery
Historian на 2–3 устройствах (07 Q4).

**Приёмка:** число запросов на сессию −40% и больше; задержка доставки p95 < 5 мин; потерь нет (сравнение
`sequence` без разрывов на сервере по когорте).

## Этап 6 (по решению). Агрессивные шаги

Вычислимые поля через серверный плагин игры с контрольными точками; пачки 100–500. Только после того, как этапы
1–5 стабильны и реальные данные показывают, что оставшиеся байты в этих полях.

## Тесты

| Тест | Что проверяет | Где |
|---|---|---|
| Эквивалентность V1/V2 | декодированный V2 = тело V1 без `event_id`, байт в байт | порт `test_roundtrip.py` в C# и сервер; общий корпус записанных пачек |
| Золотые векторы | кодировщик C# выдаёт те же байты, что эталон (`results/example_payload.bin` и ещё ~50 пачек) | SDK unit-тесты |
| Fuzz декодера | никаких падений/зависаний/OOM; все ошибки = `BAD_FRAME` | сервер, libFuzzer/Jazzer, ≥ 24 ч в CI-ночь, корпус из золотых векторов |

| Сбои | убийство процесса между отправкой и удалением; потеря ответа; 500/429/413; отключение сети посреди тела | Android instrumentation + mock-сервер |
