# 01. Спецификация Mortris Transport V2 (MTB2)

Статус: черновик для реализации. Эталонный кодировщик и декодер: `04-experiments/wire.py` (`mtb2_encode` / `mtb2_decode`).
Если текст и эталон расходятся, прав эталон, а текст считается ошибкой. Ключевые слова MUST/SHOULD/MAY в смысле RFC 2119.

Обозначения доверия: **[измерено]** воспроизводимо в `04-experiments/`, **[код]** проверено по коду SDK 0.2.0 в этом
репозитории, **[источник]** см. `08-sources.md`, **[оценка]** расчёт, **[гипотеза]**.

## 0. Что меняется относительно V1, коротко

| Аспект | V1 (сейчас) [код] | V2 |
|---|---|---|
| Тело | JSON + gzip `Fastest` | бинарный колоночный кадр MTB2 + zstd с предобученным словарём |
| ID события | UUID v4 текстом на событие | `(install_id, sequence)`; `sequence` уже есть в очереди |
| Контекст устройства | повторяется в каждом событии | таблица контекстов в пачке |
| Схема | ключи-строки в каждом событии | «формы» (shape) прямо в пачке, без внешнего реестра |
| Ответ | JSON со списками UUID (~45 Б/событие) | 4–6 байт: статус + диапазон |
| Политика | отдельный запрос `/v1/client/policy` | эпоха политики в каждом ack, тело только при изменении |
| Состояние между пачками | нет | нет (сознательно, см. 02 и 03) |

Без потерь: декодер V2 восстанавливает тело V1 **байт в байт**, кроме полей `event_id` [измерено:
`test_roundtrip.py`, 21 545 событий + граничные случаи].

## 1. Принципы

1. **Каждый запрос самодостаточен.** Сервер декодирует кадр, зная только версию формата и словарь из фиксированного
   набора. Нет кэша контекстов, нет ссылок на прошлые пачки, нет рассинхронизации по определению.
2. **Схема внутри пачки.** Имена событий и ключей едут строками в таблице строк пачки; словарь zstd делает их почти
   бесплатными. Реестр схем, числовые ID и кодогенерация **не нужны** [измерено: 03-ablation §4, CAS-кэш форм даёт
   −1…+4%].
3. **Упаковка при отправке.** Очередь хранит событие по одному, как сейчас (`payload_json` в SQLite). Кадр собирается
   из строк очереди в момент отправки; при откате на V1 те же строки отправляются старым кодировщиком.
4. **Контекст фиксируется при постановке в очередь.** Уже так [код: `PersistenceEventSerializer` пишет поля
   устройства в `payload_json` при сохранении]. V2 читает контекст из `payload_json`, а не из текущего устройства.

## 2. HTTP

### 2.1 Запрос

```
POST /v2/b HTTP/1.1
Host: <host>
Authorization: Bearer <installation_credential, 43 символа base64url>
Content-Length: <n>

<кадр MTB2>
```

- `Content-Type` и `Content-Encoding` не отправляются: кадр сам описывает кодек (§4). Это сознательно: прокси и
  CDN не должны распаковывать или перекодировать тело. Сервер MUST принимать запрос и с
  `Content-Type: application/octet-stream`.
- Клиент MUST NOT отправлять `Expect: 100-continue`. **[гипотеза]** Mono `HttpWebRequest` под Unity добавляет его к
  POST по умолчанию и ждёт до 350 мс; проверить захватом трафика (07, вопрос Q6). Если подтвердится, отключить и в V1.
- Соединение переиспользуется (keep-alive). HTTP/2 MAY, если стек клиента его поддерживает; HTTP/3 не требуется.
- Размер заголовков запроса: 141 Б в HTTP/1.1, ~10 Б в HTTP/2 после первого запроса [измерено: `results/http.md`].

### 2.2 Ответ

`200 OK`, тело = ack-кадр (§7), заголовки только `Date` и `Content-Length`. Ошибки транспорта:

| HTTP | Смысл | Действие клиента |
|---|---|---|
| 200 | кадр разобран, тело = ack | §7 |
| 400 | кадр не разобран (`BAD_FRAME`) | эту пачку отправить через V1; если и V1 даёт 400, текущее поведение V1 |
| 401 | неверный credential | как V1: `RegisterWithCredentialRecovery`, затем повтор |
| 404 / 405 | V2 не развёрнут | выключить V2 до следующего ответа `/v1/installs/register` или `/v1/client/policy` |
| 409 `install_conflict` | как V1 | как V1 |
| 413 | кадр больше `max_frame` | делить пачку пополам, как V1 |
| 429 / 503 | перегрузка | `Retry-After`, иначе backoff V1 (5 с … 5 мин) |

## 3. Согласование возможностей

V2 включается только по явному разрешению сервера. В ответы `/v1/installs/register` и `/v1/client/policy` добавляется
необязательное поле (старые SDK его игнорируют, `JsonUtility` пропускает неизвестные поля [код]):

```json
"transport": {"v2": {"path": "/v2/b", "dicts": [1], "max_frame": 262144, "max_raw": 2097152, "max_events": 500}}
```

- `dicts`: ID словарей, которые сервер умеет; клиент выбирает наибольший общий. Нет общего → кодек zstd без словаря.
- Возможности кэшируются в метаданных очереди. Ответ без поля `transport` или с `v2: null` выключает V2.
- Глобальный рубильник: сервер выключает V2 полем `transport` в политике, клиент возвращается на V1 без потери
  событий (строки очереди те же).

## 4. Кадр

```
+--------+-----------------+--------------------------------------+
| byte 0 | uvarint dict_id | сжатая полезная нагрузка до конца тела |
+--------+-----------------+--------------------------------------+
byte 0 = (frame_version << 4) | codec      frame_version = 2
codec: 0 = без сжатия, 1 = raw DEFLATE (RFC 1951, без zlib/gzip обёртки),
       2 = Brotli, 3 = zstd (RFC 8878) в формате magicless, без checksum, без content size, без dict ID
dict_id: 0 = без словаря; иначе ID из реестра словарей SDK (§8.3). Для codec 0 MUST быть 0.
```

Пример: `23 01` = версия 2, zstd, словарь 1. Целостность обеспечивает TLS, отдельной контрольной суммы нет.

Рекомендуемые настройки клиента: zstd уровень 19 со словарём 16 КиБ. На пачках 1–3 КиБ это 50–70 мкс на пачку на
Apple M-ядре [измерено: `results/cpu.md`]; на Android-ядре среднего класса ожидается в 3–10 раз медленнее, т.е.
0,2–0,6 мс [оценка, не измерено, 07 Q4]. Если zstd недоступен в сборке, `codec 1` (raw DEFLATE уровня 6) MUST
поддерживаться сервером; он даёт ~41 Б/событие вместо ~22 [измерено].

## 5. Полезная нагрузка (после распаковки)

### 5.1 Примитивы

- `uvarint`: беззнаковый LEB128, не более 10 байт, значение ≤ 2^64−1. Декодер MUST отвергать более длинные.
- `svarint`: ZigZag (`(n << 1) ^ (n >> 63)`) поверх `uvarint`; диапазон int64.
- `str`: `uvarint` длина в байтах + UTF-8. Невалидный UTF-8 MUST отвергаться.
- `uuid16`: 16 байт в порядке RFC 9562 (как `UUID.bytes`; не .NET `Guid.ToByteArray()`, у него другой порядок
  первых трёх полей).
- `f32`, `f64`: IEEE 754 little-endian.
- Индексы таблиц: `uvarint`, MUST быть меньше размера таблицы.

### 5.2 Общая раскладка

```
header | tables | meta | contexts | shapes | column_directory | body
```

### 5.3 header

```
u8      payload_version = 2
uvarint flags            bit0: присутствует origin_install_id; остальные биты MUST быть 0
[uuid16 origin_install_id]   только если bit0
uvarint first_seq        sequence первого события
uvarint n                число событий, 1..max_events
uvarint n_gaps, затем n_gaps пар (uvarint index, uvarint skip)
                         seq[0] = first_seq; seq[i] = seq[i-1] + 1 + skip(i), skip(i) = 0 если i не указан
uvarint base_time_ms     Unix ms события 0 (UTC)
svarint sent_delta_ms    sent_at_client − время последнего события
```

`origin_install_id` отсутствует, когда события созданы под той же установкой, что и credential (обычный случай):
сервер берёт `install_id` из аутентификации. Флаг нужен только после `resetIdentity` (§6.3).

### 5.4 tables

```
uvarint n_strings, затем n_strings × str          (имена, ключи, строковые значения, поля контекста)
uvarint n_uuids,   затем n_uuids × uuid16          (значения-UUID)
uvarint n_hex,     затем n_hex × (uvarint len, len байт)   (значения-hex)
```

Каждое уникальное значение встречается в таблице один раз; порядок = порядок первого использования кодировщиком.
Порядок не влияет на смысл, но эталон задаёт его детерминированно (нужно для тестов «байт в байт»).

### 5.5 meta

```
uvarint project_id (индекс строки), uvarint sdk_name (индекс), uvarint sdk_version (индекс)
```

### 5.6 contexts

```
uvarint n_ctx
каждый: u8 kind (MUST быть 0; 1 зарезервирован под ссылку на кэш, в v2 не используется)
        uuid16 session_id
        6 × uvarint индекс строки: app_version, build_number, platform, os_version, device_class, locale
        svarint timezone_offset_minutes
```

Набор полей контекста фиксирован версией payload. Новое поле контекста = `payload_version` 3; сервер поддерживает все
выпущенные версии навсегда.

### 5.7 shapes

Форма = имя события + упорядоченный список (ключ, тип). Одинаковые формы в пачке описываются один раз.

```
uvarint n_shapes
каждая: u8 kind (MUST быть 0)
        uvarint name (индекс строки)
        uvarint n_fields (≤ 32, лимит валидатора [код])
        n_fields × (uvarint key (индекс строки), u8 type [, uvarint alias_index если type = ALIAS])
```

Теги типов (реестр только дополняется, номера не переиспользуются):

| tag | имя | значение в колонке | откуда в C# [код: `EventValidator`] |
|---:|---|---|---|
| 0 | INT | svarint, режим raw/delta (§5.8) | sbyte, byte, short, ushort, int, uint, long, ulong ≤ 2^63−1 |
| 1 | STR | uvarint индекс строки | string (если не UUID/HEX) |
| 2 | BOOL | 1 байт 0/1 | bool |
| 3 | F32 | 4 байта | float |
| 4 | F64 | 8 байт | double |
| 5 | UUID | uvarint индекс в таблице UUID | string в каноническом виде `8-4-4-4-12`, только строчные |
| 6 | HEX | uvarint индекс в таблице hex | string из чётного числа строчных hex-символов, длина ≥ 16 |
| 7 | NULL | нет данных | null |
| 8 | ALIAS(j) | нет данных: значение = значение поля j той же формы, j < i | авто: дубликат (`wave_attempt_id == attempt_id`) |
| 9 | CTXREF | нет данных: значение = одноимённое поле контекста | авто: `properties.app_version == app_version` |
| 10 | U64 | uvarint | ulong > 2^63−1 |
| 11 | NUMTEXT | uvarint индекс строки с десятичным текстом | decimal (точность и хвостовые нули сохраняются) |

Правила выбора типа кодировщиком:
- UUID и HEX только для строчных строк; `"ABCDEF..."` остаётся STR, иначе регистр потеряется.
- ALIAS ставится, только если равенство выполняется **для всех событий этой формы в пачке**; иначе поле
  кодируется как обычно. CTXREF так же по контексту конкретного события. Это общий механизм для любых игр: игре не
  нужно ничего объявлять, дубликаты исчезают с провода сами.
- Если один ключ имеет разные типы в разных событиях, это разные формы и разные колонки (§5.8).

### 5.8 column_directory и body

Колонка = пара (ключ, тип) по всем формам пачки. Это и есть «общий механизм interaction frames»: `block_id` из
`detail_taken`, `detail_released`, `placement_resolved` лежит в одной колонке подряд, и дельта даёт нули.

```
column_directory:
  uvarint n_columns
  каждая: uvarint key (индекс строки), u8 type, [u8 mode, только для INT: 0 = raw, 1 = delta]
body:
  shape_col : n × uvarint  индекс формы
  ctx_col   : пары (uvarint ctx_index, uvarint run_length), сумма run_length = n
  dt_col    : n × svarint  t[i] − t[i−1], t[−1] = base_time_ms (значит dt[0] = 0)
  el_col    : n × svarint  session_elapsed_ms:
              первое событие контекста в пачке: само значение;
              далее: elapsed[i] − (elapsed[prev] + t[i] − t[prev]), prev = предыдущее событие того же контекста
  затем колонки в порядке column_directory; в каждой значения в порядке событий,
  только для событий, чья форма содержит это поле с типом, несущим данные (не ALIAS/CTXREF/NULL)
  INT mode 1: v[k] = v[k−1] + d[k], v[−1] = 0
```

Колонки и порядок их значений определяются формами, поэтому длины колонок не передаются. Кодировщик выбирает режим
INT по меньшему размеру. Порядок колонок = порядок первого появления (ключ, тип) при обходе событий.

`session_elapsed_ms` не выводится из времени: это остаток относительно стенных часов, обычно 0 или ±1 [измерено на
синтетике; на реальных данных остаток может быть больше из-за пауз, это стоит байтов, но не точности].

## 6. Идентичность и идемпотентность

### 6.1 Ключ события

`event_key = (origin_install_id, sequence)`. `sequence` выдаётся в той же SQLite-транзакции, что и вставка, из
`metadata.next_sequence` и монотонно растёт на установку [код: `AnalyticsQueue.java`]. Для хранилищ, которым нужен
`event_id`, сервер выводит его детерминированно:
`event_id = UUIDv5(NS_MORTRIS, install_id_bytes || uint64_be(sequence))`. Повтор даёт тот же `event_id`.

### 6.2 Дедупликация на сервере

Сервер хранит на установку множество принятых интервалов `[a, b]` (обычно один интервал, так как пачки идут по
порядку). Событие с `sequence` внутри принятого интервала = дубликат, подтверждается и не пишется повторно.
Дополнительно сервер SHOULD хранить 32-битный отпечаток канонического события (CRC32C тела V1 без `event_id`) и при
совпадении ключа с другим отпечатком отвечать `IDENTITY_CONFLICT` (§7), чтобы не потерять события молча при
повторном использовании `sequence` (восстановление данных приложения, баг SDK).

Защита от повторного использования уже есть: база очереди лежит в `getNoBackupFilesDir()` и не попадает в Auto Backup
[код]. После `clearAllPendingEvents` счётчик продолжается [код, тесты #0014/#0015].

### 6.3 `resetIdentity` (обязательное изменение SDK)

Сейчас `resetIdentity` переписывает `install_id` всех ожидающих событий на новый [код]. Под V1 это безопасно только
если сервер дедуплицирует по `event_id` глобально. Под V2 событие, принятое сервером под старой установкой, но не
подтверждённое (потерян ответ), после сброса придёт под новой установкой с тем же `sequence` и не будет распознано как
дубликат. Правило V2: строки очереди хранят `origin_install_id` (установку, под которой выдан `sequence`), и при сбросе
его не меняют. Кадр с событиями старой установки ставит `flags.bit0` и несёт `origin_install_id`; сервер принимает его,
если новая установка зарегистрирована как преемник старой (регистрация передаёт `previous_install_id`). Пачка не
смешивает события разных `origin_install_id`.

### 6.4 Подтверждение диапазонами

Ack подтверждает весь кадр одним статусом. Частичный результат перечисляет только исключения (§7). Клиент удаляет из
очереди всё, что подтверждено, по `sequence` (`DELETE ... WHERE sequence BETWEEN a AND b AND origin_install_id = ?`).

## 7. Ack-кадр (тело ответа)

```
u8      status
svarint server_time_delta_ms   server_time − sent_at_client (сервер знает оба значения)
uvarint policy_epoch
[policy]                       только если bit7 status: uvarint mode, uvarint next_check_seconds, u8 discard_pending
[exceptions]                   только при status PARTIAL:
        uvarint n_retry,   затем n_retry × (uvarint index_from, uvarint count)    НЕ сохранено, повторить
        uvarint n_reject,  затем n_reject × (uvarint index, u8 code)             отвергнуто навсегда, удалить
```

`status` (биты 0–6): 0 `OK` (весь кадр сохранён или был дубликатом), 1 `PARTIAL`, 2 `RETRY_LATER` (ничего не
сохранено), 3 `DICT_UNKNOWN` (повторить с `dict_id` 0), 4 `IDENTITY_CONFLICT` (вызвать `resetIdentity`, события не
удалять), 5 `V2_DISABLED` (повторить через V1). Бит 7: в ответе есть тело политики.

Семантика повторяет V1 [код: `ParseAcknowledgement`]: принятые, дубликаты и отвергнутые удаляются; всё остальное
остаётся в очереди. Обычный ответ `OK` = 4–6 байт против ~1 400 байт JSON со списком UUID у V1 на пачке из 30 событий
[измерено: `results/http.md`].

Политика: клиент хранит `policy_epoch`. Сервер присылает тело политики (бит 7) только если эпоха клиента устарела;
периодический `/v1/client/policy` больше не нужен, пока идёт трафик V2. Регистрация остаётся отдельным запросом (раз на
установку).

## 8. Версионирование и словари

### 8.1 Уровни версий

| Что | Где | Правило |
|---|---|---|
| Кадр | старшие 4 бита byte 0 | 2; новая версия = новый формат кадра |
| Payload | первый байт payload | 2; новые фиксированные поля = новая версия |
| Тег типа | §5.7 | только добавление, номера навсегда |
| Словарь | `dict_id` | только добавление, содержимое по ID неизменно навсегда |
| Схема игры | нет | не существует как отдельная сущность: формы едут в пачке |

### 8.2 Неизвестное у сервера

Неизвестная версия кадра/payload или тег → HTTP 400 `BAD_FRAME`; клиент отправляет ту же пачку через V1. Неизвестный
`dict_id` → `DICT_UNKNOWN`; клиент повторяет без словаря. Событие не теряется ни в одном из случаев.

### 8.3 Словари

- Словарь обучается (`zstd --train`, 16 КиБ) на **реальных** кадрах MTB2, собранных с согласия на тестовых сборках
  или из V1-трафика, перекодированного на сервере.
- Словарь вшивается в SDK (16 КиБ в бинаре) и хранится на сервере навсегда. Не скачивается во время работы: так нет
  нового запроса, нового состояния и вектора атаки.
- Новый словарь = новый `dict_id` в новой версии SDK. Старые SDK продолжают со своим. Словарь, обученный на данных
  одной игры, работает для другой хуже, но не ломается (zstd просто находит меньше совпадений).
- Пересобирать словарь стоит, когда доля `bytes_without_dict / bytes_with_dict` на сервере заметно падает (метрика
  считается сервером по выборке кадров).

## 9. Лимиты декодера (MUST)

| Лимит | Значение | Зачем |
|---|---|---|
| Размер кадра | `max_frame` 256 КиБ | 413 до распаковки |
| Распакованный размер | `max_raw` 2 МиБ, распаковка потоком с остановкой | decompression bomb |
| Коэффициент сжатия | отказ при raw/frame > 200 | бомба внутри лимита |
| Окно zstd | ≤ 8 МиБ (`ZSTD_d_windowLogMax` = 23) | память на запрос |
| `n` событий | ≤ `max_events` (500) | память |
| Таблицы, формы, колонки | каждая ≤ 65 536, полей в форме ≤ 32 | переполнение аллокаций |
| uvarint | ≤ 10 байт | бесконечный цикл |
| Любой индекс | < размера таблицы | выход за границу |
| Остаток байт после body | MUST быть 0 | подмена/склейка |

После декодирования события проходят ту же валидацию, что V1 (имена, лимиты размеров, 32 свойства, 8 КиБ свойств).

## 10. Сквозной пример (20 событий)

Сгенерировано `make_example.py`; полный hexdump всех секций в `04-experiments/results/example.md`, файлы
`example_batch_v1.json`, `example_payload.bin`, `example_frame.bin`, `example_dict.bin` лежат рядом. Проверка
(из `04-experiments`, magicless-кадр CLI `zstd` не читает, поэтому через библиотеку):

```python
import zstandard as z, wire
f = open("results/example_frame.bin", "rb").read()
d = z.ZstdCompressionDict(open("results/example_dict.bin", "rb").read())
raw = z.ZstdDecompressor(dict_data=d, format=z.FORMAT_ZSTD1_MAGICLESS).decompress(f[2:], max_output_size=2 << 20)
meta, events = wire.mtb2_decode(raw)   # raw == example_payload.bin, 20 событий
```

События: `session_start, attempt_started, wave_started`, затем 4 полных цикла
`detail_taken → detail_released → placement_resolved → state_checkpoint` и ещё один `detail_taken`.

| Стадия | Байт | Б/событие |
|---|---:|---:|
| V1 JSON | 16 397 | 819,9 |
| V1 JSON gzip-1 (сейчас) | 2 502 | 125,1 |
| V1 JSON gzip-6 | 2 157 | 107,8 |
| MTB2 payload | 1 483 | 74,2 |
| MTB2 zstd-19 без словаря | 1 073 | 53,6 |
| **MTB2 кадр: 2 Б префикс + zstd-19 со словарём 16 КиБ** | **546** | **27,3** |

Сокращение тела запроса на этой пачке: 2 502 → 546 байт, **−78%** [измерено]. Ответ: ~1 400 → ~5 байт.

Секции payload: header 30, tables 846, contexts 26, shapes 183, column_directory 72, body 326 байт.

Разбор header (первые 30 байт):

```
02                                        payload_version 2
01                                        flags: origin_install_id присутствует (в примере для наглядности)
cd 61 3e 30 d8 f1 4a df 91 b7 58 4a 22 65 b1 f5   install_id (uuid16)
c1 02                                     first_seq = 321
14                                        n = 20
00                                        n_gaps = 0 (sequence 321..340 подряд)
f3 e2 b7 b5 8e 34                         base_time_ms = 1 790 576 554 355 (2026-09-28T06:22:34.355Z)
f4 03                                     sent_delta = zigzag 500 -> +250 мс
```

Контекст (26 байт): `01` (n_ctx) `00` (kind) + 16 байт session_id + `07 08 09 0a 0b 0c` (индексы строк
app_version … locale) + `f0 01` (zigzag 240 = +120 минут).

Первая форма: `00 0d 03 0e 01 0f 02 10 09` = kind 0, имя = строка 13 (`session_start`), 3 поля:
`launch_type`:STR, `first_session`:BOOL, `app_version`:CTXREF (дубликат контекста, 0 байт на событие).
Вторая форма начинается `00 11 08 10 09 12 05 13 08 01 ...` = `attempt_started`, 8 полей: `app_version`:CTXREF,
`attempt_id`:UUID, `wave_attempt_id`:ALIAS(1) (дубликат `attempt_id`, 0 байт) и т.д.

Кадр на проводе начинается `23 01` (v2, zstd, словарь 1), далее 544 байта zstd.

## 11. Чего в V2 сознательно нет

- Состояния между пачками (кэши контекстов/форм, ссылки на прошлую пачку, потоковый компрессор на соединение):
  выигрыш 2–6% при цене рассинхронизации [измерено: `results/stateful_*.md`].
- Реестра схем и числовых ID: словарь даёт то же без синхронизации клиента и сервера [измерено: 03 §1, §4].
- Удаления «вычислимых» полей (например `placed_state_hash`): это игровая логика сервера, не транспорт. Механизм
  описан в 02 как агрессивный вариант, в протокол не входит.
- HTTP/3 и 0-RTT: размер выигрывают мало, а 0-RTT допускает повтор запроса злоумышленником [источник: RFC 8446 §8];
  дедупликация по `(install_id, sequence)` это бы выдержала, но выигрыш не стоит второго стека на Unity/Android.

## 12. Безопасность и приватность

**Аутентификация без раздувания.** Остаётся `Authorization: Bearer <credential>` (32 случайных байта, 43 символа
[код]). В HTTP/1.1 это ~58 Б на запрос (~2 Б/событие при пачке 30), в HTTP/2 после первого запроса ~1 Б (HPACK
индексирует значение) [измерено: `results/http.md`]. Подпись тела (HMAC) не добавляется: целостность и
конфиденциальность даёт TLS, а ключ подписи жил бы в том же приложении, что и credential, и не защитил бы от
модифицированного клиента.

**Повтор и подмена.**
- Перехваченный запрос без взлома TLS повторить нельзя. Повтор своим же клиентом безвреден: `(install_id, sequence)`
  идемпотентен (§6.2).
- Модифицированный клиент может слать мусор от своей установки. Защиты сервера: лимит событий на установку в сутки,
  лимит частоты запросов на установку и IP, отказ при скачке `sequence` больше чем на 10^6 за кадр, обычная
  валидация V1 после декодирования. Это не хуже V1.
- 0-RTT не используется (повторяемость на уровне TLS [источник: RFC 8446 §8]).

**Декодер.** Лимиты §9 обязательны; распаковка потоковая с ограничением выхода до разбора; декодер на сервере
пишется на memory-safe языке или проходит fuzz (06). Ответ сервера клиент разбирает с теми же правилами (ack
фиксированной формы, n_retry/n_reject ≤ n кадра).

**Приватность.**
- V2 переносит **ровно те же поля**, что V1. Тест эквивалентности (§0) это и фиксирует: новое поле на проводе
  ломает тест. Любое новое поле контекста = новая `payload_version` и отдельное ревью приватности. Меньший размер
  не основание собирать больше.
- `install_id`, `session_id`, `os_version`, `device_class`, `locale` вместе это псевдонимные персональные данные.
  Хранение идентификатора на устройстве и чтение сведений об устройстве попадают под ст. 5(3) ePrivacy в трактовке
  EDPB Guidelines 2/2023 [источник]; для аналитики это обычно означает согласие в ЕС. Транспорт этого не меняет: SDK
  уже имеет режим `DisableCollection` из политики [код]; решение о согласии остаётся за игрой и юристами (это не
  юридическая консультация).
- **Словарь сжатия не должен содержать пользовательских данных.** Словарь вшивается в каждую сборку SDK и виден
  любому. Если обучить его на реальном трафике, в него попадут UUID, хеши, локали, модели устройств, свободный текст
  из свойств. Правило: обучать на кадрах, где все значения UUID/HEX/STR, не входящие в белый список (имена
  событий, ключи, enum-значения, версии), заменены синтетическими; перед выпуском сканировать словарь на UUID/hex/
  e-mail/длинные цифровые строки.
- Удаление данных: запрос на удаление по `install_id` удаляет и интервалы дедупликации и отпечатки (§6.2).
- Google Play Data safety: декларация не меняется (те же данные, шифрование в пути сохраняется) [источник].
