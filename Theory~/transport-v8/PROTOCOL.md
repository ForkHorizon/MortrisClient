# Протокол V8: зафиксированные решения (черновик)

Статус: **черновик, обсуждение идёт**. Здесь только то, что уже решено в разговоре с владельцем проекта, и то, что осталось открытым. Сервер и клиент будут переписаны под этот протокол; совместимость со старыми версиями приложения сервер поддерживает отдельно (старые клиенты шлют UUID вместо короткого номера).

Основание: замеры на реальных данных и записанный обмен приложения с сервером (`profiling-run~/work/capture/traffic.jsonl`, описание в `Theory~/V7-real-example-attempt-closed.md`, сравнение V1/V7 в `Theory~/V1-vs-V7-how-events-travel.md`).

Принцип: **уменьшать то, что повторяется в каждом запросе, а не то, что происходит раз за жизнь установки.**

---

## 1. Что не устраивает в V7 (замерено)

| Что | Сейчас, байт | Комментарий |
|---|---:|---|
| Заголовки одного пакета | 410 | при теле пакета из одного события в 135 байт |
| Ответ сервера на пакет | 210 (тело) | клиент читает из него 4 поля |
| Запросы до первого пакета при обычном запуске | 966 + 290 ответ | синхронизация и загрузка алиасов |
| Первая установка, загрузка каталога и словаря | 28 423 | без сжатия |
| Идентификатор установки | 36 символов в каждом запросе | UUID |

## 2. Принятые решения

### D1. Идентификатор установки выдаёт сервер

- Номер: **один общий счётчик на все проекты**, запись в основании 62 (`0-9a-zA-Z`), **переменной длины** (первые установки получают 1–2 символа, дальше длина растёт сама; 4 символа покрывают около 14,8 млн установок, 5 символов около 916 млн).
- Префикс (`i43` и т. п.) не нужен.
- Общий счётчик нужен потому, что в заголовках больше нет `project`: номер сам определяет проект.

### D2. Проверка личности: ключ, выводимый из главного ключа сервера

- На сервере один секрет `masterKey` (с версией `kv`). Шифровать данные не нужно (это делает HTTPS), нужна **проверка личности**.
- Ключ установки: `K = первые 8 байт от HMAC-SHA256(masterKey[kv], "mortris-install-v1" ‖ id)`, в записи base64url получается **11 символов** (64 бита).
- Токен: `<id>.<kv><K>` (версия ключа один символ). Передаётся единственным заголовком: `Authorization: Bearer <id>.<kv><K>` (около 40 байт вместо 164).
- Сервер ничего не хранит на установку ради проверки, он пересчитывает `K`.
- Отзыв: чёрный список номеров. Смена главного ключа: новая версия `kv`, старые токены принимаются, пока версия не выведена из обращения.
- 64 бита: сознательный компромисс (RFC 2104 советует не менее 80). Допустимо, потому что угадывание возможно только онлайн, сервер ограничивает частоту, а ущерб от удачной попытки ограничен поддельными событиями одной установки.
- Заголовок остаётся стандартным `Authorization` (прокси и логи его скрывают, клиентская библиотека .NET не пересылает его при редиректе на другой хост). Слово `Bearer` не убираем.

### D3. Регистрация сливается с первой синхронизацией («hello»)

Решение принято исполнителем по поручению владельца.

- Первый запрос без токена: `POST /v2/hello`. Тело: `nonce` (16 случайных байт телефона, base64url), `project`, `app_version`, `build`, `platform`, `sdk`, плюс поля синхронизации (`stream_base`, `high_water`, `dropped`).
- Ответ: `token`, `epoch`, `ack_through`, `missing`, `alias_epoch`, идентификаторы каталога и словаря, `p` (версия политики).
- **Идемпотентность:** сервер хранит соответствие `nonce → id`. Повтор после потерянного ответа возвращает тот же номер и ту же эпоху. Строка живёт до первого запроса с токеном плюс запас (срок хранения: открытый вопрос).
- Телефон ничего не генерирует для идентификации, кроме `nonce`.
- Защита от массовых регистраций: ограничение по IP и по проекту (как сейчас).

### D4. Заголовки пакета

Остаются: `Authorization`, `Content-Type`, `Content-Length`, `Host` (стандартные).

| Было | Решение |
|---|---|
| `X-Mortris-Project` (40 Б) | убрать: проект следует из номера установки |
| `X-Mortris-Install` (57 Б) | убрать: в токене |
| `X-Mortris-Epoch` (20 Б) | перенести в заголовок кадра (varint, 1–2 байта) |
| `X-Mortris-Sent-At` (45 Б) | перенести в заголовок кадра (varint, 6 байт). Сервер по нему считает `clock_skew_ms` |
| `X-Mortris-Sdk` (36 Б) | убрать из пакета: имя и версия SDK едут в строке таблицы алиасов (девятое и десятое поля) |

Итого заголовки пакета: **410 → около 150 байт**, кадр +9 байт.

### D5. Ответ на пакет

Минимальный: `{"ack":N}`. Остальные поля добавляются только когда не пусты:

- `"rejected":[...]` (отклонённые события, как сейчас);
- `"missing":[[a,b],...]`;
- `"p":N` (версия политики). Если `p` отличается от запомненной клиентом, клиент один раз запрашивает политику отдельным запросом (`GET /v2/policy`).

Клиент не читает `server_time`, `accepted_count`, `duplicate_count` на пути пакета. Ответ: **210 → около 10 байт**.

Ошибки и просьбы синхронизироваться: коды `409` с полем `reason` (`need_sync`, `alias_missing`, `rollback`, `catalog_changed`, `unknown_stream`). Список окончательно утверждается при проектировании кадра.

### D6. Обычный запуск: один запрос вместо трёх

- Телефон сразу отправляет первый пакет. Отдельная `POST /v2/streams/sync` и `PUT /v2/streams/aliases` не нужны.
- В кадр добавляются необязательные разделы (флаги в заголовке): **таблица алиасов** (бинарно, около 130 байт вместо 371 JSON) и **границы потока** (`stream_base`, диапазоны пропусков, если изменились).
- Сервер при несоответствии отвечает 409 с причиной, телефон делает hello/синхронизацию и повторяет.
- Экономия около 1,2 КБ и два лишних обмена на каждый запуск.
- **Обязательное условие безопасности:** `stream_base` едет в кадре **всегда**. Это сохраняет защиту от отката счётчика (новые события с уже использованными номерами сервер иначе молча посчитал бы дубликатами): сервер видит чужой поток и отвечает `409 rollback`.

### D7. Каталог и словарь

- Сервер отдаёт их с `Content-Encoding: gzip`: **28 423 → 10 336 байт** (каталог 12 039 → 1 251, словарь 16 384 → 9 085).
- Опционально вшивать в сборку игры: тогда скачивание нужно только при смене номера.

### D8. Соединение

Проверено: один общий `HttpClient` держит **одно TCP-соединение** на 26 запросов за 95 секунд, переоткрытий не было. Ничего менять не нужно. Требование к серверу и балансировщику: ожидание простоя (`keep-alive`) **не менее 60 секунд**.

## 4. Инварианты, которые нельзя нарушить (из аудита очереди и протокола V7)

1. Потеря события недопустима: удалять из очереди только строки до `ack_through`.
2. Откат счётчика обнаруживается (D6, `stream_base` в каждом кадре).
3. Повторная отправка не создаёт дубликатов (идентификатор события выводится из установки, эпохи и номера).
4. Регистрация идемпотентна (D3).
5. Пропущенные номера (удалённые по сроку, лимиту или очистке) объявляются серверу как закрытые.
6. Любой сбой V7 уходит в запасной путь без потери данных.

Тесты, которые обязательно писать: откат очереди, потеря таблицы алиасов на сервере, повтор hello после потерянного ответа, смена главного ключа, отзыв установки, потерянный ответ на пакет, оба порядка гонки «первый пакет и hello».
