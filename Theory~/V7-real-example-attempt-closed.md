# V7 на живом примере: что реально уходит и приходит

Все данные ниже записаны с настоящего прогона: приложение на эмуляторе Android (IL2CPP), V7 включён, между приложением и локальным сервером стоял прокси, который записал каждый запрос и ответ байт в байт (кроме заголовка `Authorization`, он вырезан). Событие взято из реальной выгрузки игры. Источник записи: `profiling-run~/work/capture/traffic.jsonl`.

## 0. Главное: событие больше не едет как JSON

В V1 событие уходило текстом JSON. В V7 **событие едет бинарным пакетом** (`POST /v2/events/packet`, тип `application/vnd.mortris.m7`). JSON остался только в служебных запросах: регистрация, синхронизация потока, таблица алиасов. А «JSON события», который видит сервер, получается **после распаковки** пакета. Ниже все четыре вида по порядку.

Реальный порядок запросов этого прогона (6 событий, 11 запросов):

| № | Запрос | Тело, байт | Ответ, байт | Что делает |
|---:|---|---:|---:|---|
| 0 | `POST /v1/installs/register` | 296 | 163 | регистрация установки (один раз) |
| 1 | `POST /v2/streams/sync` | 161 | 198 | «вот мой поток, что у тебя уже есть?» |
| 2 | `GET /v2/assets/catalog/81c8a203dc3d77b4` | — | 12 039 | каталог (один раз, потом из кеша) |
| 3 | `GET /v2/assets/dictionary/933536cf9fae4ac0` | — | 16 384 | словарь zstd (один раз, потом из кеша) |
| 4 | `PUT /v2/streams/aliases` | 371 | 92 | таблица контекста (раз за запуск) |
| 5–10 | `POST /v2/events/packet` ×6 | 50 / 135 / 177 / 129 / 190 / 211 | 210 | сами события |

(В этом прогоне события шли по одному, поэтому пакетов шесть; в обычной работе в пакете до 100 событий.)

## 1. Синхронизация потока (JSON, один раз)

Запрос:

```json
{"schema_version":2,
 "project_id":"puzzle_gravity_test",
 "install_id":"b17278d1-b94a-4452-bab7-01a6e21884fa",
 "epoch":0,
 "stream_base":1,
 "high_water":1,
 "dropped":[]}
```

Ответ сервера:

```json
{"server_time":"2026-10-25T22:34:52.643Z",
 "epoch":1,
 "ack_through":0,
 "missing":[[1,1]],
 "alias_epoch":"",
 "alias_count":0,
 "assets":{"catalog_id":"81c8a203dc3d77b4","dictionary_id":"933536cf9fae4ac0"}}
```

Что значит:

| Поле | Смысл |
|---|---|
| `schema_version: 2` | версия протокола V7 |
| `project_id` | проект; по нему сервер выбирает каталог |
| `install_id` | идентификатор установки, одинаковый на все события этого телефона |
| `epoch` (запрос) | `0` = «у меня ещё нет эпохи потока, выдай». Эпоха — номер поколения нумерации событий. Если очередь телефона откатилась (например, восстановили старую копию), сервер выдаст новую эпоху |
| `stream_base: 1` | с какого номера начинается мой поток |
| `high_water: 1` | самый большой номер, который у меня уже есть |
| `dropped: []` | диапазоны номеров, которые я удалил и никогда не пришлю (устарели, очищены). Пусто = дыр нет |
| `epoch: 1` (ответ) | выданная эпоха |
| `ack_through: 0` | «подтверждено всё до номера 0», то есть пока ничего |
| `missing: [[1,1]]` | «мне не хватает номеров с 1 по 1»: пришли |
| `alias_epoch: ""`, `alias_count: 0` | таблицы алиасов у сервера пока нет |
| `assets` | номера каталога и словаря, которыми надо пользоваться. Номер = отпечаток содержимого; если он совпадает с тем, что в кеше телефона, скачивать заново не нужно |

## 2. Таблица алиасов (JSON, раз за запуск приложения)

Запрос (`PUT /v2/streams/aliases`):

```json
{"schema_version":2,
 "project_id":"puzzle_gravity_test",
 "install_id":"b17278d1-b94a-4452-bab7-01a6e21884fa",
 "epoch":1,
 "alias_epoch":"815945aa81e1da9e",
 "start":0,
 "records":[["b17278d1-b94a-4452-bab7-01a6e21884fa",
             "5161dc6e-bd50-40eb-bfef-3b6b7cc0a62b",
             "1.1.14","prof-1","android",
             "Android OS 15 / API-35 (AE3A.240806.043/12960925)",
             "Google sdk_gphone64_arm64","en-US",60]]}
```

Ответ: `{"server_time":"...","alias_epoch":"815945aa81e1da9e","alias_count":1}`

Каждая строка `records` — один «контекст», на который потом ссылаются события числом. Порядок значений в строке:

| № | Значение в примере | Смысл |
|---:|---|---|
| 0 | `b17278d1-…` | установка (кто отправляет) |
| 1 | `5161dc6e-…` | сессия игры |
| 2 | `1.1.14` | версия приложения |
| 3 | `prof-1` | номер сборки |
| 4 | `android` | платформа |
| 5 | `Android OS 15 / API-35 (…)` | версия ОС |
| 6 | `Google sdk_gphone64_arm64` | модель устройства |
| 7 | `en-US` | язык |
| 8 | `60` | сдвиг часового пояса в минутах |

`alias_epoch` — отпечаток этой таблицы. Он стоит и в заголовке каждого пакета, так что сервер сразу видит, по какой таблице расшифровывать. `start: 0` — «записи с номера 0»: если контекст меняется (новая сессия), добавляются следующие строки, а прежние не пересылаются.

Здесь 371 байт один раз за запуск, после чего **ни одно событие не повторяет эти 9 значений**. В V1 те же значения (кроме `install_id`) стояли в каждом событии и весили около 220 байт на событие.

## 3. Само событие: пакет, который уходит по сети

Событие игры: `attempt_closed` (попытка закрыта), порядковый номер 2. Пакет весит **135 байт**.

Заголовки HTTP (кроме `Authorization`):

```
X-Mortris-Project: puzzle_gravity_test
X-Mortris-Install: b17278d1-b94a-4452-bab7-01a6e21884fa
X-Mortris-Epoch: 1
X-Mortris-Sent-At: 2026-10-25T22:34:52.305Z
X-Mortris-Sdk: mortris-unity/0.2.0
Content-Type: application/vnd.mortris.m7
Content-Length: 135
```

Тело пакета целиком (шестнадцатеричная запись, по байту):

```
4d 37 06 01 81 c8 a2 03 dc 3d 77 b4 81 59 45 aa
81 e1 da 9e 93 35 36 cf 9f ae 4a c0 01 96 01 28
b5 2f fd 23 47 d5 c1 39 96 bd 02 00 53 04 0f 78
f7 ff 9f c8 11 0b 43 d6 13 10 34 ee b2 a0 78 11
53 0e c3 71 e3 fc 73 ef be e6 ff df 44 1d 54 0b
a0 b8 c9 35 47 2d 4a 76 82 d0 75 6b f7 ff bf fb
4f 95 9f 86 f8 a4 6f f2 ef f1 0f 07 fc 22 29 34
27 74 28 46 67 ae 5c c8 fd c9 f4 f4 bc e3 bd ae
2b 51 21 21 c0 09 2c
```

Разбор:

| Байты | Значение | Смысл |
|---|---|---|
| `4d 37` | `M7` | признак формата |
| `06` | флаги | включены «модель чисел» и «модель строк» (способы упаковки) |
| `01` | сжатие | `1` = тело сжато zstd |
| `81 c8 a2 03 dc 3d 77 b4` | `81c8a203dc3d77b4` | номер каталога (совпадает с `catalog_id` из синхронизации) |
| `81 59 45 aa 81 e1 da 9e` | `815945aa81e1da9e` | номер таблицы алиасов (совпадает с `alias_epoch`) |
| `93 35 36 cf 9f ae 4a c0` | `933536cf9fae4ac0` | номер словаря (совпадает с `dictionary_id`) |
| `01` | 1 | событий в пакете |
| `96 01` | 150 | размер тела **до** сжатия |
| `28 b5 2f fd … ` (100 байт) | zstd-кадр | сжатое тело |
| `21 c0 09 2c` | CRC32 | контрольная сумма: ловит битые данные |

Что внутри тела после распаковки (150 байт). Первые пять значений проверены вручную, они совпадают с событием:

```
00 04              номер события: 2 (число записано «зигзагом»: 2 → 4)
00 a2 c0 9e d3 ae 68   время: 1792967692305 мс (Unix-время; ×2 в записи)
00 c4 2e           прошедшее время сессии: 2978 мс
00 06              форма (shape) события: № 3 = attempt_closed
00 00              строка таблицы алиасов № 0 (контекст)
...                дальше колонки свойств
```

Дальше идут свойства. Видно, что UUID записаны как **16 сырых байт** (`f0 37 da 56 38 c2 48 b8 81 c0 8a 1a 7d 39 92 76` — это `f037da56-38c2-48b8-81c0-8a1a7d399276`, 16 байт вместо 36 символов), а строки — как длина и UTF-8 (`06 70 6c 61 79 65 72` = «player», `0d 77 61 76 65 5f …` = «wave_advanced»).

Важное: в пакете **нет** ни названия события, ни названий 15 полей, ни `event_id`, ни `session_id`, ни версий и устройства. Всё это сервер знает из каталога, таблицы алиасов и номера события.

Ответ сервера на пакет:

```json
{"server_time":"2026-10-25T22:34:52.721Z",
 "accepted_count":1,
 "duplicate_count":0,
 "rejected":[],
 "ack_through":2,
 "missing":[],
 "client_policy":{"mode":"active","next_check_seconds":21600,"discard_pending":false}}
```

| Поле | Смысл |
|---|---|
| `accepted_count: 1` | принято и сохранено 1 событие |
| `duplicate_count: 0` | уже были у сервера: 0 (повторная отправка не создаёт дубль) |
| `rejected: []` | отклонённые события (неверная форма и т. п.); отклонённые считаются окончательно закрытыми |
| `ack_through: 2` | **получено всё до номера 2 включительно**: по этому полю телефон удаляет события из очереди |
| `missing: []` | пропусков нет |
| `client_policy` | команды сервера клиенту: `active` = собирать как обычно; `next_check_seconds` = когда снова спросить; `discard_pending: false` = очередь не сбрасывать |

## 4. Что видит сервер после распаковки

Сервер, получив пакет, собирает событие обратно из каталога, таблицы алиасов и тела (так его восстанавливает независимый декодер, проверка прошла):

```json
{
  "sequence": 2,
  "ts": 1792967692305,
  "session_elapsed_ms": 2978,
  "name": "attempt_closed",
  "session_id": "5161dc6e-bd50-40eb-bfef-3b6b7cc0a62b",
  "app_version": "1.1.14",
  "build_number": "prof-1",
  "platform": "android",
  "os_version": "Android OS 15 / API-35 (AE3A.240806.043/12960925)",
  "device_class": "Google sdk_gphone64_arm64",
  "locale": "en-US",
  "timezone_offset_minutes": 60,
  "properties": {
    "active_elapsed_ms": 3,
    "app_version": "1.1.14",
    "attempt_event_index": 1,
    "attempt_id": "f037da56-38c2-48b8-81c0-8a1a7d399276",
    "city_id": 7,
    "close_reason": "wave_advanced",
    "house_event_index": 330,
    "house_id": 9,
    "house_run_id": "974f31fb-f3d5-4794-8d70-d3476746b81e",
    "origin": "player",
    "placed_block_count": 0,
    "progress_origin": "natural",
    "schema_version": 3,
    "wave_attempt_id": "f037da56-38c2-48b8-81c0-8a1a7d399276",
    "wave_index": 2
  }
}
```

Откуда взялось каждое поле:

| Поле | Откуда сервер его взял |
|---|---|
| `sequence: 2` | колонка «номер» в теле пакета |
| `ts` | колонка «время» в теле (мс, UTC) |
| `session_elapsed_ms: 2978` | колонка «прошедшее время сессии» |
| `name: "attempt_closed"` | из номера формы (3) по каталогу |
| `session_id`, `app_version`, `build_number`, `platform`, `os_version`, `device_class`, `locale`, `timezone_offset_minutes` | из таблицы алиасов, строка № 0 |
| `properties.*` | колонки тела; **имена и порядок полей** из каталога, **типы** тоже оттуда (целое, строка, UUID…) |

Смысл свойств игры:

| Свойство | Значение | Что это |
|---|---|---|
| `origin` | `player` | действие совершил игрок (не автоматика) |
| `city_id`, `house_id` | 7, 9 | где играл |
| `attempt_id` | `f037da56-…` | идентификатор попытки |
| `wave_index` | 2 | номер волны |
| `close_reason` | `wave_advanced` | почему попытка закрыта: перешли на следующую волну |
| `house_run_id` | `974f31fb-…` | идентификатор прохождения дома |
| `schema_version` | 3 | версия схемы событий игры |
| `progress_origin` | `natural` | прогресс естественный (не загруженный) |
| `wave_attempt_id` | `f037da56-…` | идентификатор попытки волны; здесь совпадает с `attempt_id` |
| `active_elapsed_ms` | 3 | активное время попытки |
| `house_event_index` | 330 | порядковый номер события внутри прохождения дома |
| `placed_block_count` | 0 | сколько блоков поставлено |
| `attempt_event_index` | 1 | порядковый номер события внутри попытки |
| `app_version` | `1.1.14` | версия приложения (поле игры, не путать с контекстом устройства) |

## 5. Как оно лежит в базе сервера

Запись в таблице `events` (настоящая строка из базы этого прогона):

```json
{
  "event_id": "32601ca8-0f99-4002-a309-4dea56697bc3",
  "project_id": "puzzle_gravity_test",
  "install_id": "b17278d1-b94a-4452-bab7-01a6e21884fa",
  "sequence": 2,
  "event_kind": "product",
  "name": "attempt_closed",
  "session_id": "5161dc6e-bd50-40eb-bfef-3b6b7cc0a62b",
  "occurred_at_client": "2026-10-25T23:34:52.305+01:00",
  "sent_at_client": "2026-10-25T23:34:52.305+01:00",
  "received_at": "2026-10-25T23:34:52.720334+01:00",
  "effective_at": "2026-10-25T23:34:52.305+01:00",
  "time_quality": "client",
  "clock_skew_ms": 415,
  "session_elapsed_ms": 2978,
  "app_version": "1.1.14", "build_number": "prof-1", "platform": "android",
  "os_version": "Android OS 15 / API-35 (…)", "device_class": "Google sdk_gphone64_arm64",
  "locale": "en-US", "timezone_offset_minutes": 60,
  "properties": { "…те же 15 свойств…" }
}
```

Что добавил сервер от себя, а не получил от телефона:

| Поле | Смысл |
|---|---|
| `event_id` | идентификатор события: **вычислен сервером** из (установка, эпоха, номер), телефон его не присылал |
| `event_kind` | `product` (событие игры) или `system` (служебное, как `sys_session_start`) |
| `received_at` | когда сервер получил |
| `sent_at_client` | когда клиент отправил (из заголовка `X-Mortris-Sent-At`) |
| `clock_skew_ms: 415` | разница часов телефона и сервера (оценка) |
| `time_quality: client` | время события берётся по часам клиента |
| `effective_at` | время, по которому событие учитывается в аналитике |

(Времена показаны с поясом `+01:00`, а в пакете хранится UTC; это одни и те же моменты.)

## 6. Сколько это весило

Тот же `attempt_closed`, одно событие в одном запросе:

| Вид | Байт |
|---|---:|
| V1: JSON события | 866 |
| V1: запрос целиком (с конвертом) до gzip | 1078 |
| V1: запрос после gzip | 631 |
| **V7: пакет** | **135** |

Одиночное событие в V7 в 4,7 раза меньше, чем в V1 после gzip. Когда события идут пачкой по 100 штук, разрыв больше (в среднем 19 против 150 байт на событие). Подробности по размерам, сжатию и размеру пачки: `Theory~/V1-vs-V7-how-events-travel.md`.
