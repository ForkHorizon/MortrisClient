# Transport V4 → MTB5: анализ и прототип (только клиент, сервер не ограничен)

Все числа ниже либо измерены в этой папке (`results/*.json`, `native/*.json`), либо взяты из файлов V4 (указан файл). Корпус синтетический: генераторы V2/V3 (`gen.py`, `alternate.py`, `workloads.py` из evidence.zip). На реальном трафике числа будут другими.

## 2. Куда уходят байты (MTB5 stateful, base cap100, `results/breakdown_*.txt`)

| Поле | Б/событие | Доля |
|---|---|---|

| ts (интервалы между событиями) | 1.05 | 9.5% |
| release_x / release_y / snap_distance (случайные float32) | 0.81 / 0.75 / 0.72 | 21% |

| block_id, rotation, клетки, block_type, attempt_id, slot | ~0.1–0.17 каждое | ~7% |
| имя, сессия, контекст устройства, форма свойств, sequence, elapsed | <0.06 каждое | <1% |

Аналитическая оценка энтропийного дна генератора base: **10.9 Б/событие**, из них хеши 6.0, float 2.1 (`v2-rerun/results/entropy_floor.txt`). MTB5 stateful даёт 11.08, то есть в пределах точности этой оценки. **Дальше без потерь на base выжимать почти нечего, если не использовать игровые правила.** В rich основная масса тоже приходится на случайные данные: touch_x/y, frame_ms (~2.8–2.9 Б каждое), board_rows, since_last_action_ms. В alt 64% занимает `opaque` (160 случайных байт в hex), его сжать нельзя.

Вывод: у V4 оставался запас ~33% на base, а сам V4 почти не уменьшил тело относительно V3 (−2.5%, 00-summary). Причина в том, что zstd работает на байтовом уровне и не видит структуру полей.

## 3. Что предлагается: MTB5, контекстная модель + бинарный арифметический кодер

`ctxcodec.py` + `rc.py`. Энкодер и декодер написаны одним кодом, поэтому симметричны. zstd не используется.
- Бинарный range coder в стиле LZMA, вероятности 16 бит, смесь двух скоростей адаптации (сдвиги 4 и 7).
- Для каждого поля своя модель. Контекстом служат имя события, ключ, предыдущее имя (марковская цепочка имён) и пара имён для dt.
- Целые числа: длина в бинарном дереве плюс модельные биты мантиссы. Предиктор выбирается обратно-адаптивно (обе стороны считают одинаково, сигнализация не нужна) из шести вариантов: последнее значение ключа, последнее для (имя, ключ), «время прошло», линейный, dt события, «партнёрское поле» предыдущего события (например, target_cell_x→cell_x). Для drag_ms==dt стоимость падает почти до нуля.
- Строки: «равно последнему значению ключа» (attempt_id, хеш в checkpoint), алиас на предыдущую строку события (wave_attempt_id), таблица известных значений из приора, UUID ровно в 128 бит, hex в 4 бита на символ, «продолжение прошлого» (placed_block_ids), правка относительно прошлого значения (board в alt), иначе текст с контекстом порядка 1.
- float32/64: точные IEEE-биты, знак и экспонента моделируются. -0.0, u64 max, Decimal, одиночные суррогаты сохраняются.
- Приор («словарь») — снимок модели после прогона по train202. Он поставляется с клиентом, как сейчас поставляется zstd-словарь.
- Кадр: 1 байт заголовка (+1 байт токена состояния в stateful), тело range coder, **CRC32 (4 Б) от V1-байтов**. Арифметический поток сам ошибок не ловит: до добавления CRC 63 из 2000 мутированных кадров «успешно» декодировались в мусор. С CRC отклонены все 2000 (`test_mutation.py`). CRC включён во все числа.
- Режимы:
  - **stateless**: каждая пачка начинается с приора. Надёжность как у V4.
  - **stateful**: модель и «последние значения» переносятся с последней пачки, которую сервер подтвердил ACK.
  - **stateful со сбросом на новую сессию**: модель не нужно хранить на диске между запусками.

Тесты: `test_roundtrip.py` (крайние значения + 300 fuzz-пачек, stateless и stateful) — OK. Каждый кадр во всех замерах декодирован и сверен побайтово через `exact.render` из V4.

### Игровое правило хеша (отдельно, как V4 `replay`)
Если `placed_state_hash` = SHA256(prev‖block,x,y), как в генераторе, его можно предсказать. Это проверка одного бита. V4 replay (paired-matrix.json / extreme-v4.json): cap100 11.007, лучший cap500 8.231. **MTB5 + правило:** cap100 6.496 stateless / 5.127 stateful; cap500 5.401 / 5.091; исходная каденса 9.649 / 5.338. Реальный алгоритм хеша в игре не установлен (09-open-questions), поэтому это условный результат. Но это **самый большой рычаг из всех**: 55% байт base. Если сервер может пересчитать хеш из состояния, поле лучше вообще не отправлять или кодировать одним битом-предикатом.

## 6. Стоимость на клиенте

**CPU (нативно, x86 Xeon на стенде, не ARM-телефон).** `native/rcbench.c` воспроизводит точную последовательность решений энкодера: хеш-таблица контекстов + обновление вероятностей + range coder. Логика предикторов и полей сюда не входит, это дополнительные десятки операций на поле.

|---|---|---|---|
| бинарных решений/событие | 261 | 621 | 1576 |
| MTB5 энтропийная стадия, мкс/событие | 1.44–1.54 | 4.1–4.2 | 204 (*) |

(*) На alt наивная open-addressing таблица из прототипа почти заполнена (75 тыс. контекстов текста), получились длинные пробы. Это артефакт бенча, на дизайн на клиенте не переносится (см. фиксированную таблицу ниже).

Итог: MTB5 дешевле zstd-19, которым V4 получает свои лучшие числа, но примерно в 10 раз дороже быстрого zstd. В абсолютных цифрах на base это единицы микросекунд на событие против ~1 мс на пачку. Время Python (MTB5 ~290–350 мкс/событие против V4 ~68) не показательно: у V4 zstd написан на C.

**Память.** Вся адаптивная модель — это таблица счётчиков (2×uint16 на контекст). Приор base содержит 11 623 контекста (rich 20 451, alt 75 667). Вариант для C#: фиксированная таблица с хеш-индексом без проверки ключа. Коллизии одинаковы на обеих сторонах, так что сжатие остаётся без потерь (`fixed_table.py`, `results/fixed_table_*.json`):

|---|---|---|---|
| 16K слотов = 64 КиБ | 13.60 / 12.15 | 31.97 / 29.65 | 122.11 / 117.10 |
| 64K слотов = 256 КиБ | 12.58 / 11.38 | 29.35 / 27.64 | 114.71 / 110.78 |

Приор нужно поставлять так же, как словарь: Python-снимок base после pickle+zlib весит 78 КБ, фиксированная таблица 256 КиБ до сжатия. Stateless сбрасывает таблицу в приор на каждую пачку: memcpy 512 КиБ в бенче добавил ~0.1 мкс/событие.

## 7. Что не сработало или опасно
- **Без приора** MTB5 хуже V4: base 37.27, rich 70.00, alt 150.59 (stateless cap100). Приор обязателен.
- **Чужой приор** (обучен на base, применён к drift): 62.16 Б/событие, это хуже V4 со своим словарём. У V4 с тем же несовпадением 57.29 (`results/v4_drift_mismatch.json`). Оба подхода требуют версионировать приор/словарь вместе со схемой событий. Stateful-режим сильно смягчает проблему, потому что модель учится по ходу.
- Альтернативные zstd-улучшения уже проверены автором и малы: ultra22/LDM дают <0.002% (05-ablation). Предыдущая пачка как референс у MTB2 дала −5.8% (`v2-rerun/results/stateful_base.md`). Bitpack/EF/decimal-XOR в V4 дали −2.5…−2.9%. Увеличение пачек помогает V4 (cap500 14.42), но ценой задержки, а MTB5 stateful этого не требует.
- alt (случайные hex/текст) жмётся слабо: −9…−14%. Случайные данные не сжимает ничто.
- Без потерь float32 стоят ~2.3 Б/событие (base) и ~8.5 (rich). Квантование (например, touch_x до 0.001) убрало бы большую часть, но это продуктовое решение с потерей данных. Здесь не измерялось.

## 8. Рекомендация
1. **Заменить zstd+MTB4 на MTB5 stateless** с поставляемым версионированным приором. Это то же поведение надёжности, что у V4: каждая пачка независима. Payload меньше на 21–31% (base), 24–28% (rich), 9–13% (alt), 25% (drift), H2 на проводе −13…−23%. CPU ниже zstd-19, память — таблица фиксированного размера 64–256 КиБ.
2. **Затем stateful со сбросом на начало сессии**: модель живёт в памяти процесса, на диск не пишется, сервер хранит модель последней подтверждённой пачки на origin (или пересобирает её повтором сохранённых событий). Payload base −33…−47%, drift −58%, H2 на проводе −29…−34%. Пачка кодируется в момент отправки относительно последнего ACK-состояния. При потере ответа клиент перекодирует ту же пачку от того же состояния. Если у сервера нет базы, он отвечает 409 и клиент отправляет stateless. CRC32 ловит рассинхрон.
3. **Выяснить у игры правило placed_state_hash** (или убрать поле, если сервер может его вычислить). На base это ещё −50%: 5.1 Б/событие против 11.1.
4. Политику батчинга строить от HTTP-накладных и радио, а не от кодека. Для sparse-трафика копить дольше и отправлять вместе с другими запросами.

## 9. Риски и заметки для Unity C# / IL2CPP
- Энкодер — это ~300 строк без аллокаций: `uint`/`ulong` арифметика, `ushort[]` таблица, заранее выделенный выходной буфер. Нативная библиотека zstd не нужна, это минус 116–277 КБ .so (08-resource-budget).
- Контекст = хеш (eventNameId, keyId, роль, узел дерева) → индекс в `ushort[2*slots]`. Строковые id и последние значения хранятся в небольших массивах. Прототип на Python использует dict и tuple, при переносе битовая совместимость не сохранится, поэтому **эталон и тест-векторы нужно делать на C#/Go-сервере заново**.
- Целые до u64 max: остаток предиктора может занимать до 66 бит (в Python это decimal/bigint). В C# нужна ветка UInt128 или отдельный escape для |остаток|≥2^63.
- Декодер на сервере намеренно последовательный и медленный (Python ~1 с на мусорный кадр в худшем случае). Нужны лимиты на запрос; границы длин уже проверяются.
- Приор, который поставляется с клиентом, имеет ID и SHA. На сервере хранятся все когда-либо выпущенные версии. Эти правила уже описаны в спеке V4 для словарей.
- Stateful требует строго последовательных отправок одного origin (или конвейера с явной базой), хранения состояния на сервере и тестов на kill/late-ACK. Они в этой работе не делались.
- Не проверено: реальный продакшн-корпус, ARM-телефон, батарея, C#-порт, точная форма payload_json реального SDK (kind2 overlay V4 применим и поверх MTB5).
