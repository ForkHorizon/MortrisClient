## 0. Жёсткие правила (нарушение = задание провалено)

1. **Не запускай тесты, сборки, эмуляторы, Unity, Gradle, dotnet, adb, сервер.** Их уже гоняли, их отдельно запустят потом. Разрешены только: чтение файлов, `git log`, `git diff`, `git show`, `grep`/поиск, `ls`, `wc`.
2. **Не меняй код, документы, тесты, настройки. Не делай коммитов, push, веток.** Единственное, что ты вправе записать, — файлы отчёта в папку `Theory~/queue-v2-audit/` (создай её сама).
3. **Не придумывай.** Каждое замечание подкрепляй цитатой кода с путём и номером строки и конкретным сценарием («если происходит A, затем B, то получается C»). Если не уверена — пиши «не подтверждено» и объясняй, чего не хватило. Лучше пять настоящих находок, чем тридцать догадок.

5. После того как суб-агенты закончат, **ты сама перепроверяешь** каждую находку уровня «критично» и «высоко»: открываешь указанные строки и подтверждаешь или опровергаешь. ## 1. О чём проект (прочитай полностью, это контекст)

Unity-пакет аналитики для Android (Mortris Analytics). Рабочий каталог: корень репозитория `MortrisClient`. Ветка: `feat/v7-queue-v2`. Что изменилось в этой работе: коммиты `fbf67e2`, `b01fd48`, `d732130`, `5cc7b57` (база до них: `8ad86d7`). Смотри изменения командой:
`git diff 8ad86d7 5cc7b57 -- Runtime Native~/android/analytics/src/main Native~/transport-tests/tools`
(старая версия кода — `git show 8ad86d7:<путь>`; сравнивай старое поведение с новым).

**Было:** каждое событие из игры сразу превращалось в JSON-строку, уходило через JNI в Java-очередь (SQLite), там снова разбиралось и записывалось отдельной транзакцией; при отправке читалось обратно как JSON и снова разбиралось.

**Стало (путь события):**
1. `Analytics.Track()` (`Runtime/Analytics.cs` → `Runtime/Internal/AnalyticsRuntime.cs`) проверяет событие (`EventValidator.cs`) и один раз пишет его в бинарную запись (`Runtime/Internal/Transport/EventRecord.cs`: `EventRecordWriter`).
2. Запись кладётся в память — `EventBuffer` (`Transport/EventBuffer.cs`). Через `EventBufferWindow` (по умолчанию 200 мс) или при ≥128 записях рабочий поток (`AnalyticsPersistenceWorker.cs`) отдаёт всё Java-очереди **одним вызовом и одной транзакцией**.
3. Java-очередь (`Native~/android/analytics/src/main/java/com/daliys/analytics/AnalyticsQueue.java`, схема БД версии 4) хранит записи как blob, сама присваивает **последовательные номера (sequence)** при вставке, держит счётчики (количество, байты, следующий номер) в памяти, ведёт журнал «выброшенных» диапазонов номеров.
4. Загрузчик (`AnalyticsUploader.cs`) читает строки как `QueueBatch` (`EventRecord.cs`), отправляет либо компактным пакетом V7 (`Transport/V7Session.cs`, `M7EventEncoder.cs`, `M7Event.cs`, `M7Catalog.cs`), либо старым JSON-способом V1 (JSON строится из записей).
5. Сессии: `Runtime/Internal/Session/SessionTracker.cs` + `AnalyticsLifecycle.cs` (Unity-колбэки паузы/фокуса/выхода). Генерирует события `sys_session_start`, `sys_app_background`, `sys_app_foreground`, `sys_session_end`, сохраняет состояние сессии в Java и по следующему запуску закрывает сессию убитого процесса (Android `ApplicationExitInfo`).
6. Мост к Java: `AndroidQueueBridge.cs` (горячие вызовы `enqueueRecords` и `readOldest` идут через низкоуровневый JNI с кэшем идентификаторов методов; остальные — через `AndroidJavaObject.Call`).

Документация по замыслу: `Documentation/EventPipelineAndSessions.md`, `Documentation/ServerContractLifecycle.md`, `profiling-run~/DESIGN_QUEUE_V2.md` (раздел «Решения пользователя» — **это принятые решения, их не оспаривай**), `profiling-run~/ANALYSIS.md`.

### Известные решения и ограничения (НЕ считай их багами; можно только предложить улучшение)
- Номера (sequence) присваивает Java при вставке; резервирования блоков номеров **сознательно нет**.
- Потеря событий из последних 200 мс при внезапной смерти процесса допустима; при сворачивании/выходе буфер пишется сразу, на вызывающем потоке (`PersistNow`).
- Сервер ветки `feat/v7-transport` пока не знает имён `sys_app_foreground` и `sys_session_end` (отклоняет их) — это известно и описано в `ServerContractLifecycle.md`.
- Валидатор намеренно считает суррогатные пары консервативно (по 3 байта на половину).
- `decimal` вне 64-битного диапазона отправляется как double. Целые двойные числа (3.0) сознательно становятся целыми, как в старом JSON-пути.
- Не проверено на реальном телефоне (только эмулятор), это известно.
- Тесты уже есть и проходят (207 в `Native~/transport-tests`, Java-проверки очереди, Unity-сборка). **Твоя цель — найти то, что тесты НЕ ловят.**

## 2. Что искать (главный приоритет — настоящие ошибки)

Классы ошибок, в порядке важности:
1. **Потеря или дублирование событий** (в любом сценарии: сбой записи, сбой отправки, повтор, пауза во время записи, выход приложения, отключение сбора, смена политики сервера).
2. **Нарушение порядка и непрерывности номеров (sequence)**; несогласованность журнала выброшенных диапазонов; поведение при сбросе идентичности (`resetIdentity`), `beginNewStream`, вытеснении и просрочке.
3. **Гонки и взаимные блокировки** между: главным потоком Unity, рабочим потоком (пул потоков), таймерами (`_flushTimer`, `_uploadTimer`, `_heartbeatTimer`), `PersistNow` на главном потоке, `_writeSync`, замком `EventBuffer`, замком `SessionTracker`, синхронизацией Java. Проверь порядок взятия замков и сценарии «поток A держит X и ждёт Y, поток B наоборот».
4. **Рассинхронизация кэшей в памяти с базой**: счётчики Java (`pendingCount`, `pendingBytes`, `nextSequence`), кэш `PendingCount` в `AndroidQueueBridge.cs`, `_savedSessionVersion`; что будет при исключении посреди транзакции, при пропуске вставки дубликата, при очистке, при вытеснении.
5. **Ошибки в обработке исключений и «ядовитых» данных**: может ли одна повреждённая/непонятная запись (в том числе старая JSON-строка формата 0) навсегда блокировать отправку всей очереди? Что делает загрузчик при `FormatException` из `QueueBatch.FromFrame`?
6. **Бинарный формат записи**: границы (длины, varint, переполнения), порядок байт UUID, отрицательные числа, время до 1970, очень длинные строки, 32 свойства, юникод, `QueueBatch` разбор кадра; совпадение формата между C# (`EventBuffer`, `EventRecordWriter`) и Java (`enqueueRecords`, `readOldest`) — смещения, порядок байт (big-endian/little-endian), «+4» для длины, `RECORD_HEADER = 33`.
7. **Жизненный цикл и сессии**: порядок `OnApplicationPause`/`OnApplicationFocus`/`OnApplicationQuit`, повторные вызовы, пауза без возврата, скачки системных часов (назад/вперёд), смена часового пояса, переход на летнее время, отрицательные длительности, переполнение, сессия при отключённом сборе, `Recover` с чужим/старым/пустым состоянием и устаревшей записью `ApplicationExitInfo` (можно ли закрыть сессию дважды или не ту?), Android < 11, процесс, перезапущенный системой.
8. **JNI и платформа**: низкоуровневые вызовы (`GetMethodID`, `ToByteArray`, `FromByteArray`, `DeleteLocalRef`, `ExceptionOccurred`) — утечки локальных ссылок, использование ссылок в других потоках, разделяемые массивы аргументов `_enqueueArgs`/`_readArgs` при вызовах из двух потоков, подключение/отключение потока к JVM, возврат `null`; поведение при отсутствии нативной библиотеки, на не-Android платформах и в Редакторе Unity (`#if UNITY_ANDROID && !UNITY_EDITOR`); совместимость с IL2CPP (потокозависимые статические поля `[ThreadStatic]`, обрезка кода, `Span`/`stackalloc` в C# 9).
9. **Миграция БД v3→v4** (`QueueOpenHelper.onUpgrade`), `AUTOINCREMENT`, индексы, потеря строк, форматы `0` и `1`, повторное открытие, восстановление после повреждённой БД (`openDatabaseWithRecovery` + кэшированный `insertStatement`).
10. **Загрузчик и V7/V1**: правило «после первого пакета продолжать только при ≥100 в очереди» (`sent`, `force`, `PendingCount`) — может ли остаток зависнуть навсегда, повториться бесконечно или ломать повторные попытки (429, 5xx, `Retry-After`, `BackOff`)? Производные идентификаторы событий при открытом потоке V7; соответствие ответов сервера и идентификаторов; `IsIdle`/`NothingToDo` — может ли «пустой» тик пропустить реальную работу (событие, пришедшее между проверкой и возвратом; сохранение состояния; очистка)?
11. **Прочее**: интеграционные места (`Analytics.Initialize`, `ResetForTests`, повторная инициализация, `Dispose` во время работы потоков), настройки (`EventBufferWindow`, `SessionTimeout`, `UploadEventThreshold`, лимиты очереди), валидатор (`EventValidator.cs` — рассинхрон с реальной записью), производительность в худших случаях (большие пачки, 500 строк, 8 КБ свойств).

## 4. Сквозные сценарии для проверки по коду (мысленно прогони каждый)

1. Игра шлёт 1 событие/кадр, в это время приходит `OnApplicationPause(true)`, а рабочий поток в середине записи.
2. Идёт загрузка на сервер (HTTP на рабочем потоке), игрок сворачивает игру, затем сеть отвечает 429.
3. Java выбрасывает исключение внутри `enqueueRecords` (например, неверная запись или ошибка диска): что с буфером, счётчиками, номерами, сессией?
4. Процесс убит сразу после записи пачки, но до сохранения состояния сессии; следующий запуск.
5. Очередь содержит строки формата 0 (старая версия) и 1 одновременно, одна из строк формата 0 повреждена.
6. Игра отключает сбор (`SetCollectionEnabled(false, true)`) во время работы: что с буфером, очередью, событиями сессии, таймерами?
7. Сервер возвращает «приостановить загрузку» (`pause_upload`) или «отключить сбор» (`disable_collection`).
8. Очередь заполняется до лимита (`DurableEventLimit`/`DurableByteLimit`) во время всплеска событий.
9. Системные часы переведены на сутки назад между `pause(true)` и `pause(false)`; затем на час вперёд.
10. Два вызова `Analytics.Initialize` подряд из разных потоков; затем `Dispose`.
11. Сервер подтверждает пакет частично (часть событий отклонена), затем соединение рвётся до ответа на следующий.
12. Приложение запущено в Редакторе Unity или на не-Android платформе: что происходит со всеми новыми классами?

## 5. Формат ответа каждого суб-агента (требуй дословно)

```
ID: <область>-<номер>

Уверенность: подтверждено чтением кода | вероятно | догадка
Место: <путь>:<строки>
Что не так: <1–2 предложения простыми словами>
Сценарий: <шаги: что происходит, в каком порядке → что в итоге получается неправильно>
Цитата кода: <3–10 строк>
Как исправить (кратко): <идея, без правки файлов>
```
Отдельный список: «Улучшения (необязательные)» — по одной строке. И список «Проверено, замечаний нет» — какие места ты прочитал и не нашёл проблем (чтобы было видно покрытие). Если находок нет — так и пиши.

## 6. Итоговый отчёт (пишешь ты, главный аудитор)

Файл: `Theory~/queue-v2-audit/REPORT.md`. Структура:
1. **Краткая сводка** (до 10 строк): сколько находок по серьёзности, 3–5 самых важных простыми словами.
2. **Находки**, отсортированные: критично → высоко → средне → низко. Формат из раздела 5. Без дублей (если две области нашли одно и то же — объедини и укажи обе). Только подтверждённые тобой при перепроверке или честно помеченные «вероятно/догадка».
3. **Отклонено при перепроверке** (с причиной) — чтобы не искать это второй раз.
4. **Улучшения** (необязательно): группируй по теме, по строке на идею, оценка пользы/риска.
5. **Что не удалось проверить без запуска** (и как это лучше проверить потом тестом — по одному предложению).
6. **Покрытие**: какие файлы и функции прочитаны, какие пропущены.
7. **Метаданные**: сколько суб-агентов использовано, коммит, на котором проводился аудит (`git rev-parse HEAD`).

Сырые ответы суб-агентов сохрани в `Theory~/queue-v2-audit/agents/<номер>-<область>.md`.
