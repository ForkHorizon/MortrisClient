# Профилирование SDK по стадиям (эмулятор Android 15 arm64, IL2CPP development)

Дата 2026-10-24. Данные: `results/emu/*/prof.txt`, таблицы `results/emu/PROFILE_TABLES.md` (генерирует `analyze_prof.py`). Стенд: копия SDK с замерами (`patch_sdk.py`, рабочий пакет не тронут), проба `unity/V7ProfProbe.cs`, запуск `run_matrix.sh`. Реальные события из `replay_real_20k.jsonl`, сервер локальный с настоящим каталогом и словарём. **Это эмулятор, не телефон**: пропорции между стадиями и число аллокаций осмысленны, абсолютные мкс — нет (телефон пока не подключён; тот же `run_matrix.sh` с `RUNSET=phone` повторит всё на нём).

## Как читать
CPU = время CPU потока, wall = прошедшее время (включая ожидание). Стадии вложены (inclusive). Значения на одно событие. Режим `none` — пустой плеер (база). Интервал выгрузки в пробе 5 с, порог 100 (как в прошлых прогонах; **не** дефолт SDK 30 с). Один прогон на сценарий, без повторов: шум не оценён.

## Что видно (эмулятор, индикативно)
1. **Главный расход — запись в очередь, а не кодирование.** В темпе «событие за кадр» воркер тратит 1,25–1,5 мс CPU на событие, из них 66–68% — один JNI-вызов `enqueueBatch` (SQLite + Java). Кодирование V7 — ≈80–90 мкс/событие, то есть порядка 7% от этого.
2. **Причина в том, что каждое событие будит воркер отдельно.** При темпе 1/кадр на вызов приходится 0,99 события (1207 вызовов на 1200 событий), в залпе 25–44 события на вызов. Из двух точек (1 и 25 событий на вызов): ≈530 мкс фиксированной цены вызова + ≈300 мкс на событие. Объединение записей (подождать 50–200 мс, писать пачкой) убирает фиксированную часть почти целиком. Оценка, не измерение.
3. **`GetState()` (ещё 4 JNI-вызова) выполняется на каждое событие** внутри `Flush`: 100–145 мкс CPU/событие в темпе, 500 мкс при единичных событиях. Состояние можно кешировать/не запрашивать, пока не пора выгружать.
4. **Java-сторона аллоцирует ≈41 КБ/событие в залпе и 78–133 КБ при единичных вызовах** (счётчик ART). Это сопоставимо с самой большой статьёй мусора на стороне C#. Вероятно JSON-разбор строки на стороне Java, нужно смотреть код `AnalyticsQueue.java` или `simpleperf` на телефоне.
5. **Управляемые аллокации (счётчик Unity «GC Allocated In Frame», все потоки неточно):** V1 ≈34–38 КБ/событие, V7 ≈49–52 КБ/событие (+15 КБ на кодирование, согласуется с хостовой цифрой 21,6 КБ). Пустой плеер даёт 0,3–0,6 КБ. **Итого мусор на событие ≈ 75–130 КБ (C# + Java), много по сравнению с HyperKit (2,4–9,6 КБ), примерно как GameAnalytics и Facebook (≈105–108 КБ).** Сравнение с конкурентами на разных стендах, только ориентир.
6. **Сборки мусора:** V7 47–75 против V1 35–55 на тот же сценарий (+30…+37%), каждая — полная (gen0=gen1=gen2).
7. **Главный поток:** `Track()` ≈75–185 мкс CPU на событие, но **p99 = 3–6 мс** почти во всех режимах, включая залп (пустой плеер 0,3 мкс). Вероятные причины — GC или блокировка `lock(_sync)` при снимке пачки воркером; не установлено.
8. **Трафик:** V7 20–22 Б/событие в потоковых режимах против 87–94 у V1; при одиночных событиях 139 против 583 Б. Размер пакета определяется тем, сколько событий накопилось за интервал выгрузки.
9. **Запасная проверка.** `v7_post_packet` и `http_send` ≈ 0,4–6 мс wall на запрос при почти нулевом CPU: сетевая часть CPU не нагружает.

## Ограничения
- Эмулятор на Apple Silicon, сборка dev + AllowDebugging + мои замеры (`clock_gettime` и счётчики на каждой границе стадии добавляют мкс-единицы на вызов).
- Один прогон на сценарий; «CPU процесса» в таблицах включает отрисовку пустой сцены (7,6 мс/событие в темпе 1/кадр у режима `none`), поэтому используются потоковые стадии, а не общий CPU.
- Счётчик аллокаций C# в IL2CPP (`GC.GetAllocatedBytesForCurrentThread`) возвращает 0; использован `ProfilerRecorder("GC Allocated In Frame")`, который может не учитывать фоновые потоки полностью. Нужна проверка на телефоне (или второй независимый способ).
- Явная часть Java-стороны (SQLite против JSON-разбора) не разделена: нужен `simpleperf` или `nanoTime` внутри `AnalyticsQueue.java`.
- Не проверено: интервал выгрузки по умолчанию (30 с), реальная сеть, батарея, чистая сборка без отладки (вы просили отдельным шагом).

## Что делать дальше
1. Повторить матрицу на телефоне (`RUNSET=phone ./run_matrix.sh <serial>`), по 3 повтора.
2. Разделить Java-стоимость: `nanoTime` в `AnalyticsQueue.java` (пересборка AAR в копии) и `simpleperf` на телефоне.
3. Проверить гипотезы 2–3 дешёвой правкой в копии SDK: отложенное пробуждение воркера (50–200 мс) и без `GetState()` на каждое событие; сравнить стадии до и после.
