# Дизайн новой очереди событий (черновик для обсуждения, код не менялся)

Основание: `ANALYSIS.md` (измерено на эмуляторе), чтение кода. Решения пользователя: копить события в памяти 100–200 мс допустимо; небольшая потеря при крэше не критична, но её хочется заметить; JSON-разборы убрать; счётчики держать в памяти.

## 0. Что есть сегодня (проверено grep)
В SDK **нет ни одного хука жизненного цикла** (`OnApplicationPause/Quit/Focus`, `ActivityLifecycleCallbacks`, обработчика необработанных исключений). Сейчас это не страшно: событие лежит в памяти только до пробуждения воркера (доли мс). После буфера на 100–200 мс окно потери станет реальным, поэтому хуки нужны в той же правке.

## 1. Сохранение при сворачивании, закрытии, крэше
| Ситуация | Что можно поймать | Надёжность | Что делаем |
|---|---|---|---|
| Игру свернули / потеряла фокус | Unity `OnApplicationPause(true)` и `OnApplicationFocus(false)`; Java `ActivityLifecycleCallbacks.onActivityPaused/onStopped` | Высокая: приходит почти всегда до убийства процесса системой | Немедленно сбросить буфер на диск (синхронно), затем при желании запустить выгрузку |
| Игрок закрыл (свайп из «недавних») | `onTaskRemoved` не у Activity; чаще процесс убивают без callback, но `onPause`/`onStop` уже были при сворачивании | Хорошая, потому что к свайпу игра уже свёрнута | То же, что выше |
| Выход из игры самим кодом | `Application.quitting`, `OnApplicationQuit` | Работает редко и не гарантирован на Android | Не полагаться, только дополнение |
| Java-исключение (крэш) | `Thread.setDefaultUncaughtExceptionHandler` (вызвать предыдущий обработчик после себя) | Средняя: успеваем записать буфер, если он в Java | Записать буфер синхронно |
| Нативный крэш (SIGSEGV в IL2CPP/Unity), ANR, OOM-убийство | Безопасно ничего сделать нельзя | Нет | Не сохраняется; фиксируем факт потери (ниже) |

Выбор места буфера влияет на надёжность: если буфер лежит **в Java** (`ByteArray` в памяти процесса), его можно сбросить обработчиком Java-исключений и lifecycle-callback, даже когда главный поток Unity завис. Буфер в C# сбрасывается только из Unity-хуков. Рекомендация: буфер в Java, C# отдаёт события пачками по 10–50 мс (или сам Java копит).

## 2. Как заметить потерянные события (идея)
Сейчас sequence присваивается в Java при вставке в SQLite, поэтому потеря в памяти до вставки **ничем не видна**: номера просто не выданы. Предлагаю:
- Номер присваивается в момент `Track()` атомарным счётчиком в памяти (быстро, без БД).
- На диске хранится **зарезервированный блок номеров** (например, до N+1000), обновляется редко (раз в 1000 событий или при сворачивании).
- После крэша при старте: счётчик начинается с верхней границы резерва. Дыра между последним реально записанным номером и границей резерва — это **верхняя оценка числа потерянных событий**. Клиент объявляет её серверу как «сброшенный диапазон» через уже существующий механизм dropped ranges (`/v2/streams/sync`); сервер увидит, что именно столько событий не дошло, и может учесть в статистике.
- Дополнительно метка «чистое завершение / нет» в метаданных: при следующем запуске, если метка «грязная», отправить событие `session_ended_abnormally`.
Следствие для идентичности (install, epoch, sequence): номера остаются уникальными и растут, просто с дырами; текущая серверная логика уже допускает объявленные дыры. Требует тестов на совместимость, поэтому это отдельный шаг.

## 3. Счётчики в памяти
`pendingCount`, `pendingBytes`, `nextSequence` держать полями Java-объекта (метод синхронизирован, пишущий поток один). Источник правды остаётся БД: при открытии читаем один раз, потом обновляем **после успешного коммита**. `enforceBounds` проверяет поля, а `COUNT/SUM` запускается только если лимит превышен. `deleteExpired` выполнять раз в секунды/минуты, а не на каждую вставку. Эффект: убираются 4+ запроса на вызов, т.е. большая часть «фиксированной цены» ≈530 мкс.

## 4. JSON четыре раза: что делать
Причина не в языке, а в формате на границах. C++ даст мало: IL2CPP уже компилирует C# в нативный код, а ядро сжатия уже нативное. Выигрыш в аллокациях даёт **отказ от текста**:
1. Событие кодируется в C# сразу в компактную бинарную запись (имя → номер формы из каталога сервера, значения по типам) в переиспользуемый буфер (без аллокаций на событие).
2. Java становится «тупым хранилищем»: `insert(sequence, blob)` и `readOldest(n) -> byte[]`, без разбора и без `JSONObject`.
3. V7-кодировщик берёт записи и упаковывает колонки без разбора текста (это и есть окончательный вариант «потокового разбора»).
4. V1-запасной путь: JSON собирается из бинарной записи только когда нужен откат (редко).
5. Старые строки очереди (`payload_json`) читаются как раньше (миграция без потерь).
Оценка эффекта (из измеренных долей, не обещание): Java-мусор 41–130 КБ/событие → почти 0; C# мусор V7 49 → порядка 5–10 КБ; CPU записи ≈0,3 мс → доли.
Что нужно знать: если события приходят как `Dictionary<string,object>` от игры, один раз их всё равно обходить придётся; цель — делать это один раз, без промежуточных строк.

## 5. «Потоковый разбор кодировщика V7» простыми словами
Сегодня кодировщик читает JSON-текст батча и строит из него дерево объектов (словари, коробочные числа, строки) — на одно событие десятки мелких объектов, это ≈3,3 мкс и ≈16,6 КБ из 7,6 мкс/21,6 КБ (хост). «Потоковый» значит: читать текст по символам и сразу класть значения в массивы колонок, ничего не строя. Это шаг-полумера, если JSON остаётся в очереди. Если делаем бинарную очередь (п.4), потоковый разбор не нужен вообще: данные уже типизированы. Рекомендую сразу п.4, а потоковый разбор делать только как запасной вариант, если бинарная очередь отложена.

## 6. План по шагам (каждый в отдельной ветке, с тестами)
1. Буфер в памяти 100–200 мс + хуки жизненного цикла + `GetState()` только по таймеру/порогу. Замер до/после той же матрицей.
2. Счётчики и границы в памяти (Java), редкая чистка просроченных.
3. Резервирование блока номеров и объявление потерь серверу.
4. Бинарная запись события и «тупое» Java-хранилище; потоковый кодировщик из бинарных данных; откат на V1.
Порядок 1→2 дешёвый и обратимый, 3–4 крупнее и требуют миграции и совместимости с сервером.

# Решения пользователя и уточнения (2026-10-24, вечер)
Принято (общие): применяем оптимизации; порядок шагов ещё обсуждается.
- Окно буфера: **200 мс**, плюс **немедленный сброс при сворачивании** (обязательно).
- Редкие жёсткие крэши: потеря допустима; в запас — Firebase Crashlytics (если он есть в игре).
- Объявление потерь серверу: только если не добавляет постоянной нагрузки (вызывается на редком пути). Базовые значения (CPU, мусор, байты) не должны вырасти; иначе пересмотр.
- **Конец сессии игрока — обязательное требование**: понимать, когда игрок закончил играть (свернул, ушёл, процесс убит), чтобы считать длительность. Берём все доступные механизмы (Unity, Android, практики других SDK).
- Место буфера (C# или Java) — выбрать по числам (рекомендация: C#, см. ниже).

## Рекомендация по месту буфера: C#
События рождаются в C# на главном потоке. Буфер в Java потребовал бы JNI-вызова на каждое событие прямо в `Track()`. По замеру `GetState()` один JNI-вызов стоит порядка 25–35 мкс CPU (4 вызова ≈105–145 мкс на эмуляторе), а весь `Track()` сейчас 75–185 мкс: Java-буфер поднял бы стоимость главного потока на 15–40% и усилил бы пики. C#-буфер: лёгкая блокировка/кольцо в памяти на главном потоке, сброс воркером раз в 200 мс одним JNI-вызовом и сразу по `OnApplicationPause(true)`. Java остаётся долговечным хранилищем. Проигрыш: C#-буфер не виден Java-обработчикам крэша — принято как допустимое.

## Спецификация «конец сессии и жизненный цикл»
Источники сигналов (все дешёвые, срабатывают единицы раз за сессию):
1. Unity: `OnApplicationPause(true/false)` (скрытый `DontDestroyOnLoad`-объект, создаётся в `Initialize` на главном потоке), `Application.focusChanged`, `Application.quitting`.
2. Android: `Application.ActivityLifecycleCallbacks` (`onActivityPaused/Stopped/Started`), `ComponentCallbacks2.onTrimMemory(TRIM_MEMORY_UI_HIDDEN)` как подтверждение «интерфейс скрыт».
3. Сердцебиение: метка `last_alive` (время + накопленное активное время) в памяти; на диск не чаще раза в 15–30 с и при паузе. Если процесс убит, при следующем запуске конец сессии ≈ последнее сердцебиение.
4. При следующем запуске (Android 11+, API 30+): `ActivityManager.getHistoricalProcessExitReasons()` → причина и время смерти прошлого процесса (CRASH, CRASH_NATIVE, ANR, LOW_MEMORY, SIGNALED, USER_REQUESTED, …) и «важность» (был ли на переднем плане). Бесплатно, без зависимостей, закрывает нативные крэши и убийство по памяти. Нужно проверить поведение на целевых прошивках.
5. Необязательная мягкая связь с Firebase Crashlytics через рефлексию (без жёсткой зависимости): `didCrashOnPreviousExecution()` и `setCustomKey("mortris_install_id"/session_id)` для связи отчётов о крэшах с аналитикой. Проверить наличие метода в используемой версии.
События SDK: `app_background` (активное время сессии), `app_foreground` (длительность паузы), `session_end` (причина: user_backgrounded / process_killed / crash / anr / low_memory; время конца из метки или ExitInfo). Правило новой сессии: пауза дольше порога (настраиваемо, например 30 с–5 мин). Все новые имена событий должны попасть в каталог проекта на сервере, иначе пакеты с ними откатываются на V1.

## Бюджет, чтобы базовые значения не выросли
Принимаем шаг, только если по матрице `profiling-run~/run_matrix.sh` (те же сценарии, 3 повтора) CPU воркера на событие, мусор на событие и байты на событие не хуже базовых из `REPORT.md`. Резерв блока номеров и объявление потерь стоят один инкремент счётчика на событие и одну запись на 1000 событий; тяжёлый путь только после крэша.
