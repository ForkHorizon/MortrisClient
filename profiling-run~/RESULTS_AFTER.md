# Результаты после переписывания конвейера событий (эмулятор Android 15 arm64, IL2CPP development)

Дата 2026-10-24. Сырые данные: `results/emu/` (до), `results/emu_final/` (первая версия нового конвейера), `results/emu_final3/` (итоговая сборка). Протокол тот же, что в `REPORT.md`:
реальные события из `replay_real_20k.jsonl`, локальный сервер, один прогон на сценарий. **Эмулятор, не телефон**: пропорции и объём мусора осмысленны, абсолютные микросекунды нет.
«Мусор» = управляемая куча Mono (счётчик Unity «GC Allocated In Frame», все потоки) и куча Java (ART). В него входит фон пустого плеера (≈0,3–0,6 КБ на кадр); в редких потоках он велик в пересчёте на событие.

## Что изменилось (в порядке вклада)
1. События пишутся один раз как бинарные записи, без JSON ни в одной стадии.
2. Запись в очередь раз в 200 мс одной транзакцией (раньше на каждое событие), счётчики очереди в памяти.
3. Горячие JNI-вызовы (`enqueueRecords`, `readOldest`) идут через низкоуровневый JNI: `AndroidJavaObject.Call` на каждый вызов выделял ≈34 КБ управляемой памяти.
4. Загрузчик продолжает отправку, только пока ждёт полный пакет; остаток уходит со следующим сроком.
5. Валидатор и поиск формы события не выделяют память; пустые тики таймера не подключаются к JVM.

## Жизненный цикл (сквозной тест на эмуляторе, V7 и V1)
Сворачивание (HOME) → `sys_app_background` с `active_ms`; возврат после тайм-аута → `sys_session_end` (reason `timeout`, время = момент ухода) и новая сессия; `kill -9` → следующий запуск закрывает
сессию причиной Android `signaled` и временем смерти процесса. Сервер должен разрешить `sys_app_foreground` и `sys_session_end` (см. `Documentation/ServerContractLifecycle.md`): на неизменённом сервере они отклоняются.

## Проверки
.NET 207/207 (включая независимый Python-декодер и Go-декодер сервера на пакетах нового кодировщика); Java 17 сценариев очереди на эмуляторе (включая миграцию v3→v4, откат пакета, счётчики);
сборка IL2CPP; сквозной тест жизненного цикла для V7 и V1.

## Не сделано / ограничения
Телефон (по вашей просьбе позже, без раздачи интернета); чистая сборка без отладки; батарея; один прогон на сценарий (шум не оценён); оценка мусора по стадиям грубая (рост кучи Mono).
Оставшийся мусор в редких потоках — подключение/отключение рабочих потоков к JVM на каждую запись (Java ≈34 КБ/событие при 1 событии в секунду).
