# Анализ профилирования (эмулятор) — как работает сейчас и что улучшать

Основание: `REPORT.md` и `results/emu/` (измерено), чтение кода `AnalyticsPersistenceWorker.cs`, `AnalyticsUploader.cs`, `AnalyticsQueue.java` (прочитано, не измерено). Абсолютные мкс эмулятора неточны, пропорции и число аллокаций — осмысленны. Телефон откладываем.

## 1. Путь одного события сегодня и его параметры
1. `Analytics.Track()` (главный поток): проверка имени/свойств, `Guid.NewGuid().ToString()`, копия свойств, `TrackedEvent`, кладётся в очередь памяти (ёмкость 256). ≈75–185 мкс CPU.
2. Каждый `Track` будит рабочий поток (`Schedule` → `ThreadPool`). Воркер берёт до 32 событий (`BatchSize = 32`), собирает **JSON-строку** и одним JNI-вызовом отдаёт Java.
3. Java `enqueueBatch`: парсит строку (`JSONArray`), в одной транзакции SQLite для каждого события: ещё раз копирует объект (`new JSONObject(event.toString())`), строит `properties.toString()`, `payload.toString()`, `insert`; затем обновляет счётчик sequence, `deleteExpired` (select+delete), `enforceBounds` (COUNT и SUM по таблице, не менее двух раз) и коммит.
4. Сразу после записи воркер зовёт `uploader.Flush`: `GetState()` (ещё 4 JNI-вызова), и только если подошло время (`UploadInterval` 30 с по умолчанию) или набралось `UploadEventThreshold`, читает до 100 строк (`readOldestBatch`: каждую снова парсит в `JSONObject` и пересобирает JSON), C# **в третий раз** парсит этот JSON (`MiniJson`), упаковывает колонки, zstd, HTTP.
5. Подтверждение сервера → `deleteThroughSequence` в Java.

Итого одно событие превращается в JSON ≥4 раза (C# сборка, Java разбор, Java копия, чтение и разбор в C#). Параметры, влияющие на всё: `MaximumBatchSize=100`, воркер-пачка 32, `UploadInterval` 30 с, порог 100, лимит очереди 256.

## 3. Где дыры (по убыванию вклада)
1. **Каждое событие = отдельная транзакция SQLite и 5+ JNI-вызовов.** Фиксированная цена вызова (≈0,5 мс, транзакция + COUNT/SUM + deleteExpired + мета) платится на каждое событие в темпе. Лекарство: накапливать события в памяти 50–200 мс (или до N штук), затем писать одним вызовом; не вызывать `Flush`/`GetState` на каждое событие, а только по таймеру/порогу. Ожидание: фикс. часть уходит почти полностью, т.е. 1,25 → ≈0,4 мс/событие в темпе (оценка). Цена: событие может подождать на несколько сотен мс в памяти до записи на диск (потеря при внезапном убийстве процесса — окно в сотни мс, решать вам).
2. **Тройной разбор JSON.** Java парсит и копирует каждое событие, потом снова при чтении; C# парсит ещё раз. Это и есть основная часть мусора (Java 41 КБ + C# 15–35 КБ). Лекарство: на границе C#↔Java передавать компактный бинарный блок (или хотя бы не копировать `JSONObject` и хранить `payload_json` как есть), а V7-кодировщику отдавать значения без повторного разбора. Ожидание: основная часть мусора и часть CPU, это самая крупная правка.
3. **`enforceBounds` и `result()` делают COUNT/SUM по таблице несколько раз на вызов.** Держать счётчики в памяти/метаданных. Мелкая правка.
4. **Кодировщик V7:** 80–90 мкс/событие и +15 КБ мусора против V1. Потоковый разбор уберёт большую часть (в хостовых цифрах JSON-разбор = 77% аллокаций), но это второй приоритет после пунктов 1–2.
5. **Пики `Track()` 3–6 мс.** Либо блокировка `lock(_sync)` пока воркер снимает пачку, либо GC. Нужно отдельное измерение (замерить время ожидания блокировки).
6. **Сеть:** уже выигрыш в 4–5 раз по сравнению с V1; рост пачки (собирать до 100) — дальнейший резерв: в пробе пакеты получились 25–90 событий.

## 4. Что менять не стоит
Кодирование V7 само по себе (zstd 0,09 мкс/событие), размеры словаря и модели — почти не влияют на клиентский CPU и мусор.

## 5. Что неизвестно
- Телефон: абсолютные значения и соотношение Java/SQLite (на реальном флеше коммит дороже, чем на эмуляторе).
- Доля SQLite против разбора JSON внутри Java (нужен `nanoTime` или `simpleperf`).
- Реальная доля `lock`/GC в пиках `Track()`.
- Чистый режим без отладки; интервал выгрузки по умолчанию.

## 6. Предлагаемый следующий шаг (на эмуляторе, без телефона)
Проверить пункты 1 и 3 дешёвой правкой в **копии** SDK: отложенное пробуждение воркера + без `GetState()` на каждое событие; затем повторить сценарии `perframe1`, `persec`, `single` и сравнить стадии «до/после». Рабочий SDK не трогаем.
