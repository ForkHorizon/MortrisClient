
## 4. Что найдено в самом Mortris при этих замерах

| № | Находка | Статус |
|---|---|---|
| 1 | **Дедлок на сервере (#0126)**: параллельный приём V8 из 10 установок давал HTTP 500 («deadlock detected») у 9 из 10 — построчный апсерт `event_catalog` в разном порядке. | **Исправлено** в `MortrisServer-v8/internal/ingest/batch_persist.go`: имена собираются на пачку, апсерт одним запросом в порядке имён. После исправления 190 параллельных установок без ошибок. |
| 2 | **Лимиты приёма зашиты в код** (12 запросов/мин на установку, burst 30; 30 rps на проект; 100 rps на адрес). Из-за них V1 (100 событий на запрос) не доставил 3000 событий за один заход (доставлено 85%), а V8 с пачками по 10 событий — упирался в 12 запросов/мин. | **Исправлено**: `MORTRIS_INGEST_INSTALL_PER_MIN`, `_INSTALL_BURST`, `_PROJECT_RPS`, `_PROJECT_BURST`, `_IP_RPS`, `_IP_BURST` (по умолчанию прежние значения). Для боевых значений решение за вами. |
| 3 | **Гонка в `FlushAsync`**: запрос сброса, пришедший во время уже идущего неформсированного прохода, завершался этим проходом, и последние <200 событий ждали таймер 120 с. | **Исправлено** в `AnalyticsPersistenceWorker.cs` (ожидающие запросы снимаются на каждый проход). Проверено на устройстве: `FlushAsync` теперь отдаёт хвост. Юнит-теста нет (воркер зависит от JNI). |
| 4 | **#0127 (открыта)**: на схеме midcore (70 типов событий, у сервера 1213 вариантов формы из-за необязательных полей) V8 отправляет по одному пакету за цикл выгрузки с паузой 15 с, пока сервер на лимитах по умолчанию; с поднятыми лимитами сервера доставка полная (94.7% = 1894/2000, остальные 5.3% — события с >32 свойствами, их отбрасывает клиентская валидация). Вероятная причина (гипотеза, не доказана до конца — логи SDK не читаются через logcat на этом стенде): лимит приёма и реакция клиента на отказ (бэкофф 15 с); клиент не показывает причину. | Нужно решить: реакция клиента на 429/лимит (сейчас бэкофф 5 с…5 мин) и размер каталога форм (1213 форм на 70 событий — «взрыв форм» из-за необязательных полей). |
| 5 | **Буфер передачи 1024 события**: всплеск >1000 событий за кадр теряет хвост (принято 2.1–2.7 тыс. из 6/20/100 тыс.; конкуренты принимают все, но GameAnalytics доставляет ≈4–5 тыс., Amplitude 2.40.1 ≈1000). | Дизайн; число — ваше решение (можно поднять `BufferCapacity`). |
| 6 | **Инициализация 180 мс** (конкуренты 4–16 мс): открытие SQLite-очереди, V8-состояние. | Не исправлялось. |
| 7 | **Низкая частота (5 событий/с)**: ≈3 мс CPU и ≈23 КБ аллокаций Java на событие (запись одного события на каждый вызов JNI), при пачках — 0.1 мс и 4.8 КБ. | Не исправлялось; кандидат на оптимизацию (объединять записи на окне 200 мс). |
| 8 | **После оффлайна ≥5 минут** отправка возобновляется не сразу (бэкофф вырастает до 5 минут), см. таблицу C4/C4b. | Дизайн; можно сбрасывать бэкофф по смене сети/возврату на передний план. |

## 5. Как воспроизвести

```bash
cd Assets/MortrisClient/comparison-run~
./build.sh cmp-arm64.apk                               # Unity IL2CPP release со всеми SDK
python3 tools/make_puzzle_data.py && python3 tools/make_synth_data.py   # данные (нужен night-run~/work/puzzle-1m.jsonl.gz)
tools/stack_start.sh cpu 54411 18111 seed-v7            # PostgreSQL + сервер V8 (V7 засеян обучающими установками)
python3 tools/matrix_cpu.py <serial телефона> cpu 3     # CPU/GC/PSS/кадры/байты на телефоне
python3 tools/matrix_fid.py <serial эмулятора> 18190 emu fid       # доставка и сохранность полей, 4 набора
python3 tools/matrix_chaos.py <serial> 18191 emu2 chaos 0 kill,net_loss,net_bad,offline
python3 tools/matrix_param.py <serial> 18190 emu param1 batch,rate,burst
tools/server_series.sh && tools/server_series2.sh       # нагрузка на сервер, 50/100/190 установок
python3 tools/analyze_cpu.py cpu && python3 tools/build_tables.py > RESULTS_TABLES.md
```
Журнал событий ночи и все исправления стенда — в `STATE.md`.
