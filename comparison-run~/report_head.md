# Сравнение аналитических SDK, переделанное с нуля

Дата прогона: 26.10.2026, ночной прогон на физическом телефоне **Nothing A142** (Dimensity 7200 Pro, 8 ГБ, Android 16) + два эмулятора arm64 для проверок, где CPU не важен.
Все скрипты, сырые результаты и состояние прогона лежат в `comparison-run~/` (`STATE.md` — журнал, `tools/` — стенд, `results/` — данные, `RESULTS_TABLES.md` — все таблицы целиком).

## 0. Главное

1. **Старые сравнения были нерелевантны, и это исправлено методически**: теперь все SDK работают в **одном Unity IL2CPP release-приложении**, на одном потоке событий, с одинаковыми замерами (CPU потока и всех процессов включая Google Play Services, задержка `Track()`, кадры, GC, PSS, байты на проводе). Mortris — боевой код без инструментирования.
2. **Вес на проводе (байт на доставленное событие, вверх, настоящие события Puzzle, пачки по 20 за кадр)**: Mortris V8 — **18.6** (9.9 с новым содержанием событий), V7 — 25.5, V1 — 91.6. Конкуренты: GameAnalytics 75.6 (и он теряет поля), HyperKit(core, без свойств) 384, HyperKit(ctx) 1165, Amplitude Kotlin 1318, Mixpanel 1975, Amplitude 2.40.1 ≈ 2020. С моделью TLS (рукопожатие + записи) и ответами сервера: V8 24.8 / V1 136.5 / GA 77 / Kotlin 1325 / Mixpanel 1982.
3. **CPU (чистый, за вычетом базы Unity, сценарий 20 событий/кадр, Nothing A142, 3 повтора с парными срезами)**: V8 ≈ 0.11 мс/событие (в пределах шума ±0.33), V7 0.17, V1 0.19; GameAnalytics 3.0, Firebase 2.6 (+ ≈0.4 в процессе GMS), Facebook 7.1, Mixpanel 2.4, Amplitude Kotlin 0.7, Amplitude 2.40.1 7.0, Adjust 59 (по запросу на событие). Кадры у всех одинаковые (p99 ≈ 16.9 мс), `Track()` у Mortris 22–26 мкс.
4. **Сохранность полей и доставка — отдельные метрики, и они расходятся**: на 4 наборах данных Mortris V8/V1/V7 сохраняет 100% свойств и типов (кроме клиентской валидации: события с более чем 32 свойствами отклоняются); Firebase/Facebook по их лимитам (25 параметров, 100 символов) теряют до 85% событий «целиком» на насыщенном наборе midcore; GameAnalytics теряет булевы/пустые поля (0.5–10% свойств); Adjust превращает всё в строки. **Amplitude 2.40.1 доставляет только ≈1000 из любого количества событий** — это зашитый `EVENT_MAX_COUNT=1000` (старейшие события вытесняются), а не «медленная выгрузка»: дренаж 520 секунд ничего не добавил.
5. **Сбои**: убийство процесса на 20-й секунде (50 событий/с): V8 потерял ≤ окно буфера (≈11 событий), V1 0, Kotlin/Mixpanel/HyperKit 0, **GameAnalytics потерял 437 из ≈1010, Amplitude 2.40.1 — 777 и вернул 50 дублей**. Плохая сеть (400±200 мс, 128 кбит/с, 8% обрывов): V8 доставил 3000/3000 за 16 с, V1 1599, GA 1060, Mixpanel 2829 за 15 минут, остальные ≈0 за окно ожидания (большие пачки по ~1.3–2 КБ/событие не проходят). Сервер выключен 5 минут: Kotlin и GA восстановились полностью, Mortris V1/V8 за 5 минут после возврата — нет (бэкофф до 5 минут), см. §4.
6. **Две настоящие проблемы найдены и исправлены на сервере**: дедлок `event_catalog` (#0126, воспроизводится как HTTP 500 при параллельных установках V8) и жёстко зашитые лимиты приёма (12 запросов/мин на установку при burst 30 — из-за них V1-пачки по 100 событий и маленькие пачки V8 упираются в потолок); лимиты теперь настраиваются переменными окружения (значения по умолчанию прежние).
7. **Что у Mortris хуже и это надо знать**: (а) всплеск более ≈1000 событий за один кадр теряет хвост (буфер передачи 1024 события: из 6000/20000/100000 принято ≈2100–2700); (б) инициализация 180 мс против 4–16 мс у конкурентов; (в) на низкой частоте (5 событий/с) стоимость на событие ≈3 мс CPU (пробуждения/запись очереди), а не 0.1 мс как при пачках — хотя это всё равно вдвое дешевле V1 и дешевле GameAnalytics; (г) после долгого оффлайна повторная отправка начинается не сразу; (д) открытая проблема #0127 — на схеме с очень многими вариантами формы события V8 отправляет по одному пакету за цикл (см. §4).
8. **10-минутная игровая сессия на телефоне (5 событий/с, естественные таймеры SDK, 1 повтор)**: чистый CPU на событие — Mortris V8 **2.97 мс**, V1 6.2, GameAnalytics 7.5 (≈1.1% / 2.3% / 2.8% одного ядра); вверх на событие 21 / 98 / 110 байт; пик PSS 297 / 297 / 359 МБ (без SDK 284); Mono GC0 за сессию 10 / 25 / 4. На низкой частоте V8 дешевле V1 вдвое по CPU и в пять раз по трафику, но абсолютная цена на событие в 25 раз выше, чем в пачке (пробуждения и запись очереди на каждое событие).
9. Не измерены (нужны аккаунты, которые я не вправе создавать): **Unity Analytics и ByteBrew**. Из документации: Unity Analytics отправляет пачки раз в 60 с, лимит 1 МБ на устройство за выгрузку, 10 000 событий на пользователя в сутки; ByteBrew — требует ключ приложения и серверную часть.

## 1. Что изменено по сравнению со старым прогоном и почему цифры теперь сопоставимы

| Замечание аудита | Что сделано |
|---|---|
| Разные среды (эмулятор, нативное Android-приложение, Unity) | Одно приложение: Unity 6000.3 IL2CPP release (не development), арм64, телефон. Все SDK вызываются из одного C#-зонда через тонкий Java-адаптер (JSON-строка + имя события; базу «JNI+разбор JSON» измеряет режим `noop` и вычитает). |
| Байты без TLS и заголовков | Измеряется сокет-уровень: заголовки + тела запросов и ответов (счётчик-прокси `collector2.py` для всех, включая Mortris). TLS добавляется моделью: рукопожатие (сервер — реально измерено против боевых хостов вендоров, `results/tls_handshake_hosts.json`) + 22 байта на запись + закрытие. |
| Доставка = принятие = сохранность | Три отдельные метрики: **принято SDK** (`Track` вернул успех), **доставлено** (дошло до бэкенда), **сохранность** (поля/типы после доставки, через `zz_n`-маркер события). |
| Очереди не дренировались | Хвост ждёт доставки по фактическому состоянию бэкенда (БД для Mortris, счётчик событий коллектора для остальных) или тишины 1–5 минут. |
| «Мало данных» | 4 набора: реальный Puzzle (20 непересекающихся слайсов по 3000 событий от разных установок, разделение по установкам, проверено), синтетические casual / midcore / telemetry с разной структурой. Повторы с парным дизайном (слайс r одинаков для всех SDK), доверительные интервалы Стьюдента. |
| CPU только процесса | Дельты `/proc/<pid>/stat` всех процессов до/после окна (приложение, GMS, остальные) со стороны `adb`; база Unity вычитается по ячейке `none` того же повтора. |
| Train/test | Правило `sha256(install)%5==0 → train`, 42 установки обучения, 197 отложенных, пересечений 0, слайсы только из отложенных (`results/split_verification.json`). Для синтетики «train» — отдельный поток с другим зерном, не отложенная выборка. |
| Версии | Firebase Analytics 23.0.0 (как в Firebase Unity 13.9), Amplitude 2.40.1 (как в unity-plugin) **и** Amplitude Kotlin 1.36.0 (текущий), GameAnalytics 7.2.0, Facebook core 17.0.2, Adjust 5.4.1, Mixpanel 8.2.0, HyperKit (Gamestoty). |

### Ограничения стенда (честно)

* CPU-повторов 3 на ячейку, не 30: доверительные интервалы широкие там, где эффект мал (V8 против V7/V1 по CPU **статистически неотличимы**). Остальные эксперименты (сбои, свипы, всплески) — по одному прогону на ячейку.
* Сценарий A (10 событий/с) на этом телефоне идёт на 30 кадр/с даже без SDK, и CPU там шумит сильнее эффекта; решения по нему не принимаются, он приведён для полноты.
* Firebase/Facebook/Adjust ходят на боевые серверы вендоров с фальшивыми ключами (редирект без root невозможен): их байты на проводе здесь **не** сопоставимы (повторные отправки при отказе); для них корректнее прежние замеры через MITM на эмуляторе (Firebase 73.1, Facebook 67.4, Adjust ≈2830 байт/событие, 21.10) — набор данных тогда был другой.
* Нагрузка CPU, GC и PSS на эмуляторах не использовалась; эмуляторы служили для доставки, сбоев и свипов.
* Не 30 минут, а 5 минут оффлайн и 10-минутные сессии вместо часа (время ночи ушло на повторы и отладку зависаний стенда).
* Батарею не мерили (по условию задачи).
